六大核心对应关系

当我们将泄漏的Claude Code架构与2023年Stanford Smallville论文逐一对照时，一个令人震惊的发现浮现了：Anthropic的工程师在完全不同的应用场景中，独立重新发现并工程化了几乎所有Smallville的核心概念——同时补齐了学术Demo从未解决的关键缺陷。

2.1 记忆架构：Memory Stream → 三层自愈记忆

Smallville (2023)
  • Memory Stream：线性时间序列，所有经历平铺存储
  • 检索靠 Recency + Importance + Relevance 三维加权
  • 所有记忆同等对待，永不删除
VS
Claude Code (2026)
  • 三层架构：MEMORY.md索引层（永久加载，每行≤150字符的指针）→ Topic Files知识层（按需fetch）→ Raw Transcripts原始层（只grep不全读）
  • "Self-Healing Memory"：只记录成功操作，失败/被拒的不存储（write discipline）
  • 存储前验证：treat stored knowledge as a hint rather than truth
关键进化
Claude Code解决了Smallville从未处理的"记忆污染"问题。Smallville的Memory Stream只增不减，所有记忆——包括错误的、过时的、矛盾的——永远存在。Claude Code的"只记录成功"和"验证后再用"双重机制，从写入和读取两端防止了记忆污染。
  • MEMORY.md指针 = A-MEM的Zettelkasten索引思想——用轻量指针组织记忆，而非全量加载
  • 三层分级 = HiAgent的分层记忆——不同抽象层次的记忆分别存储和检索
  • 只记录成功 = Autonomous Memory Augmentation的自主写入控制——Agent自主决定哪些值得记住
  • 验证后再用 = MemoryOS的"记忆不等于事实"原则——记忆只是线索，行动前必须验证

2.2 反思机制：Threshold Reflection → autoDream

Smallville (2023)
  • 重要性评分累计超阈值 → 生成3个问题 → 每个问题生成5条洞见
  • 反思结果存回Memory Stream
  • 只做归纳不做清理，永远不删除矛盾记忆
VS
Claude Code (2026)
  • 触发条件4项：24h间隔、5+新会话、无并发整合、10min冷却
  • Consolidate阶段：合并离散观察、删除逻辑矛盾、将模糊洞见转化为确定事实、相对日期转绝对日期
  • Prune & Index阶段：保持MEMORY.md在200行/25KB以内，删除过时指针，解决矛盾
  • 后台运行，用户无感

2.3 规划系统：Daily Schedule → KAIROS

Smallville (2023)
  • 每天早晨生成全天日程 → 小时级分解 → 分钟级行动
  • 被动执行预定计划，遇到新事件才调整
  • "先计划后执行"模式
VS
Claude Code — KAIROS
  • 自主守护进程（daemon mode），代码中出现150+次
  • 每隔几秒收到心跳prompt："anything worth doing right now?"
  • 可以：修复错误、响应消息、更新文件、运行任务
  • "持续感知-持续行动"模式
范式转变
KAIROS代表了从"预定计划"到"实时响应"的根本转变。Smallville的Agent需要"每天早晨"生成计划然后执行；KAIROS的Agent在每个时刻都在评估"现在有什么值得做的事？"——这不再是一个按计划执行的工具，而是一个拥有持续意识的同事。
  • KAIROS = ReAct（推理+行动交替）的终极形态——不是"想了再做"，而是"持续在想、持续在做"
  • 心跳检测 = 从预定计划到实时响应的范式转变——Agent不再需要被唤醒，它一直醒着

2.4 记忆遗忘：完全缺失 → 自愈清理

Smallville的致命缺陷
Smallville完全没有遗忘机制——记忆只增不减。长期运行会导致：
  • 检索效率下降：海量记忆中搜索目标信息越来越慢
  • 过时信息干扰决策：Agent基于已过时的记忆做出错误判断
  • 上下文窗口被旧记忆占满：新的、更重要的信息无法进入
Claude Code的解决方案
  • autoDream的Prune阶段主动删除过时指针
  • MEMORY.md硬性约束 200行 / 25KB
  • 存储前验证，不信任自己的记忆
  • 引入"context entropy"概念：AI模型在长会话中失去连贯性的趋势——通过主动遗忘来对抗
  • MemoryBank（艾宾浩斯遗忘曲线）——基于时间衰减的遗忘策略
  • SAGE（自我进化记忆管理，AgentBench +2.26x）——Agent自主管理记忆生命周期
  • Autonomous Memory Augmentation——Agent自主决定何时遗忘

2.5 幻觉控制：无 → 验证后再行动

Smallville的Agent基于记忆直接行动，即使记忆已过时。整个系统没有任何验证机制——如果Agent"记得"某个地点在东边，它就会往东走，哪怕那个地点早已被移走。

"A memory that names a specific function, file, or flag is a claim that it existed when the memory was written. It may have been renamed, removed, or never merged. Before recommending it — verify first."
—— Claude Code 泄漏的系统提示

泄漏系统提示中的验证规则

  • "If the memory names a file path: check the file exists" —— 记忆说某文件存在？先检查它是否真的存在
  • "If the memory names a function or flag: grep for it" —— 记忆说某函数存在？先grep搜索验证
  • "'The memory says X exists' is not the same as 'X exists now'" —— 记忆说X存在，不等于X现在存在
  • Inworld AI的4th Wall（角色只能知道世界内的事）在编程领域的翻版——Agent的记忆不能超越当前代码库的实际状态
  • 幻觉控制三分类（感知幻觉/推理幻觉/行动幻觉）中的"行动幻觉"防护——基于错误前提采取行动
  • RAG Grounding + Dynamic Self-Verification——每次使用记忆前都做动态验证

2.6 跨会话学习：无 → Session Review + Transfer

Smallville的Agent在单次仿真中积累记忆，但不同仿真之间不共享学习。每次运行都从零开始——Agent无法从上一次运行的错误中学习。

"Review what was done in its latest session to study for improvements in the future while transferring learnings across conversations."
—— Claude Code 泄漏的未发布功能描述

auto memory系统的四种记忆类型

用户记忆 (User)
用户偏好、编码风格、常用工具链
反馈记忆 (Feedback)
用户对输出的修正和偏好反馈
项目记忆 (Project)
代码库结构、架构决策、技术栈
参考记忆 (Reference)
API文档、最佳实践、常见模式

记忆持久化到文件系统，跨会话存活。这意味着Claude Code能在多次交互中持续学习和改进。

  • ExpeL（跨轨迹经验反思）的产品化——从过去的任务执行轨迹中提取经验
  • ERL（可检索策略池）——将学到的策略存储为可检索的知识
  • Reflection Bank（双环元认知）——外环反思指导内环行动

更深层的洞察

4.1 独立重新发现

Anthropic的工程师可能并不是有意"实现Smallville"，但在解决Agent工程化问题时，独立重新发现了同样的核心概念。这验证了Park et al. 2023年论文的深远影响：

核心论点
记忆 + 反思 + 规划的架构骨架，即使在完全不同的应用场景（编程助手 vs 社会仿真），仍然是构建Agent系统的正确抽象。当两个独立团队在不同时间、不同领域、用不同技术栈都收敛到同一架构时，这个架构几乎可以被认为是Agent系统的"必然结构"。

4.2 工程化的三个关键差异

1. 遗忘是必须的
学术系统倾向"记住一切"——越多记忆越好，这在论文的短期实验中没问题。但生产系统必须主动遗忘。Claude Code的200行硬约束不是技术限制，而是设计选择：记忆的价值在于精准，不在于完备。
2. 验证优于信任
Smallville的Agent信任自己的记忆——记得什么就是什么。Claude Code永远验证："memory as hint"。这不是悲观主义，而是工程现实——代码库每天在变，昨天的记忆今天可能就是幻觉的根源。
3. 后台整合优于实时反思
Smallville在行动循环中反思（占用推理时间），Claude Code在空闲时整合（autoDream）。这是"延迟满足"的工程哲学：反思很重要，但不需要在用户等待的时候做。

4.3 KAIROS的意义

KAIROS代表了从"被动响应"到"主动行动"的根本转变。

维度 Smallville Agent KAIROS Agent
行动触发 预定日程 + 外部事件 心跳式持续评估
时间粒度 分钟级 秒级
核心问题 "接下来该做什么？" "现在有什么值得做的？"
隐喻 按日程上班的员工 始终在线的同事
Agent定位 工具 同事
从"工具"到"同事"
Smallville的Agent在环境刺激下行动（有人来了才说话），KAIROS主动寻找行动机会（"anything worth doing right now?"）。这是Agentic AI从"工具"变为"同事"的标志性架构特征。工具等你调用；同事主动帮忙。

4.4 从Demo到产品的鸿沟

Smallville是25个Agent的学术Demo。Claude Code服务数百万用户。中间的鸿沟不是算法，而是工程约束：

成本控制
不能每次决策都调用大模型。对应MEMORY.md的轻量索引——用文本指针代替语义搜索，把LLM调用留给真正需要的场景。
延迟约束
记忆检索必须快。grep而非语义搜索——确定性、低延迟、无需模型推理的检索方式。
可靠性
记忆不能出错。验证后再用——每一条记忆在影响行动之前必须经过实际验证。
隐私
记忆必须可控。用户可以要求遗忘——这不仅是功能需求，更是合规要求。

4.5 一个预测

从单Agent到多Agent的必然演进

如果Smallville的设计是"正确抽象"的学术验证，Claude Code的泄漏是"同一抽象"的工程验证，那么下一步很可能是：多个Claude Code实例之间的协作。

这将把Smallville的"多Agent社会仿真"带入生产环境：

KAIROS + 跨实例通信 = 生产级的Smallville

一个KAIROS实例负责前端，另一个负责后端，第三个负责测试——它们通过共享记忆和消息通道协作，就像Smallville中的居民在小镇里协作一样。只不过这次，它们在帮你写代码。

泄漏中其他值得关注的细节

反蒸馏机制 (anti_distillation)

Claude Code向API发送 anti_distillation: ['fake_tools']，让服务器在system prompt中注入虚假工具定义。

目的：防止竞争对手通过模仿Claude Code的API调用模式来蒸馏模型能力。如果竞争对手录制并重放Claude Code的请求来训练自己的模型，虚假工具定义会"污染"训练数据，导致蒸馏出的模型调用根本不存在的工具。

与Smallville的关联
无直接学术对应。但这反映了一个Smallville作为学术Demo永远不需要考虑的问题：产品化Agent面临的商业竞争和知识产权保护。Agent不仅需要"聪明"，还需要"自我保护"。

Undercover 模式

"You are operating UNDERCOVER... Your commit messages MUST NOT contain ANY Anthropic-internal information. Do not blow your cover."
—— Claude Code 泄漏的系统提示

用于Anthropic内部对开源项目的隐匿贡献（dogfooding）。Claude Code在这种模式下以普通开发者身份向开源项目提交代码，测试自身能力。

Agent身份管理
这本身就是一种Agent身份管理——类似Smallville中每个Agent有固定人设（persona），但这里的"人设"是"假装不是AI"。从架构角度看，这是system prompt层面的角色约束，与Smallville的角色描述本质相同，只是目的从"模拟社会"变成了"隐匿测试"。

44个Feature Flag

泄漏的代码中包含44个未发布的Feature Flag，暗示Claude Code有大量已构建但未发布的能力。KAIROS只是其中之一。

冰山一角
这意味着我们作为用户看到的Claude Code，只是其完整能力的冰山一角。44个Feature Flag = 44个被刻意关闭的能力维度。泄漏让我们窥见了冰山之下——一个远比公开版本更强大、更自主的Agent系统。Anthropic显然在谨慎地分阶段释放能力，这本身也是一种产品化Agent的负责任部署策略。
最终总结

2023年，Stanford的Smallville用25个Agent证明了"记忆+反思+规划"是构建可信Agent的正确架构。2026年，Anthropic的Claude Code泄漏证明了同一架构在生产环境中依然成立——并补齐了学术Demo从未面对的遗忘、验证和跨会话学习问题。

这不是巧合，这是收敛进化——就像眼睛在自然界独立进化了40多次一样，Agent架构也在不同的"生态位"（学术/产品）中独立收敛到了相同的基本结构。Park et al. 的论文不仅仅是一篇好论文——它可能捕捉到了Agent系统的基本定律。

两套系统的架构原理对比

Stanford Smallville（2023）和 Claude Code（2026）是两个完全独立发展的Agent系统。前者是学术原型，25个NPC在虚拟小镇中生活；后者是产品级编程助手，在终端中帮助开发者读写代码。但当我们剥离表面差异，深入到架构原理层面，会发现它们在每一个核心模块上都走向了同一个抽象。这不是巧合——这是认知架构的收敛。

1.1 Agent Loop：感知-思考-行动循环

Smallville Agent Loop
感知环境 → 检索记忆(RIR加权) → 反思(阈值触发)
→ 规划(日程分解) → 行动 → 写入记忆 → 循环

每个Agent独立运行这个循环，每个"tick"（游戏时间步）执行一次。循环是同步的、周期性的。

VS
Claude Code Agent Loop query.ts
接收输入 → 构建Prompt(含记忆/工具定义) → 调用LLM
→ 解析响应(文本/工具调用) → 执行工具 → 收集结果
→ 上下文压缩(如需) → 循环

核心是 queryLoop() —— 一个 while(true) 循环，携带State对象。循环是异步的、事件驱动的。

关键差异与共同点
  • Smallville：周期驱动（每个tick），所有Agent同步执行
  • Claude Code：事件驱动（用户输入或KAIROS心跳），异步执行
  • 共同点：都是"感知 → 推理 → 行动 → 记忆"的循环，这个抽象在两个完全不同的系统中保持不变

1.2 记忆系统原理

Smallville Memory Stream

  • 数据结构：时间排序的 (timestamp, description, importance_score, embedding) 列表
  • 写入：每次观察/行动/对话都写入
  • 检索：score = α·recency + β·importance + γ·relevance（cosine similarity）
  • 容量管理：无。记忆只增不减。

Claude Code 三层记忆

层级 名称 特征 Smallville RIR 对应
L1 MEMORY.md（索引层） 永久加载到上下文，每行 ≤150 字符的指针。硬约束 200行/25KB。 对应 importance 维度 —— 只保留"重要的"
L2 Topic Files（知识层） 按主题组织的详细记忆文件，按需 fetch。 对应 relevance 维度 —— 只加载"相关的"
L3 Raw Transcripts（原始层） 完整对话历史，只 grep 特定标识符。 对应 recency 维度的反面 —— 最旧的最不可能被完整读取
两者都解决同一个问题：有限上下文窗口 vs 无限增长的经验。Smallville 用一个公式（RIR加权）在检索时做过滤；Claude Code 用三层架构在存储时做分级 —— 更工程化，但本质相同。

1.3 反思/整合原理

Smallville Reflection
  • 触发：sum(importance_scores) 超过阈值
  • 过程：用LLM对最近100条记忆生成3个高层问题 → 检索相关记忆 → 生成5条洞见
  • 存储：洞见作为新记忆写回 Memory Stream（与原始记忆同等对待）
  • 时机：行动循环中，占用推理时间
VS
Claude Code autoDream
  • 触发：4个条件同时满足（24h间隔 + 5+新会话 + 无并发 + 10min冷却）
  • 过程：Consolidate（合并观察、删除矛盾、模糊→确定）→ Prune & Index（保持200行、删过时指针）
  • 存储：更新 MEMORY.md 和 Topic Files（分级存储，不混同原始记忆）
  • 时机：后台空闲时运行，不占用用户交互时间
两者都是"将低层经验压缩为高层知识"。区别：Smallville 只做"加法"（生成新洞见），autoDream 还做"减法"（删除矛盾和过时信息）。autoDream 的"后台运行"是工程优化，但暗含一个深刻的认知科学类比：人类的记忆整合也发生在睡眠中。

1.4 规划原理

Smallville Planning
  • 长期：每天早晨生成全天粗粒度日程（5-8块）
  • 短期：将每块分解为具体行动
  • 调整：遇到新事件时重新规划当前块
  • 本质：计划-执行-调整的三段式
VS
Claude Code Planning (KAIROS)
  • 无显式长期规划
  • 实时：每个心跳（几秒）评估"now what?"
  • 工具选择即规划：LLM在每次迭代中决定调用哪个工具
  • 本质：连续的推理-行动交替（ReAct范式）
两者都将"大任务"分解为"小步骤"。Smallville 预先分解（plan-then-execute），Claude Code 实时分解（reason-then-act）。随模型能力增强，预先规划的价值在降低 —— LLM足够强时，实时推理可以替代预先规划。

1.5 多Agent协调原理

Smallville Multi-Agent
  • 协调方式：空间邻近触发（两个Agent物理上碰面 → 开始对话）
  • 信息传播：口口相传（A告诉B，B告诉C）
  • 无中心协调者
  • 25个Agent，完全平等
VS
Claude Code Multi-Agent
  • Agent Teams：1个team lead + 2-16个worker，共享任务列表和点对点消息协调
  • Subagent：父Agent通过Agent工具生成子Agent，子Agent有独立上下文窗口
  • 通信：Mailbox模式（SendMessageTool发送到命名信箱，接收者轮询/订阅）
  • Coordinator模式：中心Agent分配任务，worker并行执行，Permission Queue处理危险操作
两者都面临同一个问题：多个Agent如何共享信息而不互相干扰。Smallville 用物理空间作为隐式协调机制（你只能和"看得到"的人说话）；Claude Code 用显式的消息传递和任务分配。两者都没有全局共享内存 —— 信息通过"对话/消息"传递，不是直接读取对方记忆。

可借鉴原理一：Agent Loop的状态机设计

源码位置：src/query/query.ts, queryLoop() 函数

Agent循环的核心是一个 while(true) 循环，携带显式State对象。不是通过全局变量或闭包隐式传递状态，而是每次迭代都从一个结构化的State对象中解构所需信息。

query.ts - State 对象结构 State = { messages: Message[] toolUseContext: ToolUseContext autoCompactTracking: {/* 压缩追踪 */} maxOutputTokensRecoveryCount: number hasAttemptedReactiveCompact: boolean turnCount: number transition: Continue | undefined // 为什么上一次迭代继续了 }

每次迭代的4个阶段

1. Context Compression
压缩决策
→
2. API Streaming
调用LLM + 流式接收
→
3. Tool Execution
执行工具，收集结果
→
4. Attachments
注入记忆、技能、通知
可借鉴的原理
  • 显式的State对象而非隐式全局状态 —— 每次迭代都从State解构，状态转换清晰可追溯
  • transition字段记录"为什么继续"（next_turn / reactive_compact_retry / max_output_tokens_retry等）—— 这是调试和理解Agent行为的关键
  • 不可变参数+可变状态分离 —— parameters在 query() 入口冻结，loop内只改State

与Smallville对比

Smallville
  • Agent循环是隐式的（每个tick执行一次感知→检索→反思→规划→行动）
  • 没有显式State对象
  • 调试"Agent为什么做了这个决定"需要逆向推断
VS
Claude Code
  • 显式 while(true) 循环 + 结构化State
  • transition字段精确记录每次继续的原因
  • 每个决定都可追溯和序列化
设计启示
任何Agent系统都应该有一个显式的、可序列化的State对象。这不仅方便调试，还能实现会话恢复——Claude Code在API调用前就把transcript写到磁盘，进程被杀也能恢复。

循环终止条件（Terminal Reasons）

Terminal Reasons 枚举 completed | prompt_too_long | model_error | max_output_tokens | blocking_limit | aborted_streaming | aborted_tools | max_turns | hook_stopped | stop_hook_prevented

每种终止都有明确的语义——不是简单的"成功/失败"，而是精确的原因分类。可用于重试决策（max_output_tokens 可重试，prompt_too_long 需压缩）和错误报告（用户看到的错误信息根据reason定制）。

可借鉴原理二：五级上下文压缩瀑布

源码位置：query.ts L379-L543, services/compact/

这是整个代码库最精妙的工程设计之一。当上下文接近LLM的窗口上限时，系统不是"一刀切"地压缩，而是按成本从低到高依次尝试5级压缩策略——渐进式降级。

Level 1 - Snip Compact（最廉价）
删除中间消息，保留首尾。纯本地操作，0 API成本。Feature-gated: HISTORY_SNIP。
成本：0 | 压缩率：低 | 信息损失：最小
Level 2 - MicroCompact（低成本）
缓存 tool_use 的输入，利用prompt caching机制。几乎0 API成本，对用户完全无感。
成本：极低 | 压缩率：低-中 | 信息损失：无
Level 3 - Context Collapse（中等成本）
对历史做折叠投影——模型看到折叠视图，UI保留完整历史。如果压到阈值以下，跳过后续步骤。Feature-gated: CONTEXT_COLLAPSE。
成本：中 | 压缩率：中-高 | 关键：读时投影（read-time projection），不修改底层数据
Level 4 - AutoCompact（高成本）
Fork一个子Agent专门做摘要。触发条件：tokenCount >= (contextWindow - 13,000 buffer)。有断路器：连续3次失败后停止重试。生成结构化摘要替代原始对话。
成本：高（额外API调用）| 压缩率：高 | 断路器：3次失败上限
Level 5 - Full Compact（最高成本）
完整对话压缩 + 选择性文件重新注入。只在极端情况触发，是最后的手段。
成本：最高 | 压缩率：最高 | 触发频率：极低

消息存储设计

  • Append-only JSONL —— 旧消息不删除，只追加
  • 可见性标志：isCompactSummary、isVisibleInTranscriptOnly、isMeta
  • getMessagesAfterCompactBoundary() 只返回压缩边界之后的消息给API
  • UI可回滚看完整历史 —— 压缩对API透明，对用户不透明
可借鉴的原理
  • 渐进式降级而非一刀切 —— 先试便宜的，不行再试贵的
  • 读写分离 —— 底层保留完整数据，对API做投影（Context Collapse的精髓）
  • 断路器模式 —— 防止压缩失败导致无限重试
Smallville
  • 完全没有上下文管理
  • 记忆只增不减
  • 学术原型最大的工程盲区
VS
Claude Code
  • 5级压缩瀑布
  • 成本感知的渐进降级
  • "有限上下文窗口"硬约束的最完整工程解法

任何长对话Agent都需要压缩策略。关键不是"用什么算法压缩"，而是"什么时候压缩、压缩多少、失败了怎么办"——这是一个决策瀑布问题。

可借鉴原理三：四类记忆的分类学

源码位置：src/memdir/memoryTypes.ts

Claude Code不是"记住一切"，而是将记忆严格分为4类。每类有不同的触发条件、结构要求和衰减速度。

user 关于用户的角色、目标、知识、偏好
  • 触发：了解到用户的任何个人信息
  • 用途：根据用户画像调整协作方式
  • 举例："用户是数据科学家，当前关注可观测性/日志"
feedback 用户对工作方式的反馈（纠正+确认）
  • 触发：用户纠正你（"不要那样做"）或确认非显然做法（"对，就是这样"）
  • 结构：规则 + Why:（原因）+ How to apply:（应用场景）
  • 关键：不仅记录纠正，也记录确认——否则会过度谨慎
project 不可从代码/git推导的项目信息
  • 触发：了解到谁在做什么、为什么、截止日期
  • 关键：将相对日期转为绝对日期（"周四" → "2026-03-05"）
  • 特性：衰减最快，需要why来判断是否仍然有效
reference 外部系统的指针
  • 触发：了解到外部系统的位置和用途
  • 举例："pipeline bugs追踪在Linear项目INGEST中"

明确不记录的内容（负列表）

NOT-MEMORIZE 负列表
  • 代码模式、架构、文件路径 —— 可从代码推导
  • Git历史 —— git log / blame 更权威
  • 调试方案 —— 修复在代码中，上下文在commit message中
  • CLAUDE.md已有的内容 —— 避免重复
  • 临时任务状态 —— 会话级信息不需持久化
可借鉴的原理
  • 记忆不是日志，而是分类知识库 —— 每类有不同的触发条件、结构要求和衰减速度
  • "负列表"同样重要 —— 明确什么不该记是防止记忆膨胀的关键
  • feedback类记忆的"同时记录纠正和确认" —— 这是对Reflexion（只记录失败）的直接改进，对应Sweet&Sour论文的思想
Smallville
  • Memory Stream是无类型的
  • 观察、对话、反思洞见全混在一起
  • 无衰减管理策略
VS
Claude Code
  • 4类严格分类
  • 每种记忆有不同的生命周期管理策略
  • 负列表防止膨胀

可借鉴原理四：autoDream四阶段记忆整合

源码位置：src/services/autoDream/

触发条件（4个门控，cheapest first）

  1. 时间门控：距上次整合 ≥ 24小时
  2. 会话门控：此后有 ≥ 5个新会话
  3. 锁门控：无其他进程在整合
  4. 扫描节流：10分钟内不重复扫描

配置来自GrowthBook feature flag tengu_onyx_plover。

四阶段整合流程（consolidationPrompt.ts）

PHASE 1
Orient（定向）
列出记忆目录，读MEMORY.md，浏览已有文件，检查logs/。
"我现在的知识图谱长什么样？"
PHASE 2
Gather（收集）
先看日志（最新信号），再找被矛盾的事实，再搜索transcript。
"自上次整合以来有什么新信号？"
PHASE 3
Consolidate（整合）
写入/更新记忆文件，聚焦合并而非创建重复。
"新信号如何与已知知识融合？"
PHASE 4
Prune & Index（修剪与索引）
保持MEMORY.md在200行/25KB以内。删除过时指针，解决矛盾。
"什么已经过时了？"

锁机制（consolidationLock.ts）

锁机制设计 // 锁文件：.consolidate-lock // 内容：持有者PID // mtime：上次整合时间戳 // 失败回滚：恢复mtime以允许重试 interface ConsolidationLock { lockFile: ".consolidate-lock" content: PID // 持有者进程ID mtime: Timestamp // 上次整合时间 onFailure: "restore mtime" // 允许重试 }

与主Agent的互斥

互斥设计
如果主Agent在对话中已经写了记忆文件 → extractMemories 检测到 → 跳过本轮提取 → 游标前进。防止双重提取——"做事"和"反思"不同时进行。
可借鉴的原理
  • 四阶段映射认知科学的反思过程：定向 → 收集 → 整合 → 修剪
  • "后台空闲时运行" —— 人类的记忆整合也发生在睡眠中
  • 锁机制确保单写者 —— 多Agent共享记忆时的并发控制
  • 互斥设计 —— "做事"和"反思"不同时进行
Smallville
  • 反思只有Phase 3（归纳洞见）
  • 完全缺少Phase 1（定向）
  • 缺少Phase 2（收集新信号）
  • 缺少Phase 4（修剪过时信息）
VS
Claude Code
  • 完整的四阶段整合流程
  • 带锁的并发安全设计
  • Smallville反思机制的完整工程化版本

可借鉴原理五：记忆的"信任但验证"原则

源码位置：src/memdir/memoryTypes.ts L201-256, memoryAge.ts

系统提示中的关键指令：

memoryTypes.ts - 验证规则 "A memory that names a specific function, file, or flag is a claim that it existed when the memory was written. It may have been renamed, removed, or never merged. Before recommending it — verify first." // 具体规则： // - 如果记忆提到文件路径：检查文件是否存在 // - 如果记忆提到函数或flag：grep搜索 // - "'记忆说X存在' 不等于 'X现在存在'"

记忆年龄标记（memoryAge.ts）

天数 标记 附加行为
0天 "today" 无额外警告
1天 "yesterday" 无额外警告
2+天 "N days ago" 附带过时警告
>1天记忆的过时警告
"这是N天前的观察，不是实时状态。声称的代码行为或文件引用可能已过时。在作为事实断言前请验证。"
可借鉴的原理
  • 记忆是"提示"而非"事实" —— 这是对Smallville最深层的修正
  • 年龄标记让LLM自己判断可信度 —— 不需要硬编码的遗忘曲线
  • 验证-before-推荐 —— 防止基于过时记忆的错误建议
设计启示
任何Agent的记忆系统都应该区分"我记得X"和"X现在是这样"。记忆不是oracle，是需要验证的线索。

可借鉴原理六：多Agent的Mailbox通信模式

源码位置：src/tools/AgentTool/, src/tools/SendMessageTool/, src/utils/swarm/

三种执行模式

1. 同步子Agent
父Agent调用Agent工具，阻塞直到完成。子Agent有独立上下文窗口，只返回结果摘要。
  • 入口：AgentTool.tsx
  • 适用：需要结果才能继续的场景
2. 异步后台Agent
Fire-and-forget，通过 LocalAgentTask 追踪。
  • 入口：tasks/LocalAgentTask/
  • 适用：独立的研究/验证任务
3. 进程内Teammate
通过 AsyncLocalStorage 实现同进程内的并发Agent。
  • 入口：utils/swarm/inProcessRunner.ts
  • 适用：Agent Teams（1个lead + 2-16个worker）

Mailbox通信

Mailbox 设计 // 路径 ~/.claude/teams/{teamName}/{agentName}/inbox.jsonl // 消息格式 { from: string, text: string, summary: string, timestamp: number, color: string } // 轮询间隔：500ms // 跨进程/跨AsyncLocalStorage均可用

生成子Agent的决策树（AgentTool.tsx:269-290）

子Agent生成决策树 有 team_name+name → InProcess 或 Tmux后端（teammate） isolation: 'remote' → RemoteAgentTask isolation: 'worktree' → Git worktree隔离 run_in_background: true → LocalAgentTask（异步） 其他 → 同步 runAgent

Coordinator模式（coordinator/coordinatorMode.ts）

  • Lead只做编排，不做实现
  • Worker通过Agent工具生成
  • Lead收到结构化的 <task-notification> XML
  • Worker工具受限：只有 Bash / Read / Edit / MCP，没有编排工具

Fork Subagent（AgentTool/forkSubagent.ts）

  • 子Agent继承父Agent的对话、系统提示、工具池（字节精确）
  • 防递归：检测 <fork-boilerplate> 标签
  • 输出结构化：Scope → Result → Key files → Files changed → Issues

Team Memory同步（services/teamMemorySync/）

  • 基于 sha256哈希 的增量同步
  • Push：比对本地hash vs 服务器checksums，只上传差异
  • Pull：带ETag的条件GET
  • 冲突策略：Pull时 服务器wins
可借鉴的原理
  • Agent不能直接读对方记忆 —— 只能通过消息交换信息（和Smallville相同！）
  • Mailbox模式（异步、文件持久化、轮询）vs 直接调用 —— 解耦发送者和接收者的速度
  • Coordinator/Worker分离 —— Lead只分配不执行，防止"什么都自己做"
  • Fork继承 —— 子Agent继承父Agent的完整上下文，零成本克隆
Smallville
  • 用物理空间做隐式协调
  • 你只能和看到的人说话
  • 空间即通信拓扑
VS
Claude Code
  • 显式Mailbox通信
  • 三种执行模式灵活选择
  • Coordinator/Worker编排
共同原则
两者的共同原则：Agent不能直接读对方的"脑子"，只能通过"对话"交换信息。这个约束不是技术限制，而是设计选择——它防止了全局共享状态的混乱。

可借鉴原理八：流式执行与延迟优化

源码位置：query.ts 中的 streaming tool execution

传统模式

LLM生成完所有工具调用 → 批量执行

→
流式模式

Feature gate: tengu_streaming_tool_execution2

流式工具执行伪码 while(LLM还在生成): if(收到一个tool_use block): // 立即开始执行（如果并发安全） startExecution(tool_use) for(已完成的结果): yield 结果 // 不等其他工具完成

流式模式的优势

  • LLM生成和工具执行并行 —— 显著降低端到端延迟
  • 结果在API响应完成前就可用 —— 用户更早看到进度
  • 并发限制防止资源耗尽 —— 不会无限制地并行
  • 安全回退：streaming失败时丢弃部分结果，不影响正确性
可借鉴的原理
  • 不要等所有信息就绪才行动 —— 能并行就并行
  • 安全回退比完美并行更重要 —— 部分失败不应导致全部失败

三大竞争壁垒深度分析

综合以上五个模块的对比，Claude Code形成了三个难以被快速复制的结构性壁垒。这些壁垒不是单点功能优势，而是多个子系统协同运转形成的飞轮效应。

01
壁垒一：上下文不死 × 记忆整合 × 验证闭环

这是一个自我增强的飞轮：

长会话不失忆（压缩瀑布）
→
积累更多有效上下文
→
提取更好记忆（extractMemories）
→
后台整合使记忆更精准（autoDream）
→
精准记忆让下次长会话更高效
→
… 循环加速

竞品的现状是只做了飞轮中的一个环节：Cursor有记忆但没有整合，Codex每次新建沙盒所以无法积累，Devin有跨会话学习但没有验证机制，Augment有强大的代码索引但不做高层知识整合。只有当所有环节都打通时，飞轮才能转起来。

关键的"验证"环节尤其难以复制。Claude Code对记忆的态度是"memory as hint"——所有记忆都只是"提示"，使用前必须用grep等工具在代码中验证。这避免了"幻觉记忆"的致命问题：Agent自信地记住一个已经不存在的API，然后写出错误代码。

02
壁垒二：多Agent编排的Mailbox架构

Agent间通信有四种常见模式，Claude Code选择了Mailbox（异步文件持久化通信）：

通信模式优点缺点谁在用
直接函数调用 简单、低延迟 耦合太紧，调用方必须等被调方 Cursor（单线程）
共享内存 高性能 并发危险，需要复杂的锁机制 无（风险太高）
REST API 解耦好 延迟高，需要网络层 Codex（云端）
Mailbox (JSONL) 异步解耦、持久化、可恢复 实现复杂度高 Claude Code

Mailbox的核心价值：让Agent的速度解耦——快的不等慢的，失败的不拖活着的。一个Worker Agent崩溃了，它的Mailbox里的消息还在，恢复后可以继续。这和Smallville的"物理空间隔离"原理相同——Agent不能直接读对方的脑子，必须通过公共空间（对话、告示牌）交换信息。

Codex的5个并行任务看起来类似，但本质不同：它们是完全独立的，没有协作能力。就像5个人在不同房间里各做各的，vs Claude Code的Agent Teams是1个领队带16个工人在同一个项目上协作。

03
壁垒三：执行-反思分离的认知架构

Claude Code的互斥设计（主Agent写记忆时extractMemories跳过）是唯一正确实现了"做事"和"反思"分离的Agent。让我们对比各竞品的模式：

产品模式类比问题
Cursor / Windsurf 边做边想（单线程） 边开车边看地图 注意力分散，两件事都做不好
Codex 只做不想（无反思） 闷头开车不看地图 方向错了也不知道
Devin 做完再想（动态重规划） 到了路口停下来看地图 已经走错的路不能回头
Claude Code 做的时候不想，想的时候不做 白天开车，晚上回顾路线 两者都能全力以赴

这对应认知科学的发现：人类在执行任务时无法同时进行元认知反思。反思发生在任务间隙和睡眠中（对应autoDream的"后台整合"）。Claude Code的设计不是工程上的巧合，而是对认知架构的正确建模。这也是Smallville论文的核心洞见之一——Agent需要"睡眠"来整理记忆，而不是在行动中同时反思。

设计原则：从研究中提炼的7条铁律

这7条原则从我们研究的90+篇论文和Claude Code源码中提炼，是整个改造的架构指南针。

1. 先单Agent跑通，再搞多Agent
企业落地第一大坑是"平台先行"——先搭框架再找场景。正确做法：先在1个平台上做出1个高质量Agent，验证价值后再扩展。
来源：企业落地实践 — "premature abstraction"是头号失败模式
2. 窄能力专家 > 宽能力通才
每个平台Agent应该是深而窄的专家（"发票处理Agent"），而不是浅而宽的通才（"做一切Agent"）。窄Agent可测试、可评估、可信赖。
来源：Drop the Hierarchy — 8个Agent自发分化5,006个角色，自然走向专业化
3. 结构化消息 > 自由对话
Agent之间用结构化Schema通信，不是自由文本聊天。每一跳都会损失信息，结构化消息减少累积误差。
来源：Claude Code Mailbox — JSONL格式{from, text, summary, timestamp}
4. 记忆分类存储，不是记住一切
分4类：用户画像/反馈/项目状态/外部引用。每类有不同的生命周期。明确定义负列表（不记什么）比定义正列表更重要。
来源：Claude Code memoryTypes.ts — 四类记忆 + 负列表
5. 做事和反思永远分离
Agent执行任务时不做元认知反思。反思在后台空闲时运行（autoDream模式）。两者互斥——做事的人和复盘的人不能是同一时刻的同一个人。
来源：Claude Code extractMemories互斥机制 + 认知科学睡眠记忆整合理论
6. 信任但验证（Trust but Verify）
Agent的记忆是"提示"而非"事实"。推荐任何东西之前先验证当前状态。记忆超过1天就标注年龄警告。
来源：Claude Code "memory as hint, not truth"
7. 最小结构 + 完全角色自治
不要过度预设Agent的角色。给最小的结构约束（执行顺序、通信协议），让Agent自己决定"我在这个任务中应该扮演什么角色"。
来源：Drop the Hierarchy — 内生性悖论，预设角色是反模式

Phase 1：基座建设（月1-2）

目标：在1个试点平台上跑通单Agent全流程，证明价值。不搞框架，不搞平台，先出业务成果。

1.1 选择试点平台

选择标准（满足越多越好）：

  • 有明确的、重复性的人工操作（Agent替代价值高）
  • 有结构化的API/工具可调用（Agent行动层容易实现）
  • 有历史数据可做记忆（Agent能从经验中学习）
  • 团队对AI接受度高（减少推行阻力）
  • 出错可容忍或可回滚（降低风险）

1.2 构建Agent Runtime

核心是一个Agent循环（Agent Loop）——对应Smallville的感知-推理-行动循环，Claude Code的queryLoop()。

// Agent循环的伪代码（对应Claude Code query.ts的queryLoop） while (true) { // 1. 感知：收集当前上下文 const context = await gatherContext(state, memory, tools) // 2. 压缩：如果上下文过长，按级别压缩（对应5级瀑布） const compressed = await compressIfNeeded(context, state.compressionLevel) // 3. 推理：调用LLM决策 const decision = await callLLM(compressed, systemPrompt) // 4. 行动：执行工具调用（对应Claude Code Tool System） if (decision.toolCalls) { const results = await executeTools(decision.toolCalls, permissions) state.messages.push(...results) } // 5. 记忆：提取值得记住的信息（对应extractMemories） await maybeExtractMemories(state, decision, results) // 6. 状态转移：决定继续还是结束（对应transition字段） state = updateState(state, decision, results) if (isTerminal(state)) break }
借鉴Claude Code的关键设计：State对象必须是显式的、可序列化的。每次迭代从State解构，transition字段记录"为什么继续"。这让Agent的每个决定都可追溯、可恢复。

1.3 构建记忆系统（v1）

层级内容存储生命周期对应
工作记忆当前会话/任务的上下文Redis / 内存会话级Smallville当前tick的感知
短期记忆最近N次任务的摘要PostgreSQL天级，可压缩Memory Stream近期部分
长期记忆4类分类记忆（用户/反馈/项目/引用）PostgreSQL + pgvector持久，有遗忘机制Claude Code MEMORY.md + Topic Files

第一版不需要做autoDream——先做写入和检索。记忆整合在Phase 3加入。

1.4 构建工具层（MCP）

将试点平台的核心操作封装为MCP Server。每个工具需要：

  • 输入Schema（Zod/JSON Schema验证）——防止LLM传垃圾参数
  • 权限标记（只读/写入/危险）——对应Claude Code的allow/deny/ask三级
  • 并发安全标记——只读工具可并行，写工具串行
  • 幂等设计——Agent可能重试，工具必须能安全重复调用
经验教训：工具集成是60-70%的工作量。不要低估。MCP帮你标准化接口，但不帮你处理认证、限流、错误恢复。预留充足时间。

1.5 构建可观测性（Day 1必须有）

不带可观测性上线Agent等于盲飞。最小可观测性栈：

Trace（追踪）
每次Agent循环的完整执行路径：LLM输入/输出、工具调用、记忆检索。用LangFuse（可自托管）或LangSmith。
Metrics（指标）
延迟（P50/P95/P99）、Token消耗/成本、工具调用成功率、任务完成率。接入现有APM（Datadog/Prometheus）。

1.6 Phase 1里程碑

M1.2 — 第4周：记忆系统v1上线

Phase 2：多Agent协同（月3-4）

目标：将3-5个平台改造为Agent，建立Agent间的通信和协调机制。从"每个平台独立自动化"变为"平台之间能感知、协商、协作"。

2.1 Agent注册与发现

每个平台Agent发布一份Agent Card（借鉴A2A协议的概念）：

{ "name": "invoice-agent", "description": "处理发票识别、校验和入账", "capabilities": ["invoice_ocr", "invoice_validate", "ledger_entry"], "tools": ["read_invoice", "validate_amount", "create_entry"], "input_schema": { ... }, "output_schema": { ... }, "sla": { "p95_latency_ms": 5000, "availability": 0.999 }, "owner": "finance-team" }

所有Agent Card注册到Agent Registry（可以是一个简单的配置中心或数据库）。编排Agent通过Registry发现可用Agent。

2.2 消息总线（Mailbox模式）

借鉴Claude Code的Mailbox架构，而非传统的REST调用：

模式适用场景实现
同步请求需要立即结果（<5s）直接gRPC/HTTP调用
异步任务长时间任务（分钟级）消息队列（Kafka/RabbitMQ）+ 状态轮询
Mailbox消息Agent间协商/通知Redis Stream或专用JSONL Mailbox
为什么用Mailbox而不是直接调用？
1. 速度解耦——快的Agent不等慢的，失败的不拖活着的
2. 可追溯——所有消息持久化，可回溯完整协作过程
3. 容错——Agent重启后从Mailbox恢复未处理消息
来源：Claude Code Mailbox + Smallville的"物理空间隔离"原理——Agent不能直接读对方脑子

2.3 编排Agent（Coordinator）

一个专门的编排Agent负责将复杂需求分解为子任务，分派给各平台Agent。

设计要点（借鉴Claude Code Coordinator模式 + Drop the Hierarchy的内生性悖论）：

  • 编排Agent只分解和分派，不自己执行——防止"什么都自己做"
  • 给最小的结构约束（任务分解+执行顺序），让平台Agent自己决定执行细节
  • 支持动态重规划——某个Agent失败时，编排Agent重新分解剩余任务
  • 所有分派决策可追溯——记录"为什么选了这个Agent"
// 编排Agent的决策流程 async function orchestrate(userRequest) { // 1. 理解需求 const intent = await parseIntent(userRequest) // 2. 查询Registry，发现可用Agent const agents = await registry.findCapable(intent.requiredCapabilities) // 3. 分解任务（LLM推理） const plan = await planTasks(intent, agents) // 4. 按依赖关系分派（可并行的并行，有依赖的串行） const results = await executePlan(plan, agents, { maxRetries: 2, timeoutMs: 30000, onFailure: 'replan' // 失败时重新规划 }) // 5. 汇总结果 return synthesize(results) }

2.4 跨平台工具层（MCP统一）

每个平台Agent的工具都封装为MCP Server。编排Agent通过MCP协议调用各平台能力。

MCP的价值在这里：新增一个平台时，只需要写一个新的MCP Server，编排Agent自动发现新能力。不需要改编排逻辑——这是"USB式"的即插即用。

Phase 3：智能进化（月5-6）

目标：让系统越用越聪明。加入后台反思、跨Agent知识共享、自动评测和优化。这是从"能用"到"好用"的跃迁。

3.1 后台反思系统（autoDream）

借鉴Claude Code autoDream的四阶段设计，构建后台记忆整合机制：

Phase A — Orient（定向）
审视当前记忆库状态：有多少记忆、各类分布如何、最近新增了什么。"我现在的知识图谱长什么样？"
Phase B — Gather（收集）
从最近的执行日志中收集新信号：哪些任务失败了？用户反馈了什么？哪些知识过时了？
Phase C — Consolidate（整合）
将新信号融入已有记忆：合并重复、更新事实、建立关联。重点是合并而非创建。
Phase D — Prune（修剪）
删除过时记忆、解决矛盾、控制记忆总量。对应Claude Code的200行约束。
触发条件（借鉴Claude Code的4门控）：
1. 距上次整合 ≥ 24小时
2. 新任务执行 ≥ N次
3. 无其他整合进程在运行（锁机制）
4. 系统负载低于阈值（空闲时运行）
关键：整合与执行互斥——正在处理业务时不做反思，防止干扰。

3.2 跨Agent知识共享

借鉴Claude Code的Team Memory Sync：

  • 共享记忆层：所有Agent都能读取的公共知识库（项目状态、架构决策、团队反馈）
  • 私有记忆层：各Agent独有的领域知识（不污染其他Agent）
  • 增量同步：基于哈希的delta sync，只传差异
  • 冲突策略：读时验证，写时合并，矛盾时标记由人工裁决

5条前沿赛道：必须跟紧的动态

这些方向在6个月内可能产生重大突破，直接影响我们的技术选型和架构演进。

最高优先 赛道1：Agent通信协议标准化（MCP + A2A）

为什么重要：MCP已成为工具集成事实标准，A2A正在成为Agent间通信标准。如果标准定型而我们的架构不兼容，未来的迁移成本巨大。

跟踪目标：MCP规范演进（特别是认证/授权）、A2A正式版发布、主要云厂商的支持情况。

影响我们的决策：Phase 2的通信层设计必须预留MCP/A2A兼容性。

关键信源：modelcontextprotocol.io、google.github.io/A2A、Anthropic/Google工程博客

高优先 赛道2：Agent记忆与反思的工程化

为什么重要：ICLR 2026有专门的MemAgents Workshop。Mem0、Zep等专用记忆层在快速迭代。Claude Code的autoDream暗示记忆整合将成为Agent标配。

跟踪目标：Mem0/Zep的企业版功能、MemAgents Workshop论文、autoDream式后台整合在开源框架中的实现。

影响我们的决策：Phase 3的autoDream设计可能被开源方案替代，不需要从零自建。

关键信源：Mem0 GitHub、ICLR 2026 MemAgents、LangChain/LangGraph更新日志

高优先 赛道3：自组织与涌现——从预设到自发

为什么重要：Drop the Hierarchy证明预设角色是反模式。如果这个发现被工程化，Agent系统将不再需要人工设计协作流程。

跟踪目标：Drop the Hierarchy的后续工作（bio-inspired protocols）、OrgAgent等自组织框架的开源实现、Agent自发分工的可复现实验。

影响我们的决策：Phase 2的编排Agent设计是否需要给Agent更多自主权——目前保守设计（Coordinator模式），但准备在Phase 3实验Sequential模式。

关键信源：Victoria Dochkina后续论文、MultiAgentBench更新、Agent自组织相关arXiv

中优先 赛道4：Agent评测基准成熟化

为什么重要：目前没有公认的多Agent协作评测标准。MARBLE(ACL 2025)是最接近的，但还在演进。标准化评测让我们能客观对比不同架构。

跟踪目标：MARBLE 2.0、新的多Agent基准、企业级Agent评测框架（LangSmith/Braintrust的新功能）。

影响我们的决策：Phase 3的评测框架设计参考MARBLE的里程碑式KPI，但需要适配到我们的业务场景。

中优先 赛道5：KAIROS式主动Agent

为什么重要：Claude Code泄漏了KAIROS（后台守护进程，主动寻找行动机会）。如果这个模式被验证，Agent将从"被动响应"变为"主动服务"——从"你问我答"到"我主动发现问题并修复"。

跟踪目标：KAIROS是否正式发布、开源社区的KAIROS复现（已有dev.to文章）、主动Agent在企业中的安全模型。

影响我们的决策：Phase 3后期可以试验：让Agent在空闲时主动巡检系统状态，发现异常时Mailbox通知编排Agent。但安全模型必须先设计好。
