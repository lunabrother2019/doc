Reflexion 三组件架构 vs 工业解耦架构 后加

Reflexion (Shinn 2023) 提出了 Actor + Evaluator + Self-Reflection 的三组件串联闭环。 现代工业 coding agent（以 Claude Code / free-code 为例）走了另一条路：把反思与验证彻底解耦。 本文从原理、实现、优缺点三个维度做系统对比，并附完整的论文索引和原始链接。

原理：Reflexion 的三个组件

Reflexion (Shinn et al., 2023) 将 agent 的学习过程拆成三个显式组件，每个组件有独立职责，串联形成闭环：

① Actor（执行器）

生成 action trajectory —— 接收任务描述 + 历史反思，输出一系列动作。可以是任何 LLM agent 架构：ReAct、CoT、Plan-and-Solve 等。

输入：task + memory buffer
输出：trajectory τ

② Evaluator（评估器）

对 trajectory 打分。可以是 binary（pass/fail）或 scalar（0-1 分值）。必须是外部信号 —— Reflexion 论文自己也不信任 LLM self-eval。

输入：trajectory τ + ground truth
输出：reward r ∈ {0, 1} 或 r ∈ [0, 1]

③ Self-Reflection（自我反思）

只在 Evaluator 判 FAIL 时触发。LLM 分析失败轨迹，生成自然语言反思（"我错在哪、下次怎么改"），写入 episodic memory buffer。

输入：trajectory τ + reward r + task
输出：verbal reflection sr → memory

串联闭环公式

  ┌─────────────────────────────────────────────────────────────────────┐
  │                    Reflexion 串联闭环（per-trial）                   │
  │                                                                     │
  │   task + memory ──→ Actor ──→ trajectory τ                         │
  │                                    │                                │
  │                                    ▼                                │
  │                              Evaluator                              │
  │                              ┌────┴────┐                            │
  │                         PASS │         │ FAIL                       │
  │                              ▼         ▼                            │
  │                           完成    Self-Reflection                    │
  │                                        │                            │
  │                                        ▼                            │
  │                              episodic memory buffer                 │
  │                                        │                            │
  │                               ┌────────┘                            │
  │                               ▼                                     │
  │                    下一个 trial（Actor 再次执行）                      │
  └─────────────────────────────────────────────────────────────────────┘

关键特征：

  • 三组件串联：Evaluator 的 FAIL 信号是 Self-Reflection 的触发条件
  • per-trial 粒度：每次 trial 执行完毕后立刻评估 + 反思
  • 需要 ground truth：Evaluator 不是 LLM 猜测，是外部 oracle（unit test / game score / benchmark accuracy）
  • 有 trajectory 重试：同一个任务可以失败后从头再来

Reflexion 论文中的 Evaluator 实例

任务场景Evaluator 类型Ground Truth 来源
HumanEval（代码生成）Unit test pass/fail任务自带 test cases
ALFWorld（家庭任务仿真）Task success oracle仿真环境判定任务完成
HotPotQA（多跳问答）Exact match / F1标注答案
核心洞察
Reflexion 看似是 "LLM 自主学习"，但它的学习信号不来自 LLM 自身。Evaluator 是外部 oracle。Self-Reflection 只是把外部信号翻译成自然语言存入 memory。没有 oracle，这个闭环就断了。

实现 A：Reflexion 串联闭环

架构示意

  Trial 1:  Actor ──→ τ₁ ──→ Evaluator ──→ FAIL ──→ Self-Reflection ──→ memory
  Trial 2:  Actor(+memory) ──→ τ₂ ──→ Evaluator ──→ FAIL ──→ Self-Reflection ──→ memory
  Trial 3:  Actor(+memory) ──→ τ₃ ──→ Evaluator ──→ PASS ──→ 完成

核心实现细节

Actor 层

  • Reflexion 原文使用 ReAct 作为 Actor（Thought → Action → Observation 循环）
  • Actor 接收 task description + 之前所有 trial 的 self-reflection 作为额外 context
  • Actor 本身不做反思，只负责执行

Evaluator 层

  • 在 HumanEval 上：生成代码 → 跑 unit test → pass/fail（最简单的外部 evaluator）
  • 在 ALFWorld 上：提交动作序列 → 仿真器判定任务是否完成
  • Evaluator 的输出是 binary signal，不是自然语言
  • Self-Refine (Madaan 2023) 与此不同：它让 同一个 LLM 既生成又评估 —— 本质是 self-evaluation。Reflexion 的 evaluator 是外部的。

Self-Reflection 层

  • 只在 FAIL 时触发（PASS 不反思 —— 这是 Reflexion 与 Sweet & Sour 等思路的区别）
  • Prompt："Given the failed trajectory and the reward signal, what went wrong and how should the approach be modified?"
  • 输出是自然语言（verbal reinforcement），写入 sliding window episodic memory
  • Memory 有容量限制（论文中 window size = 3），旧的反思被丢弃

Episodic Memory Buffer

  • 存储格式：每条 entry = 一段自然语言反思 + 对应的 trial 编号
  • 生命周期：within-task（任务结束后丢弃，不跨任务持久化）
  • 注入方式：拼接在 Actor 的 prompt 末尾，作为"前人经验"

论文实验结果

任务基线 (无反思)Reflexion提升最大 trial 数
HumanEval (pass@1)80.1%91.0%+10.9pp4
ALFWorld (success)75%97%+22pp12
HotPotQA (EM)34%51%+17pp5

实现 B：工业解耦架构（free-code / Claude Code）

以 free-code（Claude Code 开源 fork）为代表的工业 coding agent，将 Reflexion 的三个组件解耦成三个独立系统，各自有不同的触发条件、时间尺度和执行上下文。

架构示意

三大系统详解

Actor 系统：query.ts 主循环

  • ReAct 模式的工程化实现 —— Thought → Tool Call → Observation 循环
  • 与 Reflexion 的 Actor 几乎完全对齐，区别是没有 trial 重试（每个 turn 只执行一次）
  • 每个 turn 结束后通过 stopHooks.ts 触发反思系统（fire-and-forget，不阻塞主循环）
  • 主 agent 也可以自己直接写 memory（L0），如果写了则 extractMemories 跳过

反思系统：extractMemories (L1) + autoDream (L2)

extractMemories (L1)autoDream (L2)
触发频率每个 turn（throttle default = 1）≥24h 且 ≥5 个 sessions
作用域本 session 内最近 N 条消息跨多个 sessions 的 transcript
执行方式runForkedAgent，共享 prompt cacherunForkedAgent，共享 prompt cache
目标从对话中提取值得持久化的信息归纳长期模式、合并/淘汰旧 memory
是否验证❌ 明文禁止："Do not waste any turns attempting to investigate or verify"❌ 不验证，只归纳
写入目标MEMORY.md 文件系统（user / feedback / project / reference 四类）
成功也反思？✅ 是（不依赖 FAIL 信号）✅ 是（综合所有 sessions）

验证系统：verification agent

  • 触发方式：主 agent 通过 Agent 工具调用 subagent_type="verification"
  • 触发条件：nudge 而非 enforce —— TodoWriteTool / TaskUpdateTool 在关闭 3+ tasks 后加 NOTE 提示；系统 prompt 加 "the contract"
  • 核心原则："reading code is not verification. Run it." + "you cannot self-assign PARTIAL"
  • FAIL 后行为：主 agent 修复 → resume verifier → repeat until PASS（类似 Reflexion 的重试，但不是整个 trajectory 重试）
  • 开放范围：ant-only A/B（tengu_hive_evidence 3P default = false）
解耦的核心设计决策
  • 反思不需要 FAIL 信号 —— 成功也反思，因为有价值的不只是"错误经验"，还有"用户偏好"和"项目知识"
  • 验证不写 memory —— verifier 只输出 VERDICT，不存储反思到 memory。修复是主 agent 的事
  • 两个系统互不引用 —— extractMemories 和 autoDream 不读 verification 结果；verifier 不读 MEMORY.md

优缺点对比

维度对比表

维度Reflexion 串联闭环工业解耦架构
任务边界 ✅ 清晰（benchmark 任务有明确开始/结束） ✅ 无需清晰边界（反思按时间窗口触发，不依赖任务完成信号）
Ground truth 依赖 ⚠ 强依赖（没有 oracle 则闭环断裂） ✅ 弱依赖（反思不需要评估信号；验证用真实命令输出替代 oracle）
单任务提升速度 ✅ 快（per-trial 迭代，HumanEval 4 次 trial 内收敛） ⚠ 慢（反思按天/周级沉淀，当前 task 不直接受益）
跨任务泛化 ❌ 无（episodic memory 任务结束即丢弃） ✅ 强（MEMORY.md 持久化，跨 session 沉淀偏好和知识）
错误反思的风险 ⚠ 高（论文 §5.2 承认：错误反思使后续 trial 更糟） ✅ 低（fork 隔离 + 必须经过"冷启动"才影响下一个 session = 隐式 staleness check）
Self-eval 风险 ✅ 低（evaluator 是外部 oracle） ✅ 低（verifier 必须跑真实命令，明文禁止 "reading code is not verification"）
延迟成本 ⚠ 高（evaluator + reflection 在主循环内，阻塞下一步） ✅ 低（反思 fire-and-forget，共享 prompt cache，主循环 0 阻塞）
Token 成本 ⚠ 高（每次 trial 重新执行整个 trajectory） ✅ 低（fork 共享 prompt cache，增量成本 ≈ 几百 tokens）
适用场景 有 oracle 的封闭任务（benchmark / 编程题 / 仿真环境） 无 oracle 的开放任务（真实软件工程、长期协作）

Reflexion 串联闭环的优势

适合什么
  1. 有清晰 ground truth 的单任务迭代 —— benchmark、竞赛编程、自动化测试驱动的代码生成
  2. 需要快速收敛 —— 4 次 trial 内从 80% → 91%（HumanEval），不需要等"下个 session"
  3. 任务可重试 —— 失败代价低（benchmark 环境可以随时 reset）
不适合什么
  1. 没有 oracle 的开放任务 —— "改进这段代码的可读性"没有 unit test 可以判 PASS/FAIL
  2. 失败代价高的场景 —— 真实代码库里"重试整个 trajectory"意味着 revert 大量修改
  3. 跨任务学习 —— episodic memory 任务结束即丢，下一个完全不相关的任务无法受益

工业解耦架构的优势

适合什么
  1. 真实软件工程 —— 任务边界模糊、没有预定义 test、用户随时改方向
  2. 长期协作 —— 跨天/周/月的知识沉淀，agent 越用越懂你
  3. 成本敏感 —— prompt cache 共享让高频反思在商业场景可行
不适合什么
  1. 需要当前 task 内快速迭代 —— 反思按天/周级沉淀，对"这次就要对"的场景无直接帮助
  2. 有 oracle 但不用 —— 如果项目有完善的 test suite，纯 fork 反思不如 Reflexion 直接拿 test 结果迭代
  3. verification agent 还在 A/B 阶段 —— 外部用户 default 没有验证系统，闭环不完整

根本差异图

  Reflexion:  反思 ←依赖← 评估 ←依赖← 执行     三者串联，缺一不可

  解耦架构:  反思 ────────── 执行 ────────── 验证   三者独立，各自运行

综合判断

不是谁优谁劣，是问题不同

Reflexion 解的是"给定 oracle，如何最快收敛到正确答案"。工业解耦架构解的是"没有 oracle，如何在长期使用中持续改善"。前者是优化问题，后者是适应问题。用 Reflexion 的框架评价 free-code 是 category error；反过来也一样。

最佳组合假说

两种架构并非互斥。一个理想的 coding agent 可以同时实现两者：

  1. 有 test suite 的项目：Reflexion 式闭环 —— 跑测试、反思、重试，直到 pass
  2. 没有 test 的项目 / 跨任务维度：工业解耦架构 —— fork 反思沉淀知识、opt-in 验证
  3. long horizon：解耦反思持续运行，Reflexion 闭环在有 oracle 信号时按需激活

事实上，free-code 的 verification agent + FAIL → fix → resume 循环已经是 Reflexion 式闭环的雏形，只是 evaluator 不是预定义 test 而是 "verifier 自主 figure out how to verify"。如果项目有 test suite，verifier 会自然地跑那些 tests —— 此时它就退化成 Reflexion 的 evaluator。

真正的创新不是"反思在循环外"，而是"反思与验证的解耦"
  • Reflexion 把"我错在哪"和"结果对不对"捆绑在一起（evaluator FAIL → self-reflection）
  • free-code 把两者分开：反思不依赖"我错了"（成功也反思）；验证不产出反思（只给 VERDICT）
  • 解耦的好处：反思可以高频运行（因为不需要等 FAIL），验证可以 opt-in（因为不需要绑定反思）
  • 解耦的代价：当前 task 内的快速迭代不如 Reflexion；需要 verification agent 成熟后才有完整闭环

Language Agent Tree Search Unifies Reasoning Acting and Planning in Language Models
Zhou, A., Yan, K., Shlapentokh-Rothman, M., Wang, H., & Wang, Y.-X. (2023).
MCTS + ReAct + ToT + Reflexion 的集大成。用 Monte Carlo Tree Search 统一推理、行动和规划，在 HumanEval 达到 94.4%（超过 Reflexion 的 91.0%）。与本文对比：LATS 证明了把评估和搜索结合在循环内可以超越 Reflexion，但其 MCTS 搜索的 token 成本极高 —— 这正是工业 coding agent 不采用的原因。
arXiv:2310.04406 GitHub: lapisrocks/LanguageAgentTreeSearch
学术上的"终极版 Reflexion"。但高 token 成本阻止了工业采用，印证了 free-code 选择解耦架构的成本考量。

记忆与知识沉淀相关论文

Generative Agents: Interactive Simulacra of Human Behavior
Park, J. S., O'Brien, J. C., Cai, C. J., Morris, M. R., Liang, P., & Bernstein, M. S. (2023). UIST 2023.
斯坦福小镇 —— 本研究项目的核心论文。其 Memory Stream（recency + importance + relevance 三维检索）和 Reflection（重要性阈值触发的高阶洞察生成）是 free-code 记忆系统的思想源头。关键区别：Generative Agents 的反思是主动触发（importance 累积到阈值）且在主循环内，free-code 的反思是定时触发（24h + 5 sessions）且在 fork 里。
arXiv:2304.03442 GitHub: joonspk-research/generative_agents
free-code 的 MEMORY.md 系统（四类 memory + MEMORY.md 索引）可以看作 Generative Agents Memory Stream 的工程化简化版。
Voyager: An Open-Ended Embodied Agent with Large Language Models
Wang, G., Xie, Y., Jiang, Y., Mandlekar, A., Xiao, C., Zhu, Y., ... & Anandkumar, A. (2023).
Minecraft 中的自动课程 + 技能库系统。Voyager 的 skill library（可执行代码 + 嵌入检索）是一种跨任务持久化记忆。与 free-code 的 MEMORY.md（自然语言 + 文件系统检索）是同一问题的两种解法。关键区别：Voyager 存的是可执行技能（代码），free-code 存的是自然语言知识（偏好、上下文、反馈）。
arXiv:2305.16291 GitHub: MineDojo/Voyager
跨任务知识持久化的另一种范式。free-code 的 MEMORY.md ≈ Voyager skill library 的自然语言版。

学习信号与人类反馈相关论文

Training Language Models to Follow Instructions with Human Feedback
Ouyang, L., Wu, J., Jiang, X., Almeida, D., Wainwright, C., Mishkin, P., ... & Lowe, R. (2022). NeurIPS 2022.
InstructGPT / RLHF 奠基论文。本文第 6 节论点的核心类比对象：free-code 的 autoDream 本质上是 RLHF 的轻量化在线版本 —— human feedback 隐式编码在多轮交互里（用户的"不对"/"继续"就是 reward signal），autoDream 通过观察 5 个 session 的轨迹把这些隐式反馈提炼成 memory。区别是 RLHF 更新模型权重，autoDream 更新文本记忆。
arXiv:2203.02155
"用户即 evaluator"的理论基础。free-code 的反思系统 ≈ 无梯度的 RLHF。

多 Agent 协作相关论文

CAMEL: Communicative Agents for "Mind" Exploration of Large Language Model Society
Li, G., Hammoud, H. A. A. K., Itani, H., Khizbullin, D., & Ghanem, B. (2023).
角色扮演多 Agent 协作框架。与 free-code 的关系：free-code 的 verification agent 是一种极简的双 Agent 协作 —— 主 agent（implementer）和 verifier（adversarial reviewer）形成对抗性合作。CAMEL 的角色指派（instructor + assistant）和 free-code 的 "you cannot self-assign PARTIAL, only the verifier assigns a verdict" 是同一种思路。
arXiv:2303.17760 GitHub: camel-ai/camel
主 agent + verification agent 的角色分工可以用 CAMEL 框架理解：implementer = assistant, verifier = instructor (adversarial)。
