核心理念

在 AI coding agent 时代，开发者倾向于直接让 AI "vibe code"——缺乏结构化的需求规格，导致产出质量不可控。Spec-Kit 的解法是：把 specification 做成可执行的（executable specifications），直接驱动 AI agent 生成实现。口号："Build high-quality software faster"。

五步工作流

1
specify init — 初始化 .specify/ 目录结构和 AI agent context 文件
2
/speckit.constitution — 建立项目原则（代码质量、测试标准、架构约束）
3
/speckit.specify — 撰写产品 spec（关注 what 和 why，不涉及技术栈）
4
/speckit.plan — 生成技术实现计划（指定 tech stack 和 architecture）
5
/speckit.tasks — 将计划拆解为可执行任务清单

Multi-Agent Integration（最大亮点）

通过 registry 模式支持多种 AI coding assistant，每个 agent 写入对应的 context 文件：

扩展体系

  • Extensions：如内置 git extension，specify extension add 管理
  • Presets：如 lean preset，specify preset add 管理
  • Workflows：如 speckit workflow
  • 社区目录：catalog.community.json + catalog.json
本质判断
Spec-Kit 是一个 prompt engineering 工程化框架——将 ad-hoc 的 prompt 转化为可版本化、可复用的 Markdown specification。它不做代码生成，不做模型推理，只做"需求→结构化 context"这一步。

核心理念

oh-my-openagent（npm 名 oh-my-opencode，正在更名）是 Claude Code 生态上的多模型编排层。核心论点：单一 LLM 有能力天花板，不同模型擅长不同任务——Claude Opus 强在推理，GPT-5.4 强在创意，Kimi K2.5 强在中文——应该按任务类型自动路由到最优模型。

11 个 Agent（希腊神话命名）

Agent职责特点
Sisyphus主 orchestrator按任务类别路由到其他 Agent
Hephaestus自主深度执行复杂任务的 long-running agent
Prometheus面试式规划通过提问澄清需求后再执行
Oracle代码分析只读分析，不修改代码
Librarian知识检索文档/依赖/API 查询
Explore代码探索快速浏览代码库结构
+ 5 个其他专职 agent…

关键技术创新

① Hashline Edit

每行读取时附带 content hash（LINE#ID），编辑时校验 hash，杜绝 stale-line 错误。在 Grok Code Fast 1 上将编辑成功率从 6.7% → 68.3%（10× 提升）。

② IntentGate

分析用户真实意图后再分类路由，避免字面误解。例如用户说"帮我看看这个函数"→ 路由到 Oracle（分析），而非 Hephaestus（修改）。

③ Category-based Agent Delegation

Sisyphus 按任务类别自动选择模型：

  • visual-engineering → 需要 UI 理解的模型
  • deep → 需要深度推理的模型（Claude Opus）
  • quick → 简单任务用轻量模型
  • ultrabrain → 所有强模型并行+投票

④ ultrawork 模式

一键命令，所有 agent 并行激活，形成 self-referential loop 直至任务完成。

工具箱

  • 52 个 lifecycle hooks + 26 个 tools
  • 工具包含：LSP rename/goto/references、AST-Grep 跨语言重写、Tmux 交互终端
  • 3 层 MCP：built-in（Exa 搜索/Context7 文档/Grep.app）+ Claude Code .mcp.json + Skill-embedded MCP
争议与风险
  • README 声称 Anthropic 曾因该项目"封锁了 OpenCode"——项目态度激进地反对供应商锁定
  • 许可证为自定义 SUL-1.0（非标准开源），商业使用需谨慎审查
  • 580 个 open issues，增长过快维护压力大
  • 377k LOC 的 monorepo 对个人维护者是风险

深层对比：两种哲学

Spec-Kit 的哲学：约束产生质量

问题不在 AI 能力不够，在于人类给的需求太模糊。解法：用结构化 specification 约束 AI 的输出空间。不增强 Agent 能力，而是提升输入质量。

oh-my-openagent 的哲学：组合产生突破

单个 LLM 有能力天花板，不同模型擅长不同任务。解法：多模型编排+任务路由。不改变输入，而是增强 Agent 集体能力。

趋势观察

Spec-Kit 的 constitution → specify → plan → tasks 流程本质上是 Plan-and-Solve 思想的工程化：先规划再执行。oh-my-openagent 的多 Agent 分工则是 MetaGPT / MACRec 的"角色分工"思想在 coding agent 领域的落地。

两者都指向同一个方向：AI Coding 正在从"单模型单轮"走向"多模型多步骤+结构化流程"——这正是小镇架构（memory + planning + multi-agent）在工程领域的自然演化。

实用建议

什么时候用 Spec-Kit
  • 团队项目需要结构化需求管理（不只是"让 AI 写个功能"）
  • 同时使用多个 AI coding tool（Claude Code + Copilot + Cursor），需要统一 context
  • 想让 AI 产出可审查、可版本化的代码（合规/安全场景）
什么时候用 oh-my-openagent
  • 已经在用 Claude Code，想突破单模型能力上限
  • 任务类型多样（有 UI、有后端、有文档），需要任务级模型路由
  • 愿意承受实验性项目的风险（非标准许可证、个人维护者、快速 breaking changes）
📌 总结

Spec-Kit = 人→Agent 的规格桥梁（GitHub 官方，稳定路线）
oh-my-openagent = Agent 内部的多模型编排（社区驱动，激进路线）
两者完全互补：先用 Spec-Kit 结构化需求，再让 oh-my-openagent 调度最优模型执行。
在协议栈中的位置：Spec-Kit 在 MCP/A2A 之上（需求层），oh-my-openagent 与 MCP 平行（编排层）。
