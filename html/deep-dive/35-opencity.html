一句话定位：把"小镇 25 人"扩到"城市万人"的工业级开源 stack

OpenCity 不是一篇"提出新 Agent 架构"的论文，而是一篇系统工程论文：它接受 Generative Agents (Park 2023) 已经定义的"Memory + Plan + Reflect" Agent 模型，专攻的是"如何让这个模型同时跑一万个、跨真实地理空间、还便宜到能在普通服务器上完成"这个问题。 它的两板斧——系统级 LLM 请求调度和提示级 group-and-distill 蒸馏——分别从"网络 IO 等待"和"prompt 冗余"两个维度做了大幅优化。

核心数据点（论文摘要 / 表格）

为什么工业界需要"大规模"城市 Agent 仿真

动机一：交通——单点决策不能预测涌现拥堵

城市交通的拥堵本质上是百万级出行决策的非线性叠加。传统交通仿真（SUMO、MATSim）使用规则化"出行链"模型——上班、回家、送娃，路径由 OD 矩阵 + 路径选择算法生成。这套模型在常规通勤建模有效，但无法描述"突发事件下的人群行为变化"：地铁停运时大家会改打车还是走路？大型活动后散场时人群心理如何影响疏散？ 这些场景需要 Agent 拥有语义理解 + 主观决策能力，正是 LLM Agent 擅长的，但前提是规模能撑得起一个真正的城市。

动机二：应急疏散——"如果"问题需要可重放仿真

地震、火灾、化学泄漏、极端天气——城市应急规划本质是大量"if-then"假设：如果路 A 封闭呢？如果只开放某些避难所呢？如果广播 5 分钟前发出呢？传统 ABM 给不出可信的"人会怎么反应"，而真人演练成本极高。 LLM Agent 的优势在于能基于个体画像（年龄、家庭、工作）做差异化反应——老人慢、家长会绕去接孩子、上班族倾向于先看消息再决定。但这要求万级以上 Agent 同时跑、并且能在小时级完成多次重放——这正是 OpenCity 600× 加速带来的工程红利。

动机三：城市规划——隔离指数 / 公平性这类社会指标

OpenCity 直接做了一个反事实实验：在纽约和旧金山把居民收入"打平"后，隔离指数从 0.845 降到 0.172。这种规划级政策模拟在传统手段里需要做问卷+建模数月，而 LLM Agent 仿真平台可以"按下按钮，第二天看新指数"。

"开源 + 大规模"的工业意义
城市仿真的工业用户（市政、规划院、应急局）必须能本地化部署。OpenCity 走开源 + commodity hardware 路线，是从学术 demo 跨到工业 stack 的关键决策。同时它把规模门槛推到 10K——这让"阶层固化、信息茧房、流行扩散"等只在大规模上才能观察到的社会涌现，第一次有了可重放的研究底座。 licensing 细节待实证

架构：多进程 + 异步调度 + 状态同步 + 提示蒸馏

OpenCity 的整体栈可以拆成 "输入层 → Agent 池 → LLM 调度层 → 提示优化层 → 状态环境" 五段。其中"LLM 请求调度器"和"group-and-distill 提示器"是论文真正的两个新贡献。

① 输入：城市 + 人口画像
从 OpenStreetMap 拉真实路网/POI；从 census 类数据生成 N 万 Agent 的 demographic profile（年龄、职业、收入、家庭结构）。
② Agent 池：多进程并发
Agent 内部沿用 Generative Agents 的 Memory Stream + Plan + Reflect。多个 Agent 进程/协程并发推进自己的"一天"，每步在需要决策时向 LLM 调度器投递 request。
③ LLM 请求调度器（关键）
IO 多路复用 (epoll)：把"等待 LLM 回包"的死时间用 epoll 监听一批 socket，批量处理 ready 的连接。
连接池复用：避免每次请求都建 TCP/TLS。
本地 CPU 任务卸载：解析 / 后处理交给空闲 worker，不阻塞下一个请求。
④ Group-and-Distill 提示器（关键）
聚类：基于静态属性（年龄、性别、收入等）把相似 Agent 聚成一簇。
蒸馏：抽出 cluster 共享的 prompt prefix，仅对每个 Agent 拼上其动态属性。
批量提交：以 batch 形式提交给 LLM，节省重复 prefix 的 token 解析。
⑤ 状态同步
每个 step 结束后，Agent 的位置 / 行为写回中心化"城市世界状态"，下一步 perception 重新读。这一层用共享内存或轻量 KV store 实现，减少广播开销。具体存储后端待实证
⑥ Web 控制台
论文额外提供 no-code Web 门户：选城市 → 选规模 → 跑仿真 → 看可视化。这是"工业可用"的重要一步。

调度器为什么有用：把"网络等待"变成"并发流水线"

LLM 仿真里最被忽视的瓶颈是网络 IO 等待——发出 request 后，CPU 大部分时间在 sleep 等 token 流回来。论文的关键观察：

论文核心 observation
"Sending LLM requests and receiving generated output account for only a small portion of total communication time, while the rest are wasted on waiting for LLM responses and repeatedly establishing TCP connections."

翻译：真正"在动"的时间只占一小部分，剩下都浪费在等 LLM 响应和重建 TCP 连接上。

解决方案就是把 LLM 当作"高延迟、高吞吐的远端服务"来对待，借鉴 Web 服务器（nginx、Node.js）的事件驱动 IO 模型——epoll/kqueue + 连接池——一个进程同时管理上千个 in-flight request。

蒸馏为什么有用：万人城市的 prompt 大量同质

一个城市仿真里，10000 个 Agent 的 prompt 大量重复——"你是一名 35 岁、男性、年收入 12 万的软件工程师，住在朝阳区..." 这种 prefix 对每个相似 Agent 几乎一样。如果分别发送，token 消耗是线性叠加的。

Group-and-Distill 直观表达： 原始（10K agents，每个独立 prompt）： cost ≈ 10000 × (prefix_tokens + dynamic_tokens) 聚类后（K=100 簇）： cost ≈ 100 × prefix_tokens + 10000 × dynamic_tokens → 节省 ~ (10000 - 100) × prefix_tokens ≈ 50% token 加上 in-context prototype learning： prompt 自适应总结每簇典型行为，进一步减少 LLM 的「想清楚」开销

论文报告的 ~50% token reduction + ~70% request reduction 主要来自这一步。注意："请求数减少"比"token 减少"更省钱——因为每个请求本身有 round-trip 成本和最低 billing 单位。

整体执行 pipeline

1
初始化：从城市数据生成 N 万 Agent + 静态属性聚类（K 簇）。
2
tick：Agent 并发推进，需要决策的 Agent 把 (cluster_id, dynamic_state) 投到调度器。
3
调度器：按 cluster 分组、套 distilled prefix、批量发 LLM 请求，epoll 监听响应。
4
回流 + 同步：解析 → 写入 Memory → 触发 action → 更新世界状态 → tick++。
技术哲学
OpenCity 没"创造新 Agent 智能"，而是把 Web 工程的事件驱动并发 + 数据库的批查询优化搬进 LLM Agent 仿真——证明 LLM Agent 已经开始有真正的工程瓶颈和工程解，非常适合 ACL Industry Track。

实验 2 · Scaling 曲线：1 → 10K 的"摊薄效应"

Per-agent time 随规模变化（论文报告）： N=1: 36.25 s/agent/step → N=10K: ~0.06 s/agent/step → 600× speedup

这条曲线说明 OpenCity 的设计规模越大越省——批处理 + 聚类需要"足够多 Agent"才能摊薄 fixed cost，这与传统 ABM"规模越大越慢"直觉相反。 工程意义：10K Agent 一天日常活动 ≈1 小时（commodity hardware），百万级 Agent 按趋势线外推也在十几小时可行域。百万级外推未在原文实测

Case Study：纽约 / 旧金山的"收入隔离反事实实验"

论文最有意思的是这个反事实实验——既能 demo 平台能力，也能输出可解释的政策洞察：

场景：模拟纽约和旧金山 10K Agent 的日常活动，测量"收入隔离指数"（Income Segregation Index，衡量不同收入群体在空间上接触的概率有多低）。

实验组对比：

  • Baseline：使用真实 census 收入分布。
    → 纽约隔离指数 = 0.845
  • 反事实：将所有 Agent 的收入改为均匀分布（即"如果每个人都收入相同"）。
    → 纽约隔离指数降到 0.172

解读：隔离的~80% 来自"哪种人住在哪"，只有少部分来自"日常活动选择"。这意味着，纯靠"鼓励大家去不同地方消费"的政策很难显著降低空间隔离——必须改变住房分布本身。

这个 case study 之所以值得放进 deep-dive，是因为它示范了"万级 Agent + 可重放 + 可调参数"组合带来的全新能力——以前只能做问卷 / 历史回归的政策实验，现在可以变成"按下按钮跑一天"的可重复仿真。

真实数据对照（验证仿真的可信度）

  • 个体级：回转半径 (radius of gyration) 与真实手机轨迹分布对照。
  • 群体级：起讫点 (OD) 流量矩阵与真实出行调查对照。
  • 社会域：收入隔离指数与 American Community Survey 等官方数据对照。

OpenCity 的 LLM Agent 在三个维度都与传统 EPR (Explore and Preferential-Return) 规则模型持平或更接近真值，证明 LLM 真能补上规则模型缺乏的"语义/动机"层。

FAQ：两个最常被问到的问题

Q1. OpenCity 跟 AgentSociety 都是清华 FIB Lab 的，到底有什么区别？要选哪一个？
  • AgentSociety（见 deep-dive 17）：上层研究框架，Agent / 社会 / 城市 / 应用四层抽象，重点是"怎么搭一个城市仿真实验"。
  • OpenCity：下层系统加速 + 开源 stack，重点是"让仿真跑得快、便宜、多"。
实践建议：研究者做舆论 / 经济 / 政策实验，优先 AgentSociety；工程师要把 LLM Agent 上量产，优先借走 OpenCity 的调度器和 group-and-distill 设计。
Q2. Group-and-Distill 把"相似 Agent"聚类共享 prefix，会不会让 Agent 失去"个体差异"？
合理担忧。论文的设计回应：
  • 共享的只是 prefix：每个 Agent 的动态属性（当前位置、心情、最近 Memory）仍然 per-agent 拼接，最终 prompt 仍然个性化。
  • 聚类基于"语义相似的静态属性"：年龄、收入、职业对"是否吃午饭"这类行为的影响本就同质，共享 prefix 不会显著伤害决策多样性。
  • 反事实实验是验证：纽约隔离指数 case 表明，聚类后仍能正确反映"收入分布 → 空间隔离"——细粒度社会信号被保住。
  • 指标对照：回转半径、OD 矩阵都与真实数据对齐，间接证明聚类+蒸馏没牺牲行为真实度。
核心思想是"对同质特征共享，对异质特征独立"——类似 vLLM 里 KV-cache prefix sharing 的角色，既省 token 又不糊掉个体。
