QueryEngine 核心行数

Claude Code的源码采用严格的五层架构。每一层只依赖其下一层，入口层的多态性保证了所有客户端共享同一个Engine层——Agent的核心逻辑只写一次。

Layer 1
Entrypoints
main.tsx（CLI入口）、bridgeMain.ts（IDE / Web / SDK统一接口）。所有客户端在此层汇聚，向下调用同一个Runtime。
Layer 2
Runtime
sessionRunner.ts（会话生命周期管理）、bridgeMessaging.ts（跨进程通信协议）。负责会话创建、恢复、持久化。
Layer 3
Engine
QueryEngine.ts（约46,000行，核心引擎）、query.ts（Agent循环）。这是整个系统的心脏——所有Agent行为的决策和执行都在此层。
Layer 4
Tools
src/tools/ 目录下每个工具是独立模块，含权限检查（checkPermissions）、Schema定义（Zod）、隔离执行逻辑。工具是Agent的"手脚"。
Layer 5
Infrastructure
权限系统、MCP（Model Context Protocol）、Hooks、配置管理、Telemetry、Feature Gates。提供横切关注点。
关键设计原则
所有入口（CLI、桌面端、Web、SDK）共享同一个Engine层。这意味着Agent的核心逻辑只写一次。这是"平台化"的基础——新增一个前端（如移动端）只需实现Layer 1的适配器，Layer 3-5完全复用。

可借鉴原理一：Agent Loop的状态机设计

源码位置：src/query/query.ts, queryLoop() 函数

Agent循环的核心是一个 while(true) 循环，携带显式State对象。不是通过全局变量或闭包隐式传递状态，而是每次迭代都从一个结构化的State对象中解构所需信息。

query.ts - State 对象结构 State = { messages: Message[] toolUseContext: ToolUseContext autoCompactTracking: {/* 压缩追踪 */} maxOutputTokensRecoveryCount: number hasAttemptedReactiveCompact: boolean turnCount: number transition: Continue | undefined // 为什么上一次迭代继续了 }

每次迭代的4个阶段

1. Context Compression
压缩决策
→
2. API Streaming
调用LLM + 流式接收
→
3. Tool Execution
执行工具，收集结果
→
4. Attachments
注入记忆、技能、通知
可借鉴的原理
  • 显式的State对象而非隐式全局状态 —— 每次迭代都从State解构，状态转换清晰可追溯
  • transition字段记录"为什么继续"（next_turn / reactive_compact_retry / max_output_tokens_retry等）—— 这是调试和理解Agent行为的关键
  • 不可变参数+可变状态分离 —— parameters在 query() 入口冻结，loop内只改State

与Smallville对比

Smallville
  • Agent循环是隐式的（每个tick执行一次感知→检索→反思→规划→行动）
  • 没有显式State对象
  • 调试"Agent为什么做了这个决定"需要逆向推断
VS
Claude Code
  • 显式 while(true) 循环 + 结构化State
  • transition字段精确记录每次继续的原因
  • 每个决定都可追溯和序列化
设计启示
任何Agent系统都应该有一个显式的、可序列化的State对象。这不仅方便调试，还能实现会话恢复——Claude Code在API调用前就把transcript写到磁盘，进程被杀也能恢复。

循环终止条件（Terminal Reasons）

Terminal Reasons 枚举 completed | prompt_too_long | model_error | max_output_tokens | blocking_limit | aborted_streaming | aborted_tools | max_turns | hook_stopped | stop_hook_prevented

每种终止都有明确的语义——不是简单的"成功/失败"，而是精确的原因分类。可用于重试决策（max_output_tokens 可重试，prompt_too_long 需压缩）和错误报告（用户看到的错误信息根据reason定制）。

可借鉴原理二：五级上下文压缩瀑布

源码位置：query.ts L379-L543, services/compact/

这是整个代码库最精妙的工程设计之一。当上下文接近LLM的窗口上限时，系统不是"一刀切"地压缩，而是按成本从低到高依次尝试5级压缩策略——渐进式降级。

Level 1 - Snip Compact（最廉价）
删除中间消息，保留首尾。纯本地操作，0 API成本。Feature-gated: HISTORY_SNIP。
成本：0 | 压缩率：低 | 信息损失：最小
Level 2 - MicroCompact（低成本）
缓存 tool_use 的输入，利用prompt caching机制。几乎0 API成本，对用户完全无感。
成本：极低 | 压缩率：低-中 | 信息损失：无
Level 3 - Context Collapse（中等成本）
对历史做折叠投影——模型看到折叠视图，UI保留完整历史。如果压到阈值以下，跳过后续步骤。Feature-gated: CONTEXT_COLLAPSE。
成本：中 | 压缩率：中-高 | 关键：读时投影（read-time projection），不修改底层数据
Level 4 - AutoCompact（高成本）
Fork一个子Agent专门做摘要。触发条件：tokenCount >= (contextWindow - 13,000 buffer)。有断路器：连续3次失败后停止重试。生成结构化摘要替代原始对话。
成本：高（额外API调用）| 压缩率：高 | 断路器：3次失败上限
Level 5 - Full Compact（最高成本）
完整对话压缩 + 选择性文件重新注入。只在极端情况触发，是最后的手段。
成本：最高 | 压缩率：最高 | 触发频率：极低

消息存储设计

  • Append-only JSONL —— 旧消息不删除，只追加
  • 可见性标志：isCompactSummary、isVisibleInTranscriptOnly、isMeta
  • getMessagesAfterCompactBoundary() 只返回压缩边界之后的消息给API
  • UI可回滚看完整历史 —— 压缩对API透明，对用户不透明
可借鉴的原理
  • 渐进式降级而非一刀切 —— 先试便宜的，不行再试贵的
  • 读写分离 —— 底层保留完整数据，对API做投影（Context Collapse的精髓）
  • 断路器模式 —— 防止压缩失败导致无限重试
Smallville
  • 完全没有上下文管理
  • 记忆只增不减
  • 学术原型最大的工程盲区
VS
Claude Code
  • 5级压缩瀑布
  • 成本感知的渐进降级
  • "有限上下文窗口"硬约束的最完整工程解法
设计启示
任何长对话Agent都需要压缩策略。关键不是"用什么算法压缩"，而是"什么时候压缩、压缩多少、失败了怎么办"——这是一个决策瀑布问题。

可借鉴原理三：四类记忆的分类学

源码位置：src/memdir/memoryTypes.ts

Claude Code不是"记住一切"，而是将记忆严格分为4类。每类有不同的触发条件、结构要求和衰减速度。

user 关于用户的角色、目标、知识、偏好
  • 触发：了解到用户的任何个人信息
  • 用途：根据用户画像调整协作方式
  • 举例："用户是数据科学家，当前关注可观测性/日志"
feedback 用户对工作方式的反馈（纠正+确认）
  • 触发：用户纠正你（"不要那样做"）或确认非显然做法（"对，就是这样"）
  • 结构：规则 + Why:（原因）+ How to apply:（应用场景）
  • 关键：不仅记录纠正，也记录确认——否则会过度谨慎
project 不可从代码/git推导的项目信息
  • 触发：了解到谁在做什么、为什么、截止日期
  • 关键：将相对日期转为绝对日期（"周四" → "2026-03-05"）
  • 特性：衰减最快，需要why来判断是否仍然有效
reference 外部系统的指针
  • 触发：了解到外部系统的位置和用途
  • 举例："pipeline bugs追踪在Linear项目INGEST中"

明确不记录的内容（负列表）

NOT-MEMORIZE 负列表
  • 代码模式、架构、文件路径 —— 可从代码推导
  • Git历史 —— git log / blame 更权威
  • 调试方案 —— 修复在代码中，上下文在commit message中
  • CLAUDE.md已有的内容 —— 避免重复
  • 临时任务状态 —— 会话级信息不需持久化
可借鉴的原理
  • 记忆不是日志，而是分类知识库 —— 每类有不同的触发条件、结构要求和衰减速度
  • "负列表"同样重要 —— 明确什么不该记是防止记忆膨胀的关键
  • feedback类记忆的"同时记录纠正和确认" —— 这是对Reflexion（只记录失败）的直接改进，对应Sweet&Sour论文的思想
Smallville
  • Memory Stream是无类型的
  • 观察、对话、反思洞见全混在一起
  • 无衰减管理策略
VS
Claude Code
  • 4类严格分类
  • 每种记忆有不同的生命周期管理策略
  • 负列表防止膨胀

可借鉴原理四：autoDream四阶段记忆整合

源码位置：src/services/autoDream/

触发条件（4个门控，cheapest first）

  1. 时间门控：距上次整合 ≥ 24小时
  2. 会话门控：此后有 ≥ 5个新会话
  3. 锁门控：无其他进程在整合
  4. 扫描节流：10分钟内不重复扫描

配置来自GrowthBook feature flag tengu_onyx_plover。

四阶段整合流程（consolidationPrompt.ts）

PHASE 1
Orient（定向）
列出记忆目录，读MEMORY.md，浏览已有文件，检查logs/。
"我现在的知识图谱长什么样？"
PHASE 2
Gather（收集）
先看日志（最新信号），再找被矛盾的事实，再搜索transcript。
"自上次整合以来有什么新信号？"
PHASE 3
Consolidate（整合）
写入/更新记忆文件，聚焦合并而非创建重复。
"新信号如何与已知知识融合？"
PHASE 4
Prune & Index（修剪与索引）
保持MEMORY.md在200行/25KB以内。删除过时指针，解决矛盾。
"什么已经过时了？"

锁机制（consolidationLock.ts）

锁机制设计 // 锁文件：.consolidate-lock // 内容：持有者PID // mtime：上次整合时间戳 // 失败回滚：恢复mtime以允许重试 interface ConsolidationLock { lockFile: ".consolidate-lock" content: PID // 持有者进程ID mtime: Timestamp // 上次整合时间 onFailure: "restore mtime" // 允许重试 }

与主Agent的互斥

互斥设计
如果主Agent在对话中已经写了记忆文件 → extractMemories 检测到 → 跳过本轮提取 → 游标前进。防止双重提取——"做事"和"反思"不同时进行。
可借鉴的原理
  • 四阶段映射认知科学的反思过程：定向 → 收集 → 整合 → 修剪
  • "后台空闲时运行" —— 人类的记忆整合也发生在睡眠中
  • 锁机制确保单写者 —— 多Agent共享记忆时的并发控制
  • 互斥设计 —— "做事"和"反思"不同时进行
Smallville
  • 反思只有Phase 3（归纳洞见）
  • 完全缺少Phase 1（定向）
  • 缺少Phase 2（收集新信号）
  • 缺少Phase 4（修剪过时信息）
VS
Claude Code
  • 完整的四阶段整合流程
  • 带锁的并发安全设计
  • Smallville反思机制的完整工程化版本

可借鉴原理五：记忆的"信任但验证"原则

源码位置：src/memdir/memoryTypes.ts L201-256, memoryAge.ts

系统提示中的关键指令：

memoryTypes.ts - 验证规则 "A memory that names a specific function, file, or flag is a claim that it existed when the memory was written. It may have been renamed, removed, or never merged. Before recommending it — verify first." // 具体规则： // - 如果记忆提到文件路径：检查文件是否存在 // - 如果记忆提到函数或flag：grep搜索 // - "'记忆说X存在' 不等于 'X现在存在'"

记忆年龄标记（memoryAge.ts）

天数 标记 附加行为
0天 "today" 无额外警告
1天 "yesterday" 无额外警告
2+天 "N days ago" 附带过时警告
>1天记忆的过时警告
"这是N天前的观察，不是实时状态。声称的代码行为或文件引用可能已过时。在作为事实断言前请验证。"
可借鉴的原理
  • 记忆是"提示"而非"事实" —— 这是对Smallville最深层的修正
  • 年龄标记让LLM自己判断可信度 —— 不需要硬编码的遗忘曲线
  • 验证-before-推荐 —— 防止基于过时记忆的错误建议
设计启示
任何Agent的记忆系统都应该区分"我记得X"和"X现在是这样"。记忆不是oracle，是需要验证的线索。

可借鉴原理六：多Agent的Mailbox通信模式

源码位置：src/tools/AgentTool/, src/tools/SendMessageTool/, src/utils/swarm/

三种执行模式

1. 同步子Agent
父Agent调用Agent工具，阻塞直到完成。子Agent有独立上下文窗口，只返回结果摘要。
  • 入口：AgentTool.tsx
  • 适用：需要结果才能继续的场景
2. 异步后台Agent
Fire-and-forget，通过 LocalAgentTask 追踪。
  • 入口：tasks/LocalAgentTask/
  • 适用：独立的研究/验证任务
3. 进程内Teammate
通过 AsyncLocalStorage 实现同进程内的并发Agent。
  • 入口：utils/swarm/inProcessRunner.ts
  • 适用：Agent Teams（1个lead + 2-16个worker）

Mailbox通信

Mailbox 设计 // 路径 ~/.claude/teams/{teamName}/{agentName}/inbox.jsonl // 消息格式 { from: string, text: string, summary: string, timestamp: number, color: string } // 轮询间隔：500ms // 跨进程/跨AsyncLocalStorage均可用

生成子Agent的决策树（AgentTool.tsx:269-290）

子Agent生成决策树 有 team_name+name → InProcess 或 Tmux后端（teammate） isolation: 'remote' → RemoteAgentTask isolation: 'worktree' → Git worktree隔离 run_in_background: true → LocalAgentTask（异步） 其他 → 同步 runAgent

Coordinator模式（coordinator/coordinatorMode.ts）

  • Lead只做编排，不做实现
  • Worker通过Agent工具生成
  • Lead收到结构化的 <task-notification> XML
  • Worker工具受限：只有 Bash / Read / Edit / MCP，没有编排工具

Fork Subagent（AgentTool/forkSubagent.ts）

  • 子Agent继承父Agent的对话、系统提示、工具池（字节精确）
  • 防递归：检测 <fork-boilerplate> 标签
  • 输出结构化：Scope → Result → Key files → Files changed → Issues

Team Memory同步（services/teamMemorySync/）

  • 基于 sha256哈希 的增量同步
  • Push：比对本地hash vs 服务器checksums，只上传差异
  • Pull：带ETag的条件GET
  • 冲突策略：Pull时 服务器wins
可借鉴的原理
  • Agent不能直接读对方记忆 —— 只能通过消息交换信息（和Smallville相同！）
  • Mailbox模式（异步、文件持久化、轮询）vs 直接调用 —— 解耦发送者和接收者的速度
  • Coordinator/Worker分离 —— Lead只分配不执行，防止"什么都自己做"
  • Fork继承 —— 子Agent继承父Agent的完整上下文，零成本克隆
Smallville
  • 用物理空间做隐式协调
  • 你只能和看到的人说话
  • 空间即通信拓扑
VS
Claude Code
  • 显式Mailbox通信
  • 三种执行模式灵活选择
  • Coordinator/Worker编排
共同原则
两者的共同原则：Agent不能直接读对方的"脑子"，只能通过"对话"交换信息。这个约束不是技术限制，而是设计选择——它防止了全局共享状态的混乱。

可借鉴原理七：工具系统的权限与隔离

源码位置：src/Tool.ts, src/tools/

工具基类设计

每个工具是一个独立模块，必须实现以下接口：

Tool.ts - 工具基类接口 interface Tool { inputSchema: ZodSchema // Zod验证 checkPermissions(): PermResult // 执行前权限检查 call(): ToolResult // 实际执行 isConcurrencySafe: boolean // 并发安全标记 isReadOnly: boolean // 只读标记 }

并发执行策略（toolOrchestration.ts）

读操作
Glob, Grep, Read —— 并行执行
  • 并发池上限：10
  • 连续的只读工具合为一个并发批次
写操作
Edit, Write, Bash（有副作用） —— 串行执行
  • 单个写工具构成一个串行批次
  • contextModifiers在批次完成后顺序应用

权限三级决策

allow
直接执行
→
deny
拒绝并记录
→
ask
弹出确认对话框
可借鉴的原理
  • 工具是Agent的"手脚"，每只手都需要独立的权限检查
  • 读写分离的并发策略 —— 简单但有效
  • Schema验证在边界执行 —— 防止跨工具状态泄漏

可借鉴原理八：流式执行与延迟优化

源码位置：query.ts 中的 streaming tool execution

传统模式

LLM生成完所有工具调用 → 批量执行

→
流式模式

Feature gate: tengu_streaming_tool_execution2

流式工具执行伪码 while(LLM还在生成): if(收到一个tool_use block): // 立即开始执行（如果并发安全） startExecution(tool_use) for(已完成的结果): yield 结果 // 不等其他工具完成

流式模式的优势

  • LLM生成和工具执行并行 —— 显著降低端到端延迟
  • 结果在API响应完成前就可用 —— 用户更早看到进度
  • 并发限制防止资源耗尽 —— 不会无限制地并行
  • 安全回退：streaming失败时丢弃部分结果，不影响正确性
可借鉴的原理
  • 不要等所有信息就绪才行动 —— 能并行就并行
  • 安全回退比完美并行更重要 —— 部分失败不应导致全部失败

# 可借鉴原理 源码位置 Smallville对比 设计启示
1 显式State状态机 query.ts queryLoop() Smallville无显式State 任何Agent都需要可序列化的State对象
2 五级压缩瀑布 query.ts L379-543 Smallville无上下文管理 渐进式降级，便宜的先试
3 四类记忆分类学 memdir/memoryTypes.ts Smallville无类型记忆流 不同类型记忆有不同生命周期
4 四阶段记忆整合 services/autoDream/ Smallville只有归纳（Phase 3） 完整的定向→收集→整合→修剪
5 信任但验证 memoryTypes.ts L201+ Smallville信任自己的记忆 记忆是线索不是事实
6 Mailbox通信 tools/SendMessageTool Smallville物理空间触发 Agent不能读对方脑子，只能对话
7 工具权限与隔离 Tool.ts, tools/ Smallville无权限概念 读写分离 + Schema验证 + 权限门控
8 流式并行执行 query.ts streaming Smallville同步执行 能并行就并行，安全回退更重要

结论：从学术原型到生产系统的8个跃迁

Smallville是"概念验证"——证明了记忆+反思+规划的Agent架构可以产生涌现行为。
Claude Code是"工程实现"——证明了同一架构在生产环境中如何处理上下文有限、记忆衰减、多Agent协调、错误恢复、延迟优化等现实约束。
