愿景：从"平台各自为政"到"Agent协作网络"

目前的状态：部门内多个平台各有独立的自动化逻辑、独立的数据存储、独立的触发机制。平台之间靠API硬编码调用，缺乏语义理解和自适应能力。

目标状态：每个平台成为一个Agent（或Agent集群），拥有独立的记忆、推理和行动能力，通过统一协议互相感知、协商和协作。一个新需求不再需要逐个平台改代码——只需告诉"编排Agent"目标，它会自动分解任务、调度各平台Agent执行。

核心类比：Smallville是25个Agent在一个小镇里自发协作。我们要做的是——让部门的N个平台成为N个Agent，在一个"数字小镇"里自发协作。每个平台Agent有自己的"性格"（能力边界）、"记忆"（历史数据和经验）、"社交"（与其他平台的通信），以及"反思"（从执行结果中学习改进）。

设计原则：从研究中提炼的7条铁律

这7条原则从我们研究的90+篇论文和Claude Code源码中提炼，是整个改造的架构指南针。

1. 先单Agent跑通，再搞多Agent
企业落地第一大坑是"平台先行"——先搭框架再找场景。正确做法：先在1个平台上做出1个高质量Agent，验证价值后再扩展。
来源：企业落地实践 — "premature abstraction"是头号失败模式
2. 窄能力专家 > 宽能力通才
每个平台Agent应该是深而窄的专家（"发票处理Agent"），而不是浅而宽的通才（"做一切Agent"）。窄Agent可测试、可评估、可信赖。
来源：Drop the Hierarchy — 8个Agent自发分化5,006个角色，自然走向专业化
3. 结构化消息 > 自由对话
Agent之间用结构化Schema通信，不是自由文本聊天。每一跳都会损失信息，结构化消息减少累积误差。
来源：Claude Code Mailbox — JSONL格式{from, text, summary, timestamp}
4. 记忆分类存储，不是记住一切
分4类：用户画像/反馈/项目状态/外部引用。每类有不同的生命周期。明确定义负列表（不记什么）比定义正列表更重要。
来源：Claude Code memoryTypes.ts — 四类记忆 + 负列表
5. 做事和反思永远分离
Agent执行任务时不做元认知反思。反思在后台空闲时运行（autoDream模式）。两者互斥——做事的人和复盘的人不能是同一时刻的同一个人。
来源：Claude Code extractMemories互斥机制 + 认知科学睡眠记忆整合理论
6. 信任但验证（Trust but Verify）
Agent的记忆是"提示"而非"事实"。推荐任何东西之前先验证当前状态。记忆超过1天就标注年龄警告。
来源：Claude Code "memory as hint, not truth"
7. 最小结构 + 完全角色自治
不要过度预设Agent的角色。给最小的结构约束（执行顺序、通信协议），让Agent自己决定"我在这个任务中应该扮演什么角色"。
来源：Drop the Hierarchy — 内生性悖论，预设角色是反模式

Phase 1：基座建设（月1-2）

目标：在1个试点平台上跑通单Agent全流程，证明价值。不搞框架，不搞平台，先出业务成果。

1.1 选择试点平台

选择标准（满足越多越好）：

  • 有明确的、重复性的人工操作（Agent替代价值高）
  • 有结构化的API/工具可调用（Agent行动层容易实现）
  • 有历史数据可做记忆（Agent能从经验中学习）
  • 团队对AI接受度高（减少推行阻力）
  • 出错可容忍或可回滚（降低风险）

1.2 构建Agent Runtime

核心是一个Agent循环（Agent Loop）——对应Smallville的感知-推理-行动循环，Claude Code的queryLoop()。

// Agent循环的伪代码（对应Claude Code query.ts的queryLoop） while (true) { // 1. 感知：收集当前上下文 const context = await gatherContext(state, memory, tools) // 2. 压缩：如果上下文过长，按级别压缩（对应5级瀑布） const compressed = await compressIfNeeded(context, state.compressionLevel) // 3. 推理：调用LLM决策 const decision = await callLLM(compressed, systemPrompt) // 4. 行动：执行工具调用（对应Claude Code Tool System） if (decision.toolCalls) { const results = await executeTools(decision.toolCalls, permissions) state.messages.push(...results) } // 5. 记忆：提取值得记住的信息（对应extractMemories） await maybeExtractMemories(state, decision, results) // 6. 状态转移：决定继续还是结束（对应transition字段） state = updateState(state, decision, results) if (isTerminal(state)) break }
借鉴Claude Code的关键设计：State对象必须是显式的、可序列化的。每次迭代从State解构，transition字段记录"为什么继续"。这让Agent的每个决定都可追溯、可恢复。

1.3 构建记忆系统（v1）

层级内容存储生命周期对应
工作记忆当前会话/任务的上下文Redis / 内存会话级Smallville当前tick的感知
短期记忆最近N次任务的摘要PostgreSQL天级，可压缩Memory Stream近期部分
长期记忆4类分类记忆（用户/反馈/项目/引用）PostgreSQL + pgvector持久，有遗忘机制Claude Code MEMORY.md + Topic Files

第一版不需要做autoDream——先做写入和检索。记忆整合在Phase 3加入。

1.4 构建工具层（MCP）

将试点平台的核心操作封装为MCP Server。每个工具需要：

  • 输入Schema（Zod/JSON Schema验证）——防止LLM传垃圾参数
  • 权限标记（只读/写入/危险）——对应Claude Code的allow/deny/ask三级
  • 并发安全标记——只读工具可并行，写工具串行
  • 幂等设计——Agent可能重试，工具必须能安全重复调用
经验教训：工具集成是60-70%的工作量。不要低估。MCP帮你标准化接口，但不帮你处理认证、限流、错误恢复。预留充足时间。

1.5 构建可观测性（Day 1必须有）

不带可观测性上线Agent等于盲飞。最小可观测性栈：

Trace（追踪）
每次Agent循环的完整执行路径：LLM输入/输出、工具调用、记忆检索。用LangFuse（可自托管）或LangSmith。
Metrics（指标）
延迟（P50/P95/P99）、Token消耗/成本、工具调用成功率、任务完成率。接入现有APM（Datadog/Prometheus）。

1.6 Phase 1里程碑

M1.1 — 第2周：Agent能完成试点平台上1个端到端任务
从输入→推理→调用工具→返回结果，全链路跑通。不要求完美，要求完整。
M1.2 — 第4周：记忆系统v1上线
Agent能记住上次任务的结果，下次被问到时能检索并引用。覆盖4类记忆的写入和检索。
M1.3 — 第6周：可观测性+评测基线
全量Trace上线。建立评测数据集（50+测试用例），跑出基线准确率/完成率。后续每次改动都对比基线。
M1.4 — 第8周：试点平台Agent灰度上线
10-20%流量灰度，人工审核Agent输出。收集真实场景的失败案例，建立"困难用例"库。

Phase 2：多Agent协同（月3-4）

目标：将3-5个平台改造为Agent，建立Agent间的通信和协调机制。从"每个平台独立自动化"变为"平台之间能感知、协商、协作"。

2.1 Agent注册与发现

每个平台Agent发布一份Agent Card（借鉴A2A协议的概念）：

{ "name": "invoice-agent", "description": "处理发票识别、校验和入账", "capabilities": ["invoice_ocr", "invoice_validate", "ledger_entry"], "tools": ["read_invoice", "validate_amount", "create_entry"], "input_schema": { ... }, "output_schema": { ... }, "sla": { "p95_latency_ms": 5000, "availability": 0.999 }, "owner": "finance-team" }

所有Agent Card注册到Agent Registry（可以是一个简单的配置中心或数据库）。编排Agent通过Registry发现可用Agent。

2.2 消息总线（Mailbox模式）

借鉴Claude Code的Mailbox架构，而非传统的REST调用：

模式适用场景实现
同步请求需要立即结果（<5s）直接gRPC/HTTP调用
异步任务长时间任务（分钟级）消息队列（Kafka/RabbitMQ）+ 状态轮询
Mailbox消息Agent间协商/通知Redis Stream或专用JSONL Mailbox
为什么用Mailbox而不是直接调用？
1. 速度解耦——快的Agent不等慢的，失败的不拖活着的
2. 可追溯——所有消息持久化，可回溯完整协作过程
3. 容错——Agent重启后从Mailbox恢复未处理消息
来源：Claude Code Mailbox + Smallville的"物理空间隔离"原理——Agent不能直接读对方脑子

2.3 编排Agent（Coordinator）

一个专门的编排Agent负责将复杂需求分解为子任务，分派给各平台Agent。

设计要点（借鉴Claude Code Coordinator模式 + Drop the Hierarchy的内生性悖论）：

  • 编排Agent只分解和分派，不自己执行——防止"什么都自己做"
  • 给最小的结构约束（任务分解+执行顺序），让平台Agent自己决定执行细节
  • 支持动态重规划——某个Agent失败时，编排Agent重新分解剩余任务
  • 所有分派决策可追溯——记录"为什么选了这个Agent"
// 编排Agent的决策流程 async function orchestrate(userRequest) { // 1. 理解需求 const intent = await parseIntent(userRequest) // 2. 查询Registry，发现可用Agent const agents = await registry.findCapable(intent.requiredCapabilities) // 3. 分解任务（LLM推理） const plan = await planTasks(intent, agents) // 4. 按依赖关系分派（可并行的并行，有依赖的串行） const results = await executePlan(plan, agents, { maxRetries: 2, timeoutMs: 30000, onFailure: 'replan' // 失败时重新规划 }) // 5. 汇总结果 return synthesize(results) }

2.4 跨平台工具层（MCP统一）

每个平台Agent的工具都封装为MCP Server。编排Agent通过MCP协议调用各平台能力。

MCP的价值在这里：新增一个平台时，只需要写一个新的MCP Server，编排Agent自动发现新能力。不需要改编排逻辑——这是"USB式"的即插即用。

2.5 Phase 2里程碑

M2.1 — 第10周：3个平台Agent上线，Agent Card注册完成
每个Agent独立工作正常，发布到Registry。
M2.2 — 第12周：编排Agent跑通第1个跨平台工作流
一个需要2+个平台Agent协作的真实业务场景端到端跑通。
M2.3 — 第14周：Mailbox通信 + 异步任务上线
Agent间通过Mailbox协商，长任务异步执行，状态可追踪。

覆盖3-5个跨平台工作流，灰度运行，收集失败案例。

Phase 3：智能进化（月5-6）

目标：让系统越用越聪明。加入后台反思、跨Agent知识共享、自动评测和优化。这是从"能用"到"好用"的跃迁。

3.1 后台反思系统（autoDream）

借鉴Claude Code autoDream的四阶段设计，构建后台记忆整合机制：

Phase A — Orient（定向）
审视当前记忆库状态：有多少记忆、各类分布如何、最近新增了什么。"我现在的知识图谱长什么样？"
Phase B — Gather（收集）
从最近的执行日志中收集新信号：哪些任务失败了？用户反馈了什么？哪些知识过时了？
Phase C — Consolidate（整合）
将新信号融入已有记忆：合并重复、更新事实、建立关联。重点是合并而非创建。
Phase D — Prune（修剪）
删除过时记忆、解决矛盾、控制记忆总量。对应Claude Code的200行约束。
触发条件（借鉴Claude Code的4门控）：
1. 距上次整合 ≥ 24小时
2. 新任务执行 ≥ N次
3. 无其他整合进程在运行（锁机制）
4. 系统负载低于阈值（空闲时运行）
关键：整合与执行互斥——正在处理业务时不做反思，防止干扰。

3.2 跨Agent知识共享

借鉴Claude Code的Team Memory Sync：

  • 共享记忆层：所有Agent都能读取的公共知识库（项目状态、架构决策、团队反馈）
  • 私有记忆层：各Agent独有的领域知识（不污染其他Agent）
  • 增量同步：基于哈希的delta sync，只传差异
  • 冲突策略：读时验证，写时合并，矛盾时标记由人工裁决

3.3 评测基准（Evaluation Framework）

借鉴MultiAgentBench(MARBLE)的里程碑式KPI设计：

维度指标基线来源目标
任务完成率端到端成功率Phase 1评测集≥ 85%
协作效率跨Agent任务的额外延迟单Agent基线≤ 2x 单Agent延迟
记忆准确率记忆检索的相关性评分人工标注≥ 0.8
反思有效性autoDream后下周任务成功率变化整合前基线正向提升

3.4 自优化循环

将评测结果反馈回系统：

// 自优化循环（对应Multi-Agent Evolve的Self-Play思想） 失败案例收集 → 分类（模型错误/工具错误/编排错误/记忆错误） → 模型错误 → 优化Prompt或切换模型 → 工具错误 → 改进MCP Server实现 → 编排错误 → 调整任务分解策略 → 记忆错误 → 改进记忆检索/整合逻辑

5条前沿赛道：必须跟紧的动态

这些方向在6个月内可能产生重大突破，直接影响我们的技术选型和架构演进。

最高优先 赛道1：Agent通信协议标准化（MCP + A2A）

为什么重要：MCP已成为工具集成事实标准，A2A正在成为Agent间通信标准。如果标准定型而我们的架构不兼容，未来的迁移成本巨大。

跟踪目标：MCP规范演进（特别是认证/授权）、A2A正式版发布、主要云厂商的支持情况。

影响我们的决策：Phase 2的通信层设计必须预留MCP/A2A兼容性。

关键信源：modelcontextprotocol.io、google.github.io/A2A、Anthropic/Google工程博客

高优先 赛道2：Agent记忆与反思的工程化

为什么重要：ICLR 2026有专门的MemAgents Workshop。Mem0、Zep等专用记忆层在快速迭代。Claude Code的autoDream暗示记忆整合将成为Agent标配。

跟踪目标：Mem0/Zep的企业版功能、MemAgents Workshop论文、autoDream式后台整合在开源框架中的实现。

影响我们的决策：Phase 3的autoDream设计可能被开源方案替代，不需要从零自建。

关键信源：Mem0 GitHub、ICLR 2026 MemAgents、LangChain/LangGraph更新日志

高优先 赛道3：自组织与涌现——从预设到自发

为什么重要：Drop the Hierarchy证明预设角色是反模式。如果这个发现被工程化，Agent系统将不再需要人工设计协作流程。

跟踪目标：Drop the Hierarchy的后续工作（bio-inspired protocols）、OrgAgent等自组织框架的开源实现、Agent自发分工的可复现实验。

影响我们的决策：Phase 2的编排Agent设计是否需要给Agent更多自主权——目前保守设计（Coordinator模式），但准备在Phase 3实验Sequential模式。

关键信源：Victoria Dochkina后续论文、MultiAgentBench更新、Agent自组织相关arXiv

中优先 赛道4：Agent评测基准成熟化

为什么重要：目前没有公认的多Agent协作评测标准。MARBLE(ACL 2025)是最接近的，但还在演进。标准化评测让我们能客观对比不同架构。

跟踪目标：MARBLE 2.0、新的多Agent基准、企业级Agent评测框架（LangSmith/Braintrust的新功能）。

影响我们的决策：Phase 3的评测框架设计参考MARBLE的里程碑式KPI，但需要适配到我们的业务场景。

中优先 赛道5：KAIROS式主动Agent

为什么重要：Claude Code泄漏了KAIROS（后台守护进程，主动寻找行动机会）。如果这个模式被验证，Agent将从"被动响应"变为"主动服务"——从"你问我答"到"我主动发现问题并修复"。

跟踪目标：KAIROS是否正式发布、开源社区的KAIROS复现（已有dev.to文章）、主动Agent在企业中的安全模型。

影响我们的决策：Phase 3后期可以试验：让Agent在空闲时主动巡检系统状态，发现异常时Mailbox通知编排Agent。但安全模型必须先设计好。
