Google A2A — Agent 互操作协议 后加

深度解读：A2A (Agent-to-Agent Protocol) 是 Google 于 2025 年开源、2026 年捐给 Linux Foundation 治理的 Agent 互操作开放协议，目的是让由不同厂商、不同框架构建的 Agent 能够互相发现、协商模态、协作完成长期任务——在不暴露内部状态、记忆或工具的前提下。与 Anthropic 的 MCP（Agent↔Tool）形成上下层互补：MCP 让 Agent 用工具，A2A 让 Agent 找 Agent。

一句话定位 & 关键数字

一句话总结
A2A = Agent 世界的 HTTP。它不规定 Agent 怎么想、用什么模型、挂什么记忆，只规定两个 Agent 相遇时怎么握手、怎么交换任务、怎么协同推进。核心三件套：AgentCard 发现 · Task 生命周期 · Message/Part/Artifact 数据模型——全部跑在 JSON-RPC 2.0 over HTTPS 之上，外加 SSE 流式和 Push Notifications 两种异步通道。

2

问题：不同框架的 Agent 为什么互相不认识

2.1 一个真实的卡点场景

设想 2025 年一个企业架构师的日常困境：

  • 法务部用 LangChain 搭了一个"合同审查 Agent"，能解析 PDF 里的风险条款；
  • 财务部用 Microsoft Copilot Studio 搭了一个"发票核对 Agent"，对接内部 ERP；
  • 销售部用 CrewAI 搭了一个"客户沟通 Agent"，对接 Salesforce；
  • 总经理想要一个"季度交易闭环 Agent"——让上面三个 Agent 协作，从发起合同到收款全自动。

问题来了：LangChain、Copilot Studio、CrewAI 是三套互不兼容的 Agent 栈。它们的消息格式不一样、工具注册方式不一样、上下文管理方式不一样。要让它们互通，架构师只有三条路：

方案 A：全部重写
把三个 Agent 都迁到同一个框架。成本高，而且各业务部门已有的 DevOps 积累全部作废。
方案 B：点对点适配
为每一对 Agent 写一层 HTTP 适配层。3 个 Agent 需要 3 个适配对；10 个就是 45 个。O(N²) 灾难。
方案 C：共同协议
让三个 Agent 都说同一种"Agent 语言"，只需要实现 1 次协议绑定，就和所有同协议 Agent 互通。这就是 A2A 要做的事。

2.2 Agent 互操作比 Web 互操作难在哪

⚠️ Agent 不是无状态 Web API
传统 REST/gRPC 假设调用是短请求、无状态、结构化 schema。Agent 交互完全不同：
  • 长任务：一个 Agent 可能花几分钟甚至几小时完成任务（例：深度研究、代码重构）；
  • 多模态：输入输出可能是文本、文件、结构化 JSON、甚至流媒体；
  • 中途交互：Agent 执行到一半可能需要用户补充信息、或要求授权；
  • 能力不透明：服务端 Agent 内部用什么模型、什么记忆，客户端不应当也不需要知道；
  • 安全边界：跨组织 Agent 调用要有强认证和审计。
这五个特性让"Agent 接口"不能简单套用 REST——A2A 本质是为这五个特性量身设计的协议。

2.3 为什么这个事 Google 在做

A2A 诞生的时间节点值得注意：Anthropic 2024 年底推出 MCP 后迅速成为事实标准（Claude、Cursor、Windsurf、VS Code 都接入）。Google 作为云厂商和 Agent 生态玩家，不能在基础设施层缺席：

  • 如果任由 MCP 扩展到 Agent↔Agent 层面，Google 会失去协议主导权；
  • 自建一个"Google 专属 Agent 协议"又会被市场嫌弃为封闭标准；
  • 最优策略：开放 + Linux Foundation 治理 + 与 MCP 互补定位——A2A 的每一步都很符合这个剧本。

协议核心：AgentCard · Task · Message/Part/Artifact

3.1 三层设计

A2A 协议的三层抽象┌─────────────────────────────────────────────────────────┐ │ Layer 3: Task 任务生命周期管理 │ │ submitted → working → input-required → completed │ │ → failed/canceled │ ├─────────────────────────────────────────────────────────┤ │ Layer 2: Message / Part / Artifact 数据模型 │ │ Message = role(user|agent) + parts[] │ │ Part = text | file(raw|url) | data(JSON) │ │ Artifact = 任务产出物（parts[]） │ ├─────────────────────────────────────────────────────────┤ │ Layer 1: AgentCard 发现与元数据 │ │ /.well-known/agent.json │ │ capabilities · skills · endpoints · security │ └─────────────────────────────────────────────────────────┘ 传输：JSON-RPC 2.0 over HTTPS · SSE 流式 · Push 异步

3.2 Layer 1 · AgentCard：Agent 的"名片"

AgentCard 是 A2A 的核心发现机制。任何 A2A 兼容的 Agent 都必须在 /.well-known/agent.json 下暴露一份 AgentCard，描述自己是谁、能做什么、怎么连。

AgentCard 结构（简化示例）{ "name": "contract-review-agent", "version": "1.2.0", "provider": { "organization": "Acme Legal", "url": "https://legal.acme.com" }, "description": "Reviews contracts for risk clauses.", "capabilities": { "streaming": true, "pushNotifications": true, "extendedAgentCard": false }, "skills": [ { "id": "risk-review", "name": "Risk Clause Review", "description": "Identify risky clauses in a contract PDF.", "inputModes": ["application/pdf", "text/plain"], "outputModes": ["application/json", "text/markdown"] } ], "url": "https://legal.acme.com/a2a", "interfaces": ["jsonrpc", "grpc"], "securitySchemes": { "oauth2": { /* ... */ } } }

这份 Card 让任何客户端（包括其他 Agent）可以：(1) 判断是否要接入；(2) 知道可以发什么格式（inputModes）、期望拿回什么格式（outputModes）；(3) 知道需要什么认证（securitySchemes）。

🔑 AgentCard 的设计哲学
AgentCard 致敬了两个成熟概念：OpenAPI/Swagger 的服务描述文件，和 OAuth 2.0 Discovery 的 /.well-known/ 约定。这让 A2A 在工程实践上对接已有基础设施几乎零摩擦——运维人员不用学新的服务注册工具，用 Nginx 返回一个 JSON 文件就能让 Agent 被发现。

3.3 Layer 2 · Message / Part / Artifact：数据模型

Message

  • messageId：消息唯一 ID；
  • contextId：会话上下文 ID（多轮对话用这个串起来）；
  • taskId：归属的 task ID（可选）；
  • role：ROLE_USER（客户端发）或 ROLE_AGENT（服务端发）；
  • parts：Part 数组——这是 A2A 最精巧的设计之一。

Part（OneOf 多态）

Part 是内容片段，支持三种类型：

  • TextPart：普通字符串，适合对话和指令；
  • FilePart：文件引用，可以是 raw（base64 内联）或 url（外部链接）；附带 mediaType 和 filename；
  • DataPart：结构化 JSON，适合表单、查询结果、工具调用参数。

一条 Message 里的 parts 可以混合多种类型——比如同时发一段文本指令 + 一个 PDF 附件 + 一段结构化参数。这比"只能发字符串 prompt"的传统 LLM API 表达力强得多。

Artifact

Task 的产出物叫 Artifact——结构上和 Message 类似（也是 parts 数组），但语义上是"任务结果"而非"对话消息"。一个 task 可以产生多个 artifact（例如一份 review 报告 + 一张风险热图）。

3.4 Layer 3 · Task：任务生命周期

Task 是 A2A 的长任务抽象。它的状态机有 8 个状态：

状态含义是否终态
SUBMITTED已接收，排队中否
WORKINGAgent 正在处理否
INPUT_REQUIRED需要客户端补充信息否（需人类干预）
AUTH_REQUIRED需要额外认证否
COMPLETED成功完成✅ 终态
FAILED执行失败✅ 终态
CANCELED客户端主动取消✅ 终态
REJECTEDAgent 拒绝接受✅ 终态

关键洞察：INPUT_REQUIRED 和 AUTH_REQUIRED 这两个非终态状态是 A2A 区别于普通 RPC 的要害——它承认了 Agent 可能在执行中途需要"暂停问用户"，而协议层原生支持这种"可中断可恢复"的语义。

3.5 核心 JSON-RPC 方法

A2A v1.0 主要 RPC 方法（a2a/ 前缀）a2a/SendMessage → 发起/继续一个 Task a2a/SendStreamingMessage → 同上，但返回 SSE 流 a2a/GetTask → 查询 Task 当前状态 a2a/ListTasks → 列出历史 Tasks（支持 filter） a2a/CancelTask → 取消 Task a2a/SubscribeToTask → 订阅 Task 更新（SSE） a2a/GetExtendedAgentCard → 拿认证后可见的完整 Card a2a/CreatePushNotification → 配置异步回调通知 a2a/GetPushNotification / ListPushNotifications / Delete...

3.6 Task 委托典型流程

1
Discovery：客户端 Agent 访问 https://legal.acme.com/.well-known/agent.json，拿到目标 Agent 的 AgentCard，确认它支持 "risk-review" skill、接受 PDF 输入。
2
Delegation：调用 a2a/SendMessage，传一条 Message：role=user, parts=[TextPart("请审查这份合同的风险"), FilePart(url=contract.pdf)]。服务端返回 taskId。
3
Streaming：客户端用 a2a/SubscribeToTask 订阅 SSE 流，实时拿到 "WORKING: 正在解析 PDF..." "WORKING: 检测到 3 处风险条款..." 等进度。
4
Mid-task Interaction：如果服务端状态变成 INPUT_REQUIRED（例："该合同涉及欧盟客户，请确认是否启用 GDPR 检查？"），客户端用 a2a/SendMessage 把补充消息塞进同一个 taskId 继续。
5
Completion：Task 到达 COMPLETED，客户端拿到 Artifact（风险报告 JSON + markdown 摘要 + 风险热图 PDF）。整个过程无需客户端知道服务端 Agent 用的是 Gemini 还是 Claude、有没有 RAG、挂的是什么工具——opacity 原则。
把 A2A 映射到斯坦福小镇：小镇 25 个 NPC 目前是在同一个 Python 进程内通过共享内存通信——简陋但够用。一旦想把小镇扩展成"跨服务器的大世界"（比如一个 NPC 跑在 A 机器、另一个跑在 B 机器），A2A 就是天然承载——Agent 之间的对话消息 = Message、NPC 能力描述 = AgentCard、跨 NPC 任务委托 = Task。小镇论文时代还没有 A2A，现在重写小镇，协议层几乎必选 A2A。

与 MCP 对比：两个协议在栈的不同层

4.1 一句话分工

📐 记住这一句
MCP 是 Agent↔Tool（一个 Agent 调用外部能力），A2A 是 Agent↔Agent（两个对等 Agent 协作）。
前者解决"Agent 不会用电锯"——给它一套标准工具接口；后者解决"两个 Agent 不互相认识"——给它们一套标准握手协议。两者是同一协议栈的不同层，不是竞争关系。

4.2 深度对照表

维度 MCP (Model Context Protocol) A2A (Agent-to-Agent Protocol)
出品方 Anthropic · 2024.11 Google · 2025.04（后归 Linux Foundation）
定位 Agent↔Tool · 工具调用协议 Agent↔Agent · 对等协作协议
核心角色 Host (LLM) + Client + Server (Tool) Client Agent + Remote Agent (对等)
核心抽象 Tool · Resource · Prompt AgentCard · Task · Message
发现机制 Client 主动列出 Server 的 tools /.well-known/agent.json 暴露 AgentCard
交互范式 同步请求/响应为主 长任务 + 流式 + 异步回调
状态管理 近乎无状态（单次调用） 有状态 Task + 生命周期
中途交互 无（要靠 Host 重新调） INPUT_REQUIRED 原生支持
典型场景 Claude Desktop 调文件系统 / 数据库 / API 法务 Agent 把合同委托给财务 Agent 核对
权力关系 主从（Host 主动、Tool 被动） 对等（两个 Agent 都可能是发起方）
组合使用 一个 A2A Agent 内部可以挂 N 个 MCP Server 两个挂 MCP 的 Agent 之间用 A2A 通信

4.3 典型组合：MCP + A2A 叠加使用

一个企业 Agent 平台的分层（推荐做法）┌──────────────────────────────────────────────────┐ │ 组织 / 团队 / 第三方 Agent (互相用 A2A 通信) │ │ 法务 Agent ─── A2A ─── 财务 Agent │ │ │ │ │ │ MCP MCP │ │ │ │ │ │ ┌────┴────┐ ┌───┴────┐ │ │ │ PDF 解析│ │ ERP API │ │ │ │ DB 查询 │ │ 邮件发送│ │ │ └─────────┘ └─────────┘ │ │ │ │ 每个 Agent 自己用 MCP 挂工具 │ │ Agent 之间协作用 A2A 发消息 │ └──────────────────────────────────────────────────┘

这张图是理解 MCP × A2A 关系的最重要一张图。每个"法务/财务 Agent"内部是一个完整 LLM + MCP 工具栈的小宇宙；而它们之间的协作不走内存、不走专有 API，统一用 A2A 说话。MCP 是垂直方向（一个 Agent 的能力深度），A2A 是水平方向（Agent 之间的协作广度）。

4.4 为什么这两个协议可以和平共处

MCP：信任边界内
MCP 假设 Host（LLM）信任 Tool——通常是同一开发者/团队的组件。所以 MCP 的安全模型相对简单（本地 stdio 传输、或者受控 HTTP），不强调跨组织强认证。
A2A：信任边界外
A2A 假设两个 Agent 可能属于不同组织、不同厂商、不同信任域。所以协议里 OAuth2 / mTLS / API Key 等方案是一等公民，还有 AgentCard 签名（防伪造名片）、extendedAgentCard（认证后才给看敏感能力）等机制。
⚠️ 容易混的点：A2A 不取代 MCP，也不延伸 MCP
有人觉得"既然都是协议，A2A 是不是 MCP 的加强版"——不是。A2A 和 MCP 解决不同层的问题，一个 Agent 可以同时：对外暴露 A2A 服务（让别的 Agent 发现和调用自己）、对内挂载 N 个 MCP server（让自己能用工具）。两个协议的字段几乎没有重叠——Message/Part/Artifact/Task 是 A2A 独有；Tool/Resource/Prompt/Sampling 是 MCP 独有。
5

对生态的意义：为什么 A2A 重要

5.1 打破"框架锁定"

2024-2025 年的 Agent 生态在经历严重的框架碎片化：LangChain、AutoGen、CrewAI、LlamaIndex、AgentScope、Swarm、Copilot Studio、Bedrock Agents……每个框架都定义自己的 Agent 接口，互相不兼容。这和 2010 年前后的 Web 框架战争有点像，但要严重得多——因为 Agent 的抽象维度远比 HTTP 请求复杂。

A2A 的价值在于：一个 Agent 只要能把自己包装成 A2A Server，就立刻可以被任何 A2A Client 发现和调用——不关心它里面用的是 LangChain 还是 AutoGen。这相当于给 Agent 世界发了一张"通行护照"。

5.2 为"跨组织 Agent 市场"铺路

🌐 Agent 互联网的雏形
A2A 支持的场景远不止企业内部 Agent 协作——它的最终愿景是跨组织、跨公司的 Agent 市场：
  • 你自己的"私人助理 Agent"可以自动调用 Expedia 的"订票 Agent"、Kayak 的"比价 Agent"、Marriott 的"酒店 Agent"完成一次出行；
  • 这些外部 Agent 只暴露 AgentCard 的公开能力描述，不需要你理解它们内部怎么实现；
  • OAuth + AgentCard 签名 + Task 审计日志构成了 "Agent 间合约"的技术基础；
  • 一旦这个生态起飞，Agent 本身会变成一种可货币化的 Web 服务——就像今天的 API 经济，但交互语义更高级。

5.3 对各类玩家的实际影响

玩家影响建议行动
Agent 框架作者 不支持 A2A 的框架会被边缘化 尽快添加 A2A Server/Client 适配（参考 a2a-samples）
企业应用开发者 可以用 A2A 解耦多部门 Agent 把遗留 Agent 包装成 A2A 服务，逐步迁移
SaaS 厂商 必须提供 A2A Agent 入口 在自家 SaaS 上 /.well-known/agent.json 暴露能力
云厂商 Agent 托管服务会标配 A2A 网关 参考 Google Vertex AI Agent Builder、AWS Bedrock Agents 动向
独立开发者 可以写 Agent 直接接入大公司 Agent 学 A2A SDK（Python/Go/JS 等 5 种语言）

5.4 潜在风险与未竟之处

⚠️ A2A 还没解决的问题
  • 语义对齐：两个 Agent 说同一个字段 "price"，含义可能不一样（含税/不含税？货币？）——A2A 只定义了传输协议，不定义领域本体；
  • 计费 / 结算：跨组织 Agent 调用谁付钱？v1.0 里没有标准计费字段 <待实证>；
  • 信任与声誉：一个 Agent 说它会做 X 但实际做不好，怎么体现？还没有"Agent 评分系统"；
  • 对抗性行为：恶意 Agent 的 AgentCard 可以撒谎。签名只防篡改，不防"自我夸大"；
  • 标准碎片化风险：微软/OpenAI 会不会推竞争协议？<观察中>——但 Linux Foundation 治理 + 早期合作伙伴广泛签约，基本锁定了 A2A 的中立地位。
🧭 结论：Agent 互联网的 TCP/IP
A2A 不会是 Agent 协议栈的全部，但它是最接近"TCP/IP for Agents"的候选。它的三个关键设计选择——对等而非主从、任务而非请求、透明边界而非黑盒——契合了 Agent 协作的本质特征。未来几年，你会看到"AgentCard 目录""Agent 注册中心""Agent 评分机构"等周边生态陆续长出来，就像 2000 年代 HTTP 周边长出 CDN / DNS / CA 一样。

对研究者：A2A 给了多 Agent 系统一个工业级运行时——以后不用再纠结"我的 paper 里多 Agent 怎么通信"；
对开发者：A2A 给了"再也不用为每个集成写胶水"的承诺——但需要时间和广泛采纳才能兑现；
对企业：A2A 给了跨系统 Agent 协作的标准化入场券——早接入早收益。
6

FAQ

Q1：A2A 和 MCP 真的是互补的吗？会不会最终一个吃掉另一个？
技术上两者是互补的，不会互相吃掉，但政治上会有竞争。

技术互补的原因已经讲过：MCP 管 Agent↔Tool、A2A 管 Agent↔Agent。两者字段几乎不重叠、解决的问题不重叠。最典型的证据是：主流框架都在同时支持两者——AgentScope、LangGraph、AutoGen v0.4、Copilot Studio 等纷纷声明兼容 MCP + A2A。

政治竞争的层面：Anthropic 和 Google 都想成为 Agent 时代的协议主导方。Anthropic 通过 MCP 已经站稳了"工具调用层"；Google 想通过 A2A 拿下"Agent 协作层"。如果 Anthropic 未来把 MCP 向上扩展支持"Agent-as-Tool"（把对面 Agent 当工具调），理论上可以覆盖 A2A 的一部分场景；反过来，Google 也可以在 A2A 里加工具调用语义（实际上 A2A 的 DataPart 已经能表达工具调用）。

最可能的未来：两者并存 3-5 年，各自成熟；然后要么出现一个新的"Super Protocol"统一它们（希望由 Linux Foundation 或 IETF 主持），要么分层稳定——就像 HTTP 和 TCP 各管各的，谁也不需要吃掉谁。<3-5 年趋势待观察>
Q2：我现在做 Agent 应用，要不要现在就上 A2A？
分三种情况回答：

单 Agent 应用（一个 LLM + 几个工具）：不需要 A2A。MCP 就够了。你的 Agent 不对外暴露、不调别人的 Agent，A2A 就是过度设计。

同一团队多 Agent 应用（LangGraph/AutoGen 内部多节点）：不强求。框架内部通信可以直接用内存/消息队列，性能更好。只有当你想把某个 Agent 暴露出去给其他团队/系统消费时，才用 A2A 封装。

跨团队 / 跨组织 / 跨产品的 Agent 集成：强烈推荐现在就上 A2A。三个理由：
  • 避免未来债：现在不上，自己写一套胶水代码，等 3 年后 A2A 成为事实标准，又要重写；
  • SDK 已经成熟：Python/Go/JS/Java/.NET 五种语言官方 SDK 都到 v1.0，工程化成本已经很低；
  • 生态势能已起：Google、Amazon、Salesforce、MongoDB 等大厂都在接入，早期接入能蹭到生态红利（比如被列入 awesome-a2a、拿到 Google 的案例推广 待实证）。

落地建议：先把你最稳定、最通用的一个 Agent 包装成 A2A Server（暴露 AgentCard + 实现 SendMessage/GetTask），放到 /.well-known/agent.json，试试让别的 Agent 发现调用——这个最小闭环打通后，扩展到其他 Agent 就是复制粘贴。整个学习成本大概2-3 天（前提是你熟悉 JSON-RPC 和 SSE）。
📌 一句话记住本篇
A2A = Google 主导、Linux Foundation 治理的 Agent↔Agent 开放协议，通过 AgentCard 发现 + Task 生命周期 + Message/Part/Artifact 数据模型 三层设计，解决不同框架/厂商/组织的 Agent 互操作问题。与 MCP（Agent↔Tool）互补叠加，是 2025-2026 年 Agent 互联网协议栈的关键拼图——对任何做跨系统 Agent 集成的团队都是必须理解的基础设施。
