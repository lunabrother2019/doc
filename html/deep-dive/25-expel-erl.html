为什么要配对读这两篇

在 Reflection 支柱下，反思的"时间跨度"有三个层次：

层次代表工作边界
Intra-step（单步内）CoT / Inner Monologue一次前向中的自我推理
Intra-task（单任务多 trial）Reflexion同一任务失败 → 反思 → 重试，反思只在本任务生命周期内有效
Inter-task（跨任务）ExpeL / ERL / AutoGuide把历史任务的经验沉淀下来，跨任务复用
这两篇正是"跨任务反思"子路线的两代代表
ExpeL (2023.08) 是第一代：把多条轨迹熬成一份通用 insights（类似"蒸馏"）。ERL (2026.03) 是第二代：发现"熬煮会丢失细节"，回归到保留每条轨迹的独特启发 + 检索时按相关性筛选。你会看到这是一个非常典型的"先聚合、后发现聚合有损、再回到检索"的循环——和信息检索领域从 topic model 走向 dense retrieval 的历史几乎同构。

在本研究库的概念图里，两篇共享 "R4 跨轨迹反思" 节点，这个放在同一个节点的决定本身就是在暗示它们是同一范畴内的演化对，而不是两个正交的工作。

3

ExpeL 深度剖析

3.1 Experience pool — 文本版的 Replay Buffer

ExpeL 的第一步是让一个 ReAct agent 在训练任务集上反复跑（成功 / 失败都记录）。每条轨迹进 pool 的形式大致是：

experience entry (简化){ task_id: "alfworld-023", trajectory: "Thought 1: ... Action 1: ... Observation 1: ...", outcome: "success" | "fail", reward: 0.0 ~ 1.0 }

作者明确把这类比 Lin 1992 的 Replay Buffer（强化学习经典的 off-policy 存储），区别是：Lin 存的是 (s, a, r, s') 张量，ExpeL 存的是自然语言 trace。相同的思想、不同的底层表征。

3.2 Insight extraction — 离线反思出"通用规则"

这是 ExpeL 最关键的一步。作者设计了一个 COMPARE 与 SUCCESS 两类操作的 prompt：

  • COMPARE：喂给 LLM 一对 (success trajectory, fail trajectory)（同任务 / 同类任务），问"为什么失败、应该怎么改"→ 产出一条 insight。
  • SUCCESS：喂给 LLM 多条成功 trajectory，问"它们共同的成功模式是什么"→ 产出一条 insight。

Insight 是一句或几句自然语言，类似："In WebShop tasks, always check product options before adding to cart." 所有提取出来的 insights 会进一步经过 ADD / EDIT / DOWNVOTE / UPVOTE / REMOVE 五个操作的"维护循环"——这是 ExpeL 一个容易被忽视的细节，insights 池不是静态追加，而是像 wiki 一样被持续编辑。

这一步为什么是"离线"而非推理时
ExpeL 刻意把反思放在训练阶段做完、把 insights 冻结下来，推理时只做检索和拼接。好处是推理延迟低；代价是对新分布的适应性差——你没有机制在看到测试任务后再产出新 insight。这正是 ERL 要攻击的点之一。

3.3 推理阶段 — 双路检索

给定一个新任务 task_test，ExpeL 做两件事：

  1. 相似轨迹检索：从 experience pool 里基于任务描述 embedding 取 top-k（论文里一般 k=2-3）相似的成功轨迹，作为"few-shot 示范"。
  2. Insights 全量注入：把所有 insights（通常几十条，token 开销可控）全部拼到 system prompt。

这是"示范 + 规则"的双管齐下。作者做了 ablation：insights-only 和 trajectories-only 都不如双路，说明两者是互补信息——trajectories 提供具体动作序列的模仿目标，insights 提供高层决策原则。

3.4 跨域迁移实验

ExpeL 最有趣的一组实验是 cross-task transfer：

源任务目标任务关系是否有提升
HotpotQAFEVER多跳问答 → 事实核查有，insights 可迁移
ALFWorldWebShop家居规划 → 网购导航部分迁移（通用规则迁得好）
WebShopALFWorld反向弱

结论：高层 insights（"先验证再执行""遇到不确定时 backtrack"）能跨域，具体 trajectory 不能。这个发现反过来也在说：如果 insights 抽象得足够高，它们对具体新任务的"颗粒度指引"就不够了——这是 ERL 要解决的张力。

4

ERL 深度剖析

4.1 Heuristics pool — 不是 insights

ERL 刻意不叫 insights。原因是：它产出的每条知识单元更长、更具体、包含原始上下文。一条 heuristic 可能包含"任务类型、失败时的关键 action 片段、修正建议"，不像 ExpeL insight 那样压缩为一句通用规则。

heuristic entry (示意){ task_signature: "search + date filter", observed_failure_pattern: "agent ignored the year constraint in query", suggested_strategy: "explicitly parse temporal constraints before issuing search", source_trajectory_digest: "...", original_outcome: "fail -> success after fix" }

4.2 单轨迹抽取 — ExpeL 做不到的

ExpeL 的 COMPARE 需要 (success, fail) 配对，SUCCESS 需要多条成功轨迹，这意味着必须有量。ERL 的提取 prompt 针对单条轨迹 + 其 outcome 就能工作：LLM 直接被问"这条轨迹揭示了什么可复用的启发"，产出一条 heuristic。

这里的权衡
单轨迹抽取的代价是："启发"的普适性更弱，容易 overfit 到这一条轨迹的具体情境。ERL 的设计哲学是：不在抽取阶段强求普适，把筛选的活交给后续 relevance scoring——让"什么时候用哪条启发"留到测试时动态决定。

4.3 Relevance scoring + top-k 注入

测试时，给定新任务，ERL 让 LLM 对 pool 里每条（或经粗召回后的候选）heuristic 打一个 relevance 分，取 top-k（论文里一般 k=3-5）注入 context。这是和 ExpeL "insights 全量拼接"的根本区别：

  • ExpeL：pool 里所有 insights 一次全塞，假设它们都是通用规则，互不干扰。
  • ERL：pool 大了之后全塞装不下（heuristics 单条更长），且很多 heuristic 对当前任务是噪声 → 必须检索。

4.4 Gaia2 基准 — 比 ExpeL 年代的基准更难

ERL 主战场是 Gaia2（GAIA 基准的第二代），分为：

  • Search split：需要调用搜索工具、多源信息整合。
  • Execution split：需要跨工具执行复杂计算 / 操作。

论文报告 ERL 在 Gaia2 上达到 56.1% 成功率，比 ReAct baseline 提升 7.8 个百分点，同时高于 ExpeL 和 AutoGuide 的复现结果。注意：这是 ERL 自己复现 baseline 的数字，ExpeL 原论文不在 Gaia2 上评过——所以需要客观看待这个对比（见 FAQ）。

6

关键演化论点

论点 1 ：insights vs heuristics 是 LLM agent 经验复用的两种范式
它们不是"孰优孰劣"的关系，而是"压缩 vs 保留"的两端。ExpeL 开创了 post-hoc 抽取高层规则的压缩路径；ERL 反向回到保留原始轨迹细节 + 检索筛选的非压缩路径。这两条路都有存在价值——它们服务于不同的任务分布特性和 token budget 约束。
论点 2 ：这是一次隐含的 "bitter lesson" 复现
Sutton 的 bitter lesson 说："那些把人类先验塞进去的方法，长期会被让机器自己搜索 / 学习的方法打败。" ExpeL 的"聚合出通用规则"本质是一种特征工程——人为设计了"insight 必须是高抽象度通用规则"这个先验。ERL 放弃了这个先验，让检索自己决定该用什么——这是从 compression 走向 retrieval 的标志性一步。在更早的 NLP 史上，这对应从 LDA topic model 到 dense retrieval 的演化。
论点 3 ：但 ERL 不是终点
保留细节 + 检索的路径也有边界：pool 无限增长时，relevance scoring 本身成了瓶颈（要给 N 条 heuristic 打分）。下一代可能的演化方向是：hierarchical heuristics（粗召回 → 精筛） / graph-indexed heuristics（像 A-MEM 那样加语义边）/ self-compressing heuristics（池过大时触发"二次蒸馏"，回到一个带选择性的 insights 层）。事实上 24 号综述里列的 "Memory-R1" 和 "Memory+RL 联合优化"就是在做这件事。

与 Generative Agents / 斯坦福小镇的联系

7.1 Reflection 的范围之别

小镇的 reflection 是：当 memory stream 中近期记忆的 importance 累计超过阈值，触发反思，抽取 higher-level insight 写回 memory stream。形式上和 ExpeL 非常像——都是"从一堆观察中抽取一条高层规则"。但范围不同：

反思的时间跨度反思的主体产物去向
Smallville Reflectionintra-character（单 agent 的生命周期内）单个 agent写回自己的 memory stream
Reflexionintra-task（同任务的多 trial）单 agent × 单任务下轮 trial 的 prompt
ExpeL / ERLinter-task（跨任务、跨分布）通常是"系统级"（一个 agent 在训练任务集上跑完得到）共享的 insights / heuristics pool

7.2 Relevance 打分的同源

小镇的记忆检索公式是 score = Recency × Importance × Relevance，其中 Relevance 来自当前 query 与 memory 的 embedding 相似度。ERL 的 heuristic relevance scoring 虽然换成了 LLM-as-judge，但功能位置完全一致——都是"给候选记忆 / 启发打分，只取最相关的注入"。两者都认识到：记忆 / 经验池会膨胀，必须有打分机制决定用哪些。

如果把小镇的 Memory Stream 理解为"一个 agent 一生的 experience pool"，那么小镇的 reflection 就是个人版 ExpeL——不跨任务、但跨事件。ExpeL 把这个机制从"一个 agent 内"放大到"训练任务集上"，本质是把时间维度的经验累积换成了任务维度的经验累积。ERL 再进一步，承认聚合会丢信息、回到基于检索的调用——这正好也呼应了小镇没有把 raw memory 扔掉的设计：反思出 insight 后，原始记忆还在 stream 里可检索。小镇在 2023 年用一个耦合的打分公式把两层都做了，ExpeL / ERL 在 2024-2026 把它们拆成了正交的设计选择。

7.3 与 Voyager 的对照

Voyager（Minecraft 里的终身学习 agent）也有"经验库"的概念，但它的产物是可执行 JavaScript 技能函数，不是自然语言规则。映射关系：

  • Voyager skill library ≈ ExpeL insights（跨任务沉淀、可检索复用），但形式是代码。
  • Voyager 的"技能可直接执行"带来了一个 ExpeL / ERL 都没有的优势：可验证——代码在环境里跑出结果，对就对、错就错。ExpeL insights 对不对，只能靠下游任务成功率间接验证。
  • 但 Voyager 的代价是只能用于"动作可代码化"的环境（Minecraft 的离散 API），在 QA / Web browsing 这类任务里就不适用——这正是 ExpeL / ERL 的地盘。

8.2 FAQ — 澄清常见误解

Q1：ExpeL 和 Reflexion 区别是什么？不都是反思吗？
反思的时间跨度不同。Reflexion 是：在同一个任务里失败 → 反思 → 重新尝试；反思只在本任务的多个 trial 之间传递，任务结束后不保留。ExpeL 是：在一批训练任务里跑完，把所有经验离线反思成一个 insights pool，这个 pool 被后续所有新任务共享。一个是 intra-task 循环，一个是 inter-task 知识沉淀。Reflexion 解决"给我第二次机会"，ExpeL 解决"别让前人的失败白费"。
Q2：ERL 真的超越 ExpeL 吗？对比公平吗？
需要谨慎。ERL 报告的 "+7.8% vs ReAct, 超 ExpeL" 是在 Gaia2 基准、用 ERL 团队自己复现的 ExpeL 上得到的。ExpeL 原论文根本没在 Gaia2 上评（那时 Gaia2 还没出），所以这是 "ERL 把 ExpeL 方法迁移到 Gaia2 后跑出的结果 vs ERL 自己"。这不等于 "ExpeL 在它的主场（ALFWorld / WebShop）也输"。更严谨的说法是：在 Gaia2 这种异构 tool use 场景下，保留 granular 细节 + 检索式调用 优于 聚合式规则——这和 ExpeL 原来的主场特性（ALFWorld 的高度结构化任务）刚好反过来，结论合情合理，但不能简单推广为"ERL 全面超越 ExpeL"。
Q3：跨轨迹经验 和 memory stream 的边界在哪里？它们不都是"存历史"吗？
关键看"谁拥有"和"存什么"。Memory stream（小镇）属于单个 agent，存的是原始事件观察（"在公园看到 Klaus 和 Maria 争吵"），是 character-centric 的自传体记忆。跨轨迹经验池（ExpeL / ERL）属于系统 / 一类 agent，存的是反思产物（"遇到工具调用失败时应该 X"），是 skill-centric 的程序性知识。两者完全可以共存：一个 agent 同时有自己的 memory stream（记我是谁、我经历了什么）和一个共享的 experience pool（记该怎么解决任务）——事实上 MetaGPT、CAMEL 这类多 agent 系统的记忆设计正在往这个方向走。
Q4：我该先读哪一篇？
如果你对 方法论原型感兴趣（"跨轨迹反思这个 idea 怎么来的"），先读 ExpeL——它有更完整的消融、更清晰的 Replay Buffer 类比、更好的基准覆盖、还有开源代码。如果你关心当前 SOTA 的做法（"现在 Gaia2 上什么工作有效"），先读 ERL——它是对前者的精确修正，能直接看到"ExpeL 哪一步被改了、为什么"。理想顺序是：ExpeL → ERL → 回头读 ExpeL 的 limitation 讨论，你会发现 ERL 正好在回应那些 limitation。
