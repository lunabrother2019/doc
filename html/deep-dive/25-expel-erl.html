2

为什么要三代同读

在 Reflection 支柱下，反思的"时间跨度"有三个层次：

层次代表工作边界
Intra-step（单步内）CoT / Inner Monologue一次前向中的自我推理
Intra-task（单任务多 trial）Reflexion同一任务失败 → 反思 → 重试，反思只在本任务生命周期内有效
Inter-task（跨任务）ExpeL / AutoGuide / ERL把历史任务的经验沉淀下来，跨任务复用
这三篇正是"跨任务反思"子路线的三代递进
ExpeL (2024.03) 是第一代：把多条轨迹熬成一份通用 insights（类似"蒸馏"）—— 推理时一锅全塞。
AutoGuide (2024.11) 是第二代：发现"一锅乱炖会让无关 insight 干扰决策"，转为情境感知 IF-THEN guidelines —— 推理时按 context 匹配、条件激活。
ERL (2026.03) 是第三代：进一步发现"条件句也会丢失轨迹细节"，回归到保留每条轨迹的独特启发 + 检索时按相关性筛选。
你会看到这是一个非常典型的"先聚合、后发现聚合有损、再回到结构化分发、最后彻底走向检索"的递进——和信息检索领域从 topic model 走向 dense retrieval 的历史几乎同构。

2.1 时间线与承上启下

2024.03 · AAAI 2024
ExpeL — 聚合式 insights
Zhao et al. (清华 LeapLab)。第一个把 Replay Buffer 思想搬到文本反思上的工作。推理时把所有 insights 一并塞进 prompt，假设它们都是"普适通用规则"。
2024.11 · NeurIPS 2024
AutoGuide — 情境感知 guidelines
Fu, Kim, Logeswaran et al.（LG AI Research 等合作）。观察到 ExpeL 把所有规则无差别注入，无关规则反而会干扰决策。提出把规则写成 IF context THEN action，并构造 Context Identification Module 做情境匹配——从"一锅乱炖"走向"条件分发"。
2026.03 · arXiv v2
ERL — 检索式 heuristics
继续攻击：即便写成 IF-THEN，规则本身还是从多条轨迹"蒸馏"出来的；如果轨迹本身就稀少、异构（Gaia2 这种场景），蒸馏代价过高。ERL 的做法是根本不蒸馏，一条轨迹就产出一条保留原始细节的 heuristic，推理时 LLM 直接给 relevance 打分筛选。

在本研究库的概念图里，三篇共享 "R4 跨轨迹反思" 节点——这个放在同一个节点的决定本身就是在暗示它们是同一范畴内的演化链，而不是三个正交的工作。

3

ExpeL 深度剖析

3.1 Experience pool — 文本版的 Replay Buffer

ExpeL 的第一步是让一个 ReAct agent 在训练任务集上反复跑（成功 / 失败都记录）。每条轨迹进 pool 的形式大致是：

experience entry (简化){ task_id: "alfworld-023", trajectory: "Thought 1: ... Action 1: ... Observation 1: ...", outcome: "success" | "fail", reward: 0.0 ~ 1.0 }

作者明确把这类比 Lin 1992 的 Replay Buffer（强化学习经典的 off-policy 存储），区别是：Lin 存的是 (s, a, r, s') 张量，ExpeL 存的是自然语言 trace。相同的思想、不同的底层表征。

3.2 Insight extraction — 离线反思出"通用规则"

这是 ExpeL 最关键的一步。作者设计了一个 COMPARE 与 SUCCESS 两类操作的 prompt：

  • COMPARE：喂给 LLM 一对 (success trajectory, fail trajectory)（同任务 / 同类任务），问"为什么失败、应该怎么改"→ 产出一条 insight。
  • SUCCESS：喂给 LLM 多条成功 trajectory，问"它们共同的成功模式是什么"→ 产出一条 insight。

Insight 是一句或几句自然语言，类似："In WebShop tasks, always check product options before adding to cart." 所有提取出来的 insights 会进一步经过 ADD / EDIT / DOWNVOTE / UPVOTE / REMOVE 五个操作的"维护循环"——这是 ExpeL 一个容易被忽视的细节，insights 池不是静态追加，而是像 wiki 一样被持续编辑。

这一步为什么是"离线"而非推理时
ExpeL 刻意把反思放在训练阶段做完、把 insights 冻结下来，推理时只做检索和拼接。好处是推理延迟低；代价是对新分布的适应性差——你没有机制在看到测试任务后再产出新 insight。这正是 AutoGuide / ERL 要攻击的点之一。

3.3 推理阶段 — 双路检索

给定一个新任务 task_test，ExpeL 做两件事：

  1. 相似轨迹检索：从 experience pool 里基于任务描述 embedding 取 top-k（论文里一般 k=2-3）相似的成功轨迹，作为"few-shot 示范"。
  2. Insights 全量注入：把所有 insights（通常几十条，token 开销可控）全部拼到 system prompt——这是"一锅乱炖"的由来，也是 AutoGuide 直接攻击的点。

这是"示范 + 规则"的双管齐下。作者做了 ablation：insights-only 和 trajectories-only 都不如双路，说明两者是互补信息——trajectories 提供具体动作序列的模仿目标，insights 提供高层决策原则。

3.4 跨域迁移实验

ExpeL 最有趣的一组实验是 cross-task transfer：

源任务目标任务关系是否有提升
HotpotQAFEVER多跳问答 → 事实核查有，insights 可迁移
ALFWorldWebShop家居规划 → 网购导航部分迁移（通用规则迁得好）
WebShopALFWorld反向弱

结论：高层 insights（"先验证再执行""遇到不确定时 backtrack"）能跨域，具体 trajectory 不能。这个发现反过来也在说：如果 insights 抽象得足够高，它们对具体新任务的"颗粒度指引"就不够了——这正是 AutoGuide / ERL 要解决的张力。

4

AutoGuide 深度剖析

核心立意：ExpeL 的 insights 是"无条件"的——不管你当前处于哪个状态，所有规则一并注入。但现实里，大部分规则只在特定情境下才成立。AutoGuide 的贡献就是把这个"条件性"显式化。

4.1 Guideline 的形式 — IF-THEN 条件句

AutoGuide 的输出单元不叫 insight 而叫 context-aware guideline。形式大致是：

context-aware guideline (示意){ context: "when the user's query asks about a specific product and the page shows a list of search results", guideline: "first click on the product matching the exact name before scrolling to read details" }

对比 ExpeL 的 insight："always check product options before adding to cart" —— ExpeL 版是"任何时候都遵守"；AutoGuide 版是"只有在 {搜索结果页} 这个情境下，才执行 {先点击精确匹配}"。IF-THEN 让规则具备了情境触发的语义，从"所有规则都在背景里闪烁"变成"只有匹配的规则亮起来"。

为什么"条件化"是关键进步
在 web navigation 类任务里，一个轨迹通常跨越多个截然不同的页面状态（登录页 / 搜索结果 / 商品详情 / 购物车 / 结算）。ExpeL 的无条件规则会把"结算页面应该先检查邮箱"这种页面专属建议在"搜索页"时也塞进 prompt，污染决策。AutoGuide 的 IF-THEN 让规则只在匹配的页面状态被激活，相当于给 LLM 提供了一份"根据当前情境动态组装的小抄"。

4.2 两模块架构

Context Identification Module

把训练 trajectory 切成片段，对每个片段识别它所处的"情境" —— 情境可以是页面类型、任务阶段、观察到的 UI 元素模式等。关键：情境粒度是"状态级 / 单步级"，不是"整条轨迹级"。一条轨迹会跨越多个情境标签。

Guideline Extraction Module

对每个（情境, 此情境下的动作片段, outcome）三元组，LLM 反思出一条 IF-THEN guideline。因为 context 已经明确，guideline 不必追求"全场景通用"，只需"此情境下有效"——这让规则更具体、更可操作。

4.3 推理时 — context 匹配 → guideline 激活

  1. 当前 state（观察 / 页面 DOM / 近期 action 序列）输入 Context Identification Module → 得到当前情境标签。
  2. 在 guideline 库里筛选所有 context == 当前情境 的 guideline。
  3. 只把这个子集注入 prompt，作为 LLM 的"临时决策手册"。
对比 ExpeL / ERL 的筛选机制
ExpeL：不筛选，全塞。
AutoGuide：按离散的 context 标签筛选（精确匹配）。
ERL：按连续的 LLM-as-judge relevance 分数筛选（top-k）。
AutoGuide 的筛选是"结构化条件判断"（像 rule-based retrieval），ERL 的筛选是"语义相关性排序"（像 dense retrieval）。这正是 AutoGuide → ERL 这一步演化的本质差别。

4.4 个体 context 粒度 — 关键设计决策

这里有一个非常容易误读的点：AutoGuide 的 context 不是"任务级"，而是"单步级 / 状态级"。同一条 trajectory 中不同的 step 会落入不同的 context bucket：

  • Step 3（在搜索结果页）→ context A → 激活 guideline G1
  • Step 7（在商品详情页）→ context B → 激活 guideline G4, G7
  • Step 11（在结算页）→ context C → 激活 guideline G2

这意味着 guideline 是随 agent 执行过程动态切换的——agent 每走一步，激活的规则集都在变。这种"按状态动态组装的 prompt"，比 ExpeL 整条任务用同一份 prompt 要细粒度得多。

4.5 实验结果 — 大幅超过 ExpeL

AutoGuide 主要在 web navigation 基准（WebArena 类）和 embodied 任务上评测。论文报告相比 ExpeL baseline 有显著提升，作者把这归因于：

  • Web 任务的情境分布差异非常大（不同页面状态对应完全不同的最优策略），context 分发正好切中要害；
  • 无关 guideline 的过滤让 LLM 更容易在正确规则上做出决策（减少注意力分散）；
  • Guideline 的具体度比 insight 高，对 "下一步该干什么" 提供了更直接的信号。
但 AutoGuide 不是终点
AutoGuide 的瓶颈是：context 必须能被"离散标签"化。如果任务的情境是连续的、异构的、甚至是 ad-hoc 的（比如 Gaia2 那种"每条任务要调用完全不同的 tool 组合"），context identification 本身就会失准——失准后，guideline 激活错误比 ExpeL 的"全塞但无筛选"还糟糕。ERL 正是观察到这一点，干脆放弃"离散 context 匹配"，改走"连续 relevance 打分"。
5

ERL 深度剖析

5.1 Heuristics pool — 不是 insights，也不是 guidelines

ERL 刻意不叫 insights，也不叫 guidelines。原因是：它产出的每条知识单元更长、更具体、包含原始上下文。一条 heuristic 可能包含"任务类型、失败时的关键 action 片段、修正建议"，不像 ExpeL insight 那样压缩为一句通用规则，也不像 AutoGuide guideline 那样写成规整的 IF-THEN。

heuristic entry (示意){ task_signature: "search + date filter", observed_failure_pattern: "agent ignored the year constraint in query", suggested_strategy: "explicitly parse temporal constraints before issuing search", source_trajectory_digest: "...", original_outcome: "fail -> success after fix" }

5.2 单轨迹抽取 — ExpeL / AutoGuide 都做不到

ExpeL 的 COMPARE 需要 (success, fail) 配对，SUCCESS 需要多条成功轨迹；AutoGuide 虽然可以单轨迹切片，但切完之后的情境标签要在多条轨迹间聚类才稳定。两者都需要"量"。ERL 的提取 prompt 针对单条轨迹 + 其 outcome 就能工作：LLM 直接被问"这条轨迹揭示了什么可复用的启发"，产出一条 heuristic。

这里的权衡
单轨迹抽取的代价是："启发"的普适性更弱，容易 overfit 到这一条轨迹的具体情境。ERL 的设计哲学是：不在抽取阶段强求普适，把筛选的活交给后续 relevance scoring——让"什么时候用哪条启发"留到测试时动态决定。这和 AutoGuide 的"抽取时就写 IF context THEN action"恰好是相反的两种哲学。

5.3 Relevance scoring + top-k 注入

测试时，给定新任务，ERL 让 LLM 对 pool 里每条（或经粗召回后的候选）heuristic 打一个 relevance 分，取 top-k（论文里一般 k=3-5）注入 context。这是和前两代最根本的区别：

  • ExpeL：pool 里所有 insights 一次全塞，假设它们都是通用规则，互不干扰。
  • AutoGuide：按 context 标签精确匹配，激活相关 guideline。
  • ERL：pool 大了之后全塞装不下（heuristics 单条更长），且 context 标签本身在异构任务上不好定义 → 必须连续 relevance 打分 + top-k。

5.4 Gaia2 基准 — 反超 AutoGuide

ERL 主战场是 Gaia2（GAIA 基准的第二代），分为：

  • Search split：需要调用搜索工具、多源信息整合。
  • Execution split：需要跨工具执行复杂计算 / 操作。

论文报告 ERL 在 Gaia2 上达到 56.1% 成功率，比 ReAct baseline 提升 7.8 个百分点，同时高于 ExpeL 和 AutoGuide 的复现结果。Gaia2 的任务特征（异构 tool use、context 难以离散化）正好撞在 AutoGuide 的短板上，ERL 的连续 relevance 打分因此占优。注意：这是 ERL 自己复现 baseline 的数字——所以需要客观看待这个对比（见 FAQ）。

7

关键演化论点（聚合 → 条件 → 检索）

7.1 三代演化的形式化表达

如果把"跨轨迹反思"建模成一个函数 f(pool, task) → prompt，三代的差别在于筛选函数的形态：

三代的筛选函数ExpeL : prompt = concat(all insights) // 无筛选 AutoGuide : prompt = concat({g | g.context = c(state)}) // 离散条件 ERL : prompt = top_k({(h, score(h,task)) ∀h}) // 连续相关性

从函数形式看，这是一个信息检索领域经典的演化路径：无过滤 → 基于规则 / 字段的过滤 → 基于向量 / 打分的 dense retrieval。跨轨迹反思这三代刚好完整复刻了这条路径。

论点 1：三代不是"孰优孰劣"，而是"筛选函数的复杂度递增"
每一代都在用一种更复杂的筛选函数换取更好的精准度。ExpeL 的筛选函数是常量（不筛），AutoGuide 的是离散函数（匹配），ERL 的是连续函数（打分）。函数越复杂，拟合能力越强，但代价是计算开销和对打分器本身的依赖也越强。这和机器学习从线性模型 → 决策树 → 神经网络的演化方向一致。
论点 2：这是一次隐含的 "bitter lesson" 复现
Sutton 的 bitter lesson 说："那些把人类先验塞进去的方法，长期会被让机器自己搜索 / 学习的方法打败。"
· ExpeL 的"聚合出通用规则"本质是一种特征工程——人为设计了"insight 必须是高抽象度通用规则"这个先验。
· AutoGuide 的"IF-THEN + 离散 context"仍然带有人工结构先验——假设情境可以离散化、条件可以写清楚。
· ERL 放弃了这两个先验，让检索自己决定该用什么——这是从 compression / structure 走向 retrieval 的标志性一步。
在更早的 NLP 史上，这对应从 LDA topic model → rule-based retrieval → dense retrieval 的演化。
论点 3：但 ERL 也不是终点
保留细节 + 检索的路径也有边界：pool 无限增长时，relevance scoring 本身成了瓶颈（要给 N 条 heuristic 打分）。下一代可能的演化方向是：hierarchical heuristics（粗召回 → 精筛） / graph-indexed heuristics（像 A-MEM 那样加语义边）/ self-compressing heuristics（池过大时触发"二次蒸馏"，又回到带选择性的 insights / guidelines 层，形成闭环）。事实上 24 号综述里列的 "Memory-R1" 和 "Memory+RL 联合优化"就是在做这件事。
论点 4：三代并存、非替代
工业落地里，三代其实常常共存：ExpeL 风格做"全局准则"（不论什么任务都要遵守的几条红线）、AutoGuide 风格做"状态感知小抄"（UI / 工作流阶段触发）、ERL 风格做"细节案例库"（检索过往类似问题的 solution）。把三种表征混在一个 agent 里用，比孤立选一个往往效果更好——这也是"记忆系统"从单一形式走向 hybrid 的趋势。

与 Generative Agents / 斯坦福小镇的联系

8.1 Reflection 的范围之别

小镇的 reflection 是：当 memory stream 中近期记忆的 importance 累计超过阈值，触发反思，抽取 higher-level insight 写回 memory stream。形式上和 ExpeL 非常像——都是"从一堆观察中抽取一条高层规则"。但更有趣的是：小镇的"importance 触发"机制本身已经是一种朴素的情境感知——只有"重要事件"才会触发反思，反思出的 insight 也天然携带"在什么情境下重要"的信息。AutoGuide 的 context-aware guidelines 可以看成是把这个思想跨任务化、形式化后的产物。

8.2 Relevance 打分的同源

小镇的记忆检索公式是 score = Recency × Importance × Relevance，其中 Relevance 来自当前 query 与 memory 的 embedding 相似度。ERL 的 heuristic relevance scoring 虽然换成了 LLM-as-judge，但功能位置完全一致——都是"给候选记忆 / 启发打分，只取最相关的注入"。两者都认识到：记忆 / 经验池会膨胀，必须有打分机制决定用哪些。而 AutoGuide 的 context 匹配对应的是小镇公式里的 Importance——只不过小镇是"重要度触发反思"，AutoGuide 是"情境触发规则激活"。

如果把小镇的 Memory Stream 理解为"一个 agent 一生的 experience pool"，那么小镇的 reflection 就是个人版 ExpeL——不跨任务、但跨事件。ExpeL 把这个机制从"一个 agent 内"放大到"训练任务集上"，本质是把时间维度的经验累积换成了任务维度的经验累积。AutoGuide 进一步把小镇"importance 触发"的情境感知思想显式化为 IF-THEN 规则；ERL 再进一步，承认聚合 / 条件化都会丢信息、回到基于检索的调用——这正好也呼应了小镇没有把 raw memory 扔掉的设计：反思出 insight 后，原始记忆还在 stream 里可检索。小镇在 2023 年用一个耦合的打分公式把三层都做了，ExpeL / AutoGuide / ERL 在 2024-2026 把它们拆成了三个正交的设计选择。

8.3 与 Voyager 的对照

Voyager（Minecraft 里的终身学习 agent）也有"经验库"的概念，但它的产物是可执行 JavaScript 技能函数，不是自然语言规则。映射关系：

  • Voyager skill library ≈ ExpeL insights（跨任务沉淀、可检索复用），但形式是代码。
  • Voyager 的"技能可直接执行"带来了一个 ExpeL / AutoGuide / ERL 都没有的优势：可验证——代码在环境里跑出结果，对就对、错就错。三代自然语言规则对不对，只能靠下游任务成功率间接验证。
  • 但 Voyager 的代价是只能用于"动作可代码化"的环境（Minecraft 的离散 API），在 QA / Web browsing 这类任务里就不适用——这正是 ExpeL / AutoGuide / ERL 的地盘。

9.2 FAQ — 澄清常见误解

Q1：为什么要把 AutoGuide 塞进来？它不是比 ExpeL / ERL 老吗？
时间上 AutoGuide 是 2024.11 NeurIPS 2024，正好夹在 ExpeL（2024.03 AAAI 2024）和 ERL（2026.03 arXiv）之间。如果只讲 ExpeL → ERL，会遗漏一个关键中间态："从无条件聚合 → 条件分发"这一步是独立的范式转变，没有它就跳不到 ERL 的"连续检索"。三代同读才能看到"筛选函数从 常量 → 离散 → 连续"这条清晰的演化主线。
Q2：三代里哪代最好？
没有最好，取决于任务的 context 多样性 + 是否能接受检索开销：
· 任务 context 同质、延迟敏感 → ExpeL（训练好一套通用规则，上线零开销）；
· 任务 context 离散且边界清晰（GUI / UI 流程） → AutoGuide（IF-THEN 精准激活，效率最高）；
· 任务异构、每条都要具体参考（Gaia2 类 tool use） → ERL（保留细节 + 相关性打分）；
· 实战落地 → 三者组合使用最可能取得最优结果。
Q3：ExpeL 和 Reflexion 区别是什么？不都是反思吗？
反思的时间跨度不同。Reflexion 是：在同一个任务里失败 → 反思 → 重新尝试；反思只在本任务的多个 trial 之间传递，任务结束后不保留。ExpeL（以及 AutoGuide、ERL）是：在一批训练任务里跑完，把所有经验离线反思成一个共享 pool，这个 pool 被后续所有新任务共享。一个是 intra-task 循环，一个是 inter-task 知识沉淀。Reflexion 解决"给我第二次机会"，ExpeL 系解决"别让前人的失败白费"。
Q4：ERL 真的超越 ExpeL / AutoGuide 吗？对比公平吗？
需要谨慎。ERL 报告的 "+7.8% vs ReAct, 超 ExpeL / AutoGuide" 是在 Gaia2 基准、用 ERL 团队自己复现的 baseline 上得到的。ExpeL 和 AutoGuide 原论文根本没在 Gaia2 上评过，所以这是 "ERL 把两种方法迁移到 Gaia2 后跑出的结果 vs ERL 自己"。这不等于 "ExpeL / AutoGuide 在它们的主场（ALFWorld / WebArena）也输"。更严谨的说法是：在 Gaia2 这种异构 tool use 场景下，保留 granular 细节 + 检索式调用 优于 聚合式规则 / 离散条件匹配——这和前两代原来的主场特性刚好反过来，结论合情合理，但不能简单推广为"ERL 全面超越"。
Q5：AutoGuide 的"context"和 ERL 的"relevance"在概念上不是差不多吗？
功能目标一样（都是"筛选出当前任务相关的规则"），但实现机制截然不同。AutoGuide 的 context 是预先定义的离散标签（比如 {搜索结果页, 商品详情页, 结算页}），规则库在 offline 就按这些标签索引，上线时是精确查表。ERL 的 relevance 是在线 LLM 打分，每来一个任务都要重算每条 heuristic 的分数，是连续空间的排序。前者快但依赖 context 可枚举，后者慢但适应任意新分布。工程上两者可以叠用：AutoGuide 做粗召回（按 context 取候选），ERL 做精排序（LLM 打分取 top-k）。
Q6：我该先读哪一篇？
如果你对 方法论原型感兴趣（"跨轨迹反思这个 idea 怎么来的"），先读 ExpeL——它有更完整的消融、更清晰的 Replay Buffer 类比、更好的基准覆盖、还有开源代码。
如果你关心当前 Web / GUI 场景的 SOTA 做法，先读 AutoGuide——IF-THEN 结构清晰、在 WebArena 上的对比很直观。
如果你关心异构 tool use 的当前做法（"现在 Gaia2 上什么工作有效"），先读 ERL。
理想顺序是：ExpeL → AutoGuide → ERL → 回头读 ExpeL 的 limitation 讨论，你会发现每一代都在精确回应上一代的 limitation。
