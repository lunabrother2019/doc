两套系统的架构原理对比

Stanford Smallville（2023）和 Claude Code（2026）是两个完全独立发展的Agent系统。前者是学术原型，25个NPC在虚拟小镇中生活；后者是产品级编程助手，在终端中帮助开发者读写代码。但当我们剥离表面差异，深入到架构原理层面，会发现它们在每一个核心模块上都走向了同一个抽象。这不是巧合——这是认知架构的收敛。

1.1 Agent Loop：感知-思考-行动循环

Smallville Agent Loop
感知环境 → 检索记忆(RIR加权) → 反思(阈值触发)
→ 规划(日程分解) → 行动 → 写入记忆 → 循环

每个Agent独立运行这个循环，每个"tick"（游戏时间步）执行一次。循环是同步的、周期性的。

VS
Claude Code Agent Loop query.ts
接收输入 → 构建Prompt(含记忆/工具定义) → 调用LLM
→ 解析响应(文本/工具调用) → 执行工具 → 收集结果
→ 上下文压缩(如需) → 循环

核心是 queryLoop() —— 一个 while(true) 循环，携带State对象。循环是异步的、事件驱动的。

关键差异与共同点
  • Smallville：周期驱动（每个tick），所有Agent同步执行
  • Claude Code：事件驱动（用户输入或KAIROS心跳），异步执行
  • 共同点：都是"感知 → 推理 → 行动 → 记忆"的循环，这个抽象在两个完全不同的系统中保持不变

1.2 记忆系统原理

Smallville Memory Stream

  • 数据结构：时间排序的 (timestamp, description, importance_score, embedding) 列表
  • 写入：每次观察/行动/对话都写入
  • 检索：score = α·recency + β·importance + γ·relevance（cosine similarity）
  • 容量管理：无。记忆只增不减。

Claude Code 三层记忆

层级 名称 特征 Smallville RIR 对应
L1 MEMORY.md（索引层） 永久加载到上下文，每行 ≤150 字符的指针。硬约束 200行/25KB。 对应 importance 维度 —— 只保留"重要的"
L2 Topic Files（知识层） 按主题组织的详细记忆文件，按需 fetch。 对应 relevance 维度 —— 只加载"相关的"
L3 Raw Transcripts（原始层） 完整对话历史，只 grep 特定标识符。 对应 recency 维度的反面 —— 最旧的最不可能被完整读取
两者都解决同一个问题：有限上下文窗口 vs 无限增长的经验。Smallville 用一个公式（RIR加权）在检索时做过滤；Claude Code 用三层架构在存储时做分级 —— 更工程化，但本质相同。

1.3 反思/整合原理

Smallville Reflection
  • 触发：sum(importance_scores) 超过阈值
  • 过程：用LLM对最近100条记忆生成3个高层问题 → 检索相关记忆 → 生成5条洞见
  • 存储：洞见作为新记忆写回 Memory Stream（与原始记忆同等对待）
  • 时机：行动循环中，占用推理时间
VS
Claude Code autoDream
  • 触发：4个条件同时满足（24h间隔 + 5+新会话 + 无并发 + 10min冷却）
  • 过程：Consolidate（合并观察、删除矛盾、模糊→确定）→ Prune & Index（保持200行、删过时指针）
  • 存储：更新 MEMORY.md 和 Topic Files（分级存储，不混同原始记忆）
  • 时机：后台空闲时运行，不占用用户交互时间
两者都是"将低层经验压缩为高层知识"。区别：Smallville 只做"加法"（生成新洞见），autoDream 还做"减法"（删除矛盾和过时信息）。autoDream 的"后台运行"是工程优化，但暗含一个深刻的认知科学类比：人类的记忆整合也发生在睡眠中。

1.4 规划原理

Smallville Planning
  • 长期：每天早晨生成全天粗粒度日程（5-8块）
  • 短期：将每块分解为具体行动
  • 调整：遇到新事件时重新规划当前块
  • 本质：计划-执行-调整的三段式
VS
Claude Code Planning (KAIROS)
  • 无显式长期规划
  • 实时：每个心跳（几秒）评估"now what?"
  • 工具选择即规划：LLM在每次迭代中决定调用哪个工具
  • 本质：连续的推理-行动交替（ReAct范式）
两者都将"大任务"分解为"小步骤"。Smallville 预先分解（plan-then-execute），Claude Code 实时分解（reason-then-act）。随模型能力增强，预先规划的价值在降低 —— LLM足够强时，实时推理可以替代预先规划。

1.5 多Agent协调原理

Smallville Multi-Agent
  • 协调方式：空间邻近触发（两个Agent物理上碰面 → 开始对话）
  • 信息传播：口口相传（A告诉B，B告诉C）
  • 无中心协调者
  • 25个Agent，完全平等
VS
Claude Code Multi-Agent
  • Agent Teams：1个team lead + 2-16个worker，共享任务列表和点对点消息协调
  • Subagent：父Agent通过Agent工具生成子Agent，子Agent有独立上下文窗口
  • 通信：Mailbox模式（SendMessageTool发送到命名信箱，接收者轮询/订阅）
  • Coordinator模式：中心Agent分配任务，worker并行执行，Permission Queue处理危险操作
两者都面临同一个问题：多个Agent如何共享信息而不互相干扰。Smallville 用物理空间作为隐式协调机制（你只能和"看得到"的人说话）；Claude Code 用显式的消息传递和任务分配。两者都没有全局共享内存 —— 信息通过"对话/消息"传递，不是直接读取对方记忆。

1.6 上下文管理（Claude Code 独有）

Smallville 完全没有的模块
Claude Code 面对一个 Smallville 不需要处理的问题：LLM的上下文窗口是硬性有限的。这催生了一个精密的5级压缩瀑布。

消息存储机制

Append-only JSONL。旧消息不删除，新消息在压缩后追加。消息带标志控制API可见性：

// 消息可见性标志
isCompactSummary: boolean // 是压缩摘要
isVisibleInTranscriptOnly: boolean // 仅在转录中可见
isMeta: boolean // 元信息

// 关键函数：只返回压缩边界之后的消息给API
getMessagesAfterCompactBoundary()
与Smallville的联系
Smallville 也面临类似问题（记忆太多时检索变慢），但用"加权检索"优雅回避了。Claude Code 的上下文压缩本质上是"强制遗忘"—— 这正是学术界（MemoryBank、MemoryOS）在研究的问题在工程中的暴力解法。

五层架构与源码阅读入口

Claude Code 的源码可以按5层架构理解。每一层有明确的职责边界和入口文件：

Layer 1
Entrypoints
main.tsx → CLI入口，React Ink渲染终端UI。这是用户键入 claude 后第一个执行的文件。
Layer 2
Runtime
sessionRunner.ts → 会话管理 | bridgeMain.ts → 桥接层（IDE/Web/SDK统一接口）。处理不同运行环境的适配。
Layer 3
Engine
QueryEngine.ts (46,000行) → 核心引擎 | query.ts → Agent循环。这是整个系统最核心、最复杂的层。
Layer 4
Tools
src/tools/ → 每个工具一个模块（Read, Edit, Bash, Grep, Agent等）。工具系统是Agent能力的边界。
Layer 5
Infra
权限系统、MCP服务器集成、hooks、配置。支撑整个系统安全运行的基础设施层。

源码阅读路线图（从 Smallville 视角）

推荐按以下顺序阅读，每一步对应 Smallville 的一个核心概念：

01
路线一：Agent Loop（对应Smallville的感知-行动循环）
src/core/query.ts → queryLoop() 函数
这是一个 while(true) 循环，是整个系统的心脏。
  • State对象的结构（messages, toolUseContext, autoCompactTracking等）
  • 每次迭代如何决定"调工具"还是"回复用户"
  • 工具调用的执行流程（调用 → 收集结果 → 追加到messages）
这就是Agent的"一个tick" —— 感知（读取消息）→ 推理（LLM调用）→ 行动（工具执行）→ 记忆（结果追加）
02
路线二：记忆系统（对应Smallville的Memory Stream）
src/memory/（auto memory模块）
Claude Code的记忆是分级的、选择性的，与Smallville的"记住一切"形成鲜明对比。
  • MEMORY.md的读写逻辑：如何决定什么值得记住
  • Topic Files的创建和检索
  • 记忆类型分类（user, feedback, project, reference）
  • 写入纪律：什么条件下才写入
对比 Memory Stream 的"记住一切" vs Claude Code 的"选择性记忆"
03
路线三：上下文压缩（对应Smallville的记忆检索）
query.ts 中的压缩瀑布（约 L379-L453）
这是学术论文不会告诉你的工程核心 —— 如何在硬性有限的上下文窗口中保持最大信息量。
  • 5级压缩策略的触发条件和优先级
  • autoCompact如何fork一个子agent做摘要
  • 压缩后消息的可见性标志
  • getMessagesAfterCompactBoundary() 的过滤逻辑
Smallville 用 RIR加权 做"软过滤"（所有记忆都在但权重不同），Claude Code 用压缩做"硬过滤"（旧内容直接不可见）
04
路线四：反思/整合（对应Smallville的Reflection）
autoDream 相关逻辑（feature flag: KAIROS）
Smallville的反思是实时的、阈值触发的；Claude Code的整合是后台的、条件门控的。
  • 触发条件的4个门控
  • Consolidate阶段如何合并和清理
  • Prune如何维持200行约束
  • 与Memory System的交互
对比 threshold-triggered reflection vs condition-gated consolidation
05
路线五：工具系统（对应Smallville的Action）
src/tools/ 目录
Smallville的"行动"是在沙盒中移动/使用物品/对话，Claude Code的"行动"是读文件/写代码/搜索/执行命令。抽象相同，实现不同。
  • 每个工具的 input schema 定义
  • 权限模型（哪些工具需要用户确认）
  • 工具执行的隔离上下文
  • Agent工具（src/tools/Agent.ts） —— 这是多Agent的核心，一个工具就能生成子Agent
Smallville的Action是沙盒内有限的物理操作；Claude Code的Action是开放的工具调用。但两者都需要"权限门控"：Smallville靠环境规则约束，Claude Code靠显式权限系统。
06
路线六：多Agent协调（对应Smallville的Agent间交互）
src/tools/Agent.ts + src/bridge/bridgeMessaging.ts
从Smallville的25个平等NPC到Claude Code的层级化Agent Teams，多Agent协调的范式发生了根本变化。
  • Agent工具如何生成子Agent（subagent_type, model选择, isolation模式）
  • SendMessageTool的Mailbox通信模式
  • Agent Teams的coordinator/worker分工
  • 父子Agent间的上下文隔离（子Agent有独立上下文窗口，只返回结果）
Smallville 用物理空间做隐式协调，Claude Code 用显式消息传递。但两者的信息流模式相同 —— Agent不能直接读取对方的"记忆"，只能通过"对话"交换信息。
07
路线七：QueryEngine 深潜（高级）
src/core/QueryEngine.ts (46,000行)
这是Smallville论文没有讨论的"工程冰山" —— 如何高效可靠地调用LLM。
  • Prompt构建逻辑（system prompt + 记忆 + 工具定义 + 消息历史如何拼接）
  • Streaming处理
  • Token计数和成本追踪
  • Prompt caching策略
  • 重试和错误处理
Smallville论文中一句"We use GPT-3.5"背后，在生产环境中是46,000行的工程代码。

给读者的建议

如果你是研究 Smallville 的学生
读 Claude Code 源码能帮你理解"论文中的抽象概念在生产环境中长什么样"。重点读路线一（Agent Loop）和路线二（记忆系统），这两个模块和论文的对应最直接。当你看到 queryLoop() 的 while(true) 循环时，你会发现它和Smallville的tick循环在抽象层面惊人地一致。
如果你是做 Agent 工程的开发者
重点读路线三（上下文压缩）和路线五（工具系统），这是学术论文不会告诉你的工程 know-how。特别是5级压缩瀑布 —— 这是处理"上下文窗口有限"这个硬约束的最完整工程方案。每一级都有明确的触发条件、成本权衡和降级策略。
如果你是做多 Agent 研究的
重点读路线六（多Agent协调），对比 Claude Code 的 Mailbox 模式和学术论文中的各种拓扑（star/chain/tree/graph）。Claude Code 选择了 Mailbox（本质是异步消息传递），而不是共享内存或层级控制 —— 这个工程选择背后有深刻的原因：异步消息传递天然支持容错和扩展，而共享内存在分布式环境中是灾难。
