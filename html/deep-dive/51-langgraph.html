1

一句话定位：把 Agent 从"线性 chain"升格为"有状态图"

LangChain 早期的 Agent 抽象（AgentExecutor）是一个黑盒 while-loop：LLM → tool → LLM → tool …，开发者既难看清执行流向，也难插入"人类审批"、"中断续跑"、"跳回上一步重试"这些真实产品需求。LangGraph 的做法是把 Agent 反过来看：所有控制流都显式为一张图，节点是函数，边是跳转规则，图上流动的是一个共享状态（State）。整个执行是一次状态机遍历，由框架持久化每一步的状态快照，因此天然支持回溯、重放、人类接管、长运行恢复。

一句话核心主张
"Agent = StateGraph（显式节点 + 条件边 + 持久状态）"。LangGraph 不是 LangChain 的升级版，而是一个更底层的Agent 运行时（runtime）。LangChain 的高层 create_agent 现在也是 基于 LangGraph 实现的 —— 图是新的基座，chain 变成了图的一个特例（有且只有线性边）。

为什么要"图化"？四个驱动力
  1. 循环成一等公民：ReAct、Reflexion、Plan-and-Solve 本质都是"LLM ⇄ tool/env"的循环。在 chain 里只能用 while 假装，在图里就是一条回边。
  2. 多 Agent 协作需要分发/汇合：MetaGPT / ChatDev 那种"分工–审阅–综合"模式，在图里就是 fan-out / fan-in。
  3. 长运行任务需要持久化：跑 4 小时的 agent 中途宕机，需要从 checkpoint 复活 —— 只有状态机能给这个保证。
  4. 人类介入需要中断点：审批、注入修正、纠偏，这些都需要可暂停的执行模型，线性 chain 天然做不到。

图式 State Machine 架构：节点 + 边 + 状态三件套

2.1 三大原语：StateGraph / Node / Edge

① State（状态）

定位：图上所有节点共享的、类型化的结构（通常是 TypedDict、Pydantic 或 dataclass）。

Reducer：每个字段可配聚合函数（如 operator.add）—— 并行节点返回的部分状态如何合并，由 reducer 决定。

类比：React 的 Redux store，或者 Elm Architecture 的 Model。

② Node（节点）

定位：纯函数 state → partial_state。接收当前 State，返回对 State 的增量更新。

典型节点：LLM 调用、工具执行、校验器、路由器、人类审批等待点。

关键约束：节点只能通过返回 partial_state 修改状态，不能副作用式写全局 —— 这是可回溯的基础。

③ Edge（边）

普通边：add_edge(a, b) 固定从 a 到 b。

条件边：add_conditional_edges(a, router_fn, {...}) —— router 读 State，动态决定下一站。这就是循环 / 分支 / 终止的统一机制。

特殊节点：START 与 END 是框架内置的入口/出口标记。

2.2 一个最小可运行骨架

# 5 行 hello-world：LLM + tool 循环 from langgraph.graph import StateGraph, START, END, MessagesState def agent_node(state: MessagesState): return {"messages": [llm.invoke(state["messages"])]} def should_continue(state): last = state["messages"][-1] return "tools" if last.tool_calls else END graph = StateGraph(MessagesState) graph.add_node("agent", agent_node) graph.add_node("tools", tool_node) graph.add_edge(START, "agent") graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END}) graph.add_edge("tools", "agent") # 回边 → ReAct 循环 app = graph.compile(checkpointer=InMemorySaver())

这短短 10 行就展示了 LangGraph 的全部核心机制：显式循环（tools → agent 的回边）、条件分支（should_continue）、持久化（checkpointer）。

2.3 高级原语：Checkpointer / Interrupt / Send / Subgraph

① Checkpointer（持久化引擎）durable execution

每个"超步"（super-step）结束，框架把 State 快照写入 checkpointer（支持 Memory / SQLite / Postgres / Redis）。这意味着：程序崩溃可复活、session 可跨天续跑、任意时刻可回到过去的某个 state 重放分支。

Checkpointer 的实现依赖一个关键概念 —— thread_id：多个用户或多个 session 共用一张图定义，但状态按 thread 隔离，天然支持 multi-turn。

② Interrupt（人类接管入口）HITL

图可以在任意节点处主动抛出中断（interrupt()），等待外部 resume。中断时 State 已落盘，人类可以：审批 / 改写 state / 注入消息 / 跳过该节点。

这是 LangGraph 相对 AutoGen 的最显著差异：HITL 不是回调或中间件，而是图的内建调度点。

③ Send（动态 fan-out）map-reduce

一个节点可以返回 [Send("worker", payload_1), Send("worker", payload_2), …]，框架并行调度多个 worker 实例，再由 reducer 汇合。这就是 map-reduce 的图版本 —— 典型场景：把一个大文档拆 N 段让 N 个 LLM 并行摘要，再合并。

④ Subgraph（图嵌套）composition

一个图可以作为另一张图的节点，状态在父子图之间映射。这是组合复杂 multi-agent 系统的标准姿势：每个 Agent 自己是一张子图，外层图负责编排他们。

MetaGPT 的 PM/架构师/程序员/QA 流水线，在 LangGraph 里最自然的表达就是 4 个 subgraph + 一张外层 DAG。

⑤ Time Travel（时间旅行）replay / fork

因为每步 state 都被 checkpoint，开发者可以：列出一个 thread 的所有历史快照 → 选一个旧快照作为起点 → 从这里分叉一条新路径。这对调试多 Agent 系统是革命性的 —— 不再需要靠反复运行复现 bug。

配合 LangSmith（LangChain 的可观测平台），每一个中间 state 都可视化。

⑥ Command（节点内路由）state update + goto

节点不仅可以返回 partial_state，还可以返回 Command(update={...}, goto="node_x") —— 同时更新状态和显式指定下一节点。这等于把"边"的决策权部分下放给节点，适合需要由节点自己"知道下一步该去哪"的场景。<待实证>：Command 的语义细节（与 conditional edge 的优先级）需对照官方文档。

2.4 执行语义：Pregel-style super-step

LangGraph 的执行模型借鉴了 Google Pregel：把每一轮执行切成一个"超步"，所有在本超步中被激活的节点并行执行，他们的输出通过 reducer 合并写回 State，然后基于新 State 决定下一超步激活谁。

LangGraph 执行的一个 super-step（伪码） active_nodes = select_by_incoming_edges(state) # 谁被激活 updates = parallel_exec(active_nodes, state) # 并行跑 state = reduce_merge(state, updates) # 合并状态 checkpoint(state, thread_id) # 落盘快照 if all_edges_land_at(END) or interrupt_raised: halt else: goto next super-step

这个模型意味着：图上任何可以并行的分支，框架自动并行；任何需要同步的汇合点，框架自动等待。开发者只需要声明"谁依赖谁"，不需要自己管线程。

和 DAG workflow 工具（Airflow / Prefect）的区别
表面上都是"图上跑任务"，但 LangGraph 区别于 Airflow：① 状态是一等公民（Airflow 任务间只传 XCom 小包）；② 允许循环（Airflow 是严格 DAG，不能自环）；③ 粒度是秒级（Airflow 节点通常分钟级+）；④ 为 LLM 设计的 reducer / message 语义。一句话：LangGraph 是"为 Agent 小步循环而设计的持久化状态机"，而不是"离线 batch DAG"。

与 LangChain Chain 的本质区别：stateful / 可回溯 / 可 HIL

很多人会问："LangChain 不是已经有了 AgentExecutor 和 LCEL chain，为什么还要 LangGraph？"一句话回答：chain 的抽象对"循环 + 持久化 + 人类介入"这三件事是不够的。

迁移策略：chain 还是图？
官方立场很清晰 —— 简单管道继续用 LCEL，但凡涉及循环/多 agent/持久化/HIL，直接上 LangGraph。LangChain 新版 create_agent 底层已切换为 LangGraph 实现，某种意义上"chain"的时代已经让位给"图"。

3.1 三个痛点的具象对比

场景 A：ReAct agent 需要无限循环直到任务完成
  • LangChain：AgentExecutor 内部黑盒 while，外部看不到每步 state，中断 = kill 进程。
  • LangGraph：agent ⇄ tools 是两个节点 + 一条回边 + 一个 should_continue 条件。每次循环都是一次 super-step，自动 checkpoint，任何时候 interrupt 可挂起。
场景 B：用户中途说"等等，改一下参数再继续"
  • LangChain：没法优雅暂停 —— 要么让 chain 跑完，要么直接 kill。
  • LangGraph：在关键节点前放 interrupt_before，UI 拿到 state 让用户改，改完 resume 继续。从 state 改动点往下重跑即可，之前的工作不丢。
场景 C：长跑任务 4 小时后崩了
  • LangChain：从头开始跑，4 小时和 200 次 API 调用都没了。
  • LangGraph：相同 thread_id 重启进程，自动从上次 checkpoint 恢复，只需重放最后一个未完成的 super-step。
场景 D：调试 multi-agent 协作
  • LangChain：只能靠 print / LangSmith trace 反复复现。
  • LangGraph：列出 thread 的所有 checkpoint → 挑出异常快照 → 从那里 update_state 修改变量 → fork 一条新路径验证假设。
Smallville 里每个 agent 有 memory stream + reflection + planning 三层循环。用 LangGraph 表达的自然形式是：一张父图编排 25 个 agent 的 subgraph；每个 agent 子图内部是 perceive → retrieve → reflect? → plan? → act 的条件分支。25 份 state 各自 checkpoint 到独立 thread，运行一两个"游戏日"后崩溃可以无损恢复 —— 这正是原版斯坦福实现里缺失、作者在论文里提到"仿真可靠性低"的问题的根治方案。

4.1 三种抽象哪种更"对"？

没有绝对答案，但有三条经验规律：

  • 工作流导向 → 图：如果你的 Agent 是"要依次做 A→B→C，中间可能回 B 再来一次"，图最自然。LangGraph 的节点/边模型对此是最贴合的。
  • 对话导向 → 群聊：如果 Agent 协作是"几个角色你一句我一句讨论"，AutoGen 的 GroupChat 最简洁。
  • 仿真/大规模导向 → Actor 总线：如果需要成百上千个 Agent 独立演化偶尔交互（Smallville-like 场景），actor 模型（AgentScope、MegaAgent 等）更有扩展性。
一个有趣的观察：三者正在互相借鉴
AutoGen 0.4 加入了 event-driven 与类似 graph 的编排；AgentScope 新版本加入了流程图 DSL；LangGraph 则通过 Subgraph 支持群聊式角色扮演。图 / 总线 / 群聊正在收敛成同一个东西的不同投影：一个有显式状态、可暂停、可回溯、支持多角色的 runtime。区别将越来越表现在"默认抽象"和"生态集成"而非"能否做到"。

4.2 LangGraph 的独特优势

  1. LangChain 生态黏性：直接复用 LangChain 数百种 LLM 封装、数百种工具、VectorStore、Retriever；LangSmith 开箱即用观测。
  2. 生产级 HITL 是第一公民：interrupt + update_state + resume 是规划层面的设计，不是贴上去的中间件。
  3. Time Travel 是天花板：就算其他框架做了 checkpoint，也很少把"从历史 state 分叉"做到 API 级别。这对 agent 调试是质变。
  4. 部署产品线完整：LangGraph Platform / LangGraph Cloud 提供托管 agent server，一键上线。<待实证>：具体产品化程度（收费模式、SLA）需查官方产品页。

用例场景：复杂工作流 Agent 与 Multi-turn 对话

5.1 用例 A：企业级复杂工作流 Agent（Klarna / Replit）

场景：Klarna 的客服 Agent 处理一个退款请求，需要：① 查用户订单 → ② 验证退款条件 → ③ 风控评分 → ④ 高价订单触发人工审批 → ⑤ 调支付 API → ⑥ 发邮件通知 → ⑦ 记录 CRM。整个流程可能跨越数分钟到数小时，任何一步可能失败需重试。

这个流程图在 LangGraph 里就是字面意义上的 6 个节点 + 2 条条件边（风控分支、人审 gate）+ 1 条并行分发（通知与 CRM 同时）。关键收益：

  • HITL 不是特例：人审节点就是一个 interrupt()，审批员在 UI 上看到的是当前完整 state。
  • 断点续跑：审批员下班了，明早来审批也没问题 —— 状态在 Postgres 里躺着。
  • 可审计：每一步 state 快照都存档，监管问"为什么这单被批了"时可以原封回放。

5.2 用例 B：Multi-turn 对话 Agent（带记忆 + 工具）

经典场景：用户和 Assistant 多轮对话，Assistant 需要：① 记住用户 preference；② 在必要时调工具（搜索、计算、数据库）；③ 处理"撤销上一条"这类指令。

LangGraph 表达 multi-turn agent StateGraph( MessagesState + UserPreferences ) ├─ perceive # 解析最新用户消息 ├─ retrieve # 从长期记忆检索相关片段 ├─ agent # LLM 决策：回答还是调工具 ├─ tools # 工具执行 └─ respond # 最终回复 + 更新 preference thread_id = user_id # 不同用户状态天然隔离

关键点：MessagesState 的 messages 字段使用 add_messages reducer，所以每次节点只需返回 "要追加的消息"，框架自动把它合并到历史。这就是为什么 LangGraph 的 multi-turn 比 chain 的"在内存里维护一个 list"更可靠 —— state 是结构化的、持久的、类型化的。

5.3 用例 C：多 Agent 协作（MetaGPT / ChatDev 风格）

外层 StateGraph（"软件开发项目"） ├─ PM 子图 (需求 → 用户故事) │ └─ interrupt：用户审核用户故事 ├─ 架构师子图 (用户故事 → 架构图) ├─ 程序员子图 (架构 → 代码) │ └─ Send × N fan-out 到多个文件并行生成 ├─ QA 子图 (代码 → 测试报告) └─ 条件边：测试失败 → 回到程序员子图

这就是 MetaGPT 纸面流程的精确翻译。每个角色是一个 subgraph，外层图用条件边控制"跑通就发布，没跑通就回去改"。Time Travel 在这里的价值特别大：产品经理可以回到"用户故事刚写完"的状态，改需求再 fork 一条新路径，和现在这条对比。

5.4 用例 D：长运行 Research Agent

给 agent 一个研究题目："分析 2024 年欧洲碳市场走势"，它需要：搜索 → 总结 → 建立笔记 → 反思 → 继续搜索 → 合成报告，可能持续数小时、产生上百条工具调用。用 LangGraph 实现：

  • 外循环是 search ⇄ summarize ⇄ reflect 三个节点带回边，直到 enough_evidence 条件成立。
  • 每次回边触发 checkpoint；即便宿主机挂了，换一台机器按同一 thread_id 启动进程，从上次断点继续。
  • 研究员（人）可以随时 get_state 看 agent 当前在想什么，必要时 update_state 注入指导（"别再查这个方向了，看看 X"）。
这类用例里 LangGraph 的"最后一公里"痛点
  1. State schema 设计是门艺术：字段太少状态表达力不够，太多 checkpoint 序列化开销爆炸。
  2. Reducer 易错：operator.add 对 list 是追加，对 dict 是合并吗？初学者容易踩坑。
  3. 大 State 序列化：如果把大文档整个塞进 state，每一超步都复制一遍 —— 性能下降明显。实践中会用引用（S3 key、DB id）。
  4. 图结构一旦上线难以修改：改了图但旧的 checkpoint schema 不匹配，需要迁移策略 <待实证>（官方是否提供 schema migration 工具需查文档）。
Smallville 的"一个游戏日"本质上就是一个持续 24 小时模拟时间的长运行 agent 集群。原版实现崩溃就要从头再来，这是它 scale 不上去的关键原因之一。LangGraph 的 Checkpointer + thread_id 设计恰好就是为这个而生的 —— 如果重写斯坦福小镇，这几乎是默认选项。

FAQ

Q1：我已经在用 LangChain LCEL 写 chain 了，迁到 LangGraph 要重写多少？成本值得吗？
具体看场景。如果你的 chain 就是"一次 RAG + 一次回答"这种线性管道，其实不需要迁移 —— LCEL 足够好。但如果你已经在 chain 里写过这样的代码：① 用 RunnableLambda 套了 while 循环；② 拿 callback 做"某步之前让用户确认"；③ 用外部 Redis 自己维护 conversation state；④ 需要在多个 chain 之间分发任务再合并 —— 那几乎是明确的信号：你正在用 chain 模拟状态机，迁到 LangGraph 代码会大幅精简。官方的 create_agent 本身已经是 LangGraph 实现，所以"用 LangChain 的高层 API"其实已经悄悄等于"在用 LangGraph"。

迁移时有两个常见阻力：①State schema 要先设计，不能像 chain 那样 dict 随便塞 —— 这一步花时间，但长期代码可读性、可测试性受益明显；② LCEL 的流式语法（.stream()）和 LangGraph 的 stream 语义略有差异，流式响应前端要适配。整体看，对多 Agent / 长运行 / HIL 三类场景，迁移的 ROI 在 1-2 周内见效。
Q2：LangGraph 的"图 + 持久化"听起来像是把应用逻辑和数据库耦合了，这不会让测试和本地开发变难吗？
这是一个真实的顾虑，但框架在设计上已经缓解了大半。关键是 Checkpointer 是可插拔的接口：本地开发用 InMemorySaver —— 就是个内存字典，单元测试零开销；集成测试用 SqliteSaver —— 单文件、跑完删掉；生产环境切到 PostgresSaver / RedisSaver，代码零改动。所以应用逻辑和"具体什么数据库"没有耦合。

真正需要建立的新心智模型是："State schema 是你的数据库 schema"。你在设计 TypedDict 时等同于在设计一张表，字段增删要考虑兼容老 checkpoint。这比"chain 里随便传 dict"多一层约束，但它换来的是：① 回溯能力；② HIL 不糊弄；③ 调试时能看到每一步的完整世界状态。

至于"测试变难"—— 实际经验是 反而变容易：你可以直接构造一个 state dict 丢给任意节点跑单元测试，再断言输出的 partial_state；集成测试可以用 Time Travel，构造一个"经过 5 步运行之后的 state"然后验证第 6 步行为，不用把前 5 步都跑一遍。这是"显式状态"带来的测试性红利，chain 时代是很难做到的。最后一个小坑：<待实证> checkpointer 在高并发下的性能特性（尤其是 Postgres 底层是否有行锁争抢），官方给出过基准数据但需要结合自己的负载压测，不宜迷信默认配置直接上线。
