3.2 排除 GLM 嫌疑

候选召回流程中 GLM 没有参与：

候选召回流程（问题出在这里）: ┌─────────────────────────────────────────────────────────────┐ │ user 历史 → GLM 生成 profile 文本 → MiniLM 编码 (384d) │ │ ↓ │ │ item meta (title+cat+desc) ────→ MiniLM 编码 (384d) │ │ ↓ │ │ cosine_sim(user_emb, 13776 item_embs) → top-50 │ │ ↑ │ │ └── 问题在这一步：50/13776 太稀疏 │ └─────────────────────────────────────────────────────────────┘ GLM 的角色（在召回之后才参与）: ┌─────────────────────────────────────────────────────────────┐ │ Stage1: GLM 为候选物品写推广 → GLM 扮演用户打分 1-5 │ │ Stage2: 纯算法重排（不用 GLM） │ │ │ │ → 这些都发生在 top-50 之后，无法挽救召回率为零的问题 │ └─────────────────────────────────────────────────────────────┘

4. 根因分析

原因一：候选池比例失调

合成数据: top-50 / 286 物品 = 17.5% 覆盖率 → 能 work
真实数据: top-50 / 13,776 物品 = 0.36% 覆盖率 → 必然失败

TOP_K_CANDIDATES = 50 是为 286 物品设计的，直接搬到 13,776 物品没有调整。

原因二：语义鸿沟（query-document mismatch）

all-MiniLM-L6-v2 是通用语义相似度模型，不是为 "用户画像 → 物品描述" 的跨模态匹配训练的。

user profile embedding 的来源item embedding 的来源
"This user enjoys jazz and classic rock, prefers relaxing evening music with smooth instrumentals..." "Greatest Hits by Artist_X. Category: Rock. 12 tracks including..."

这两种文本在 MiniLM 的语义空间中未必接近——一个是偏好描述，一个是物品事实描述。在 286 物品时空间小、碰巧能 work；13,776 物品时噪声淹没了信号。

原因三：无协同过滤信号

当前候选召回完全基于内容相似度（content-based），没有利用协同过滤信号（"买了 A 的人也买了 B"）。真实推荐系统几乎都用协同过滤做召回，内容相似度做补充。

5. 修复方向

方案 A：扩大候选池 最简单

改动：TOP_K_CANDIDATES = 50 → 500
覆盖率：500/13776 = 3.6%（×10）
代价：LLM 调用量 ×10（Item 推广 500次/用户），耗时可能 30+ 小时
是否解决根因：缓解但不根治。3.6% 覆盖率仍然很低，且依赖 embedding 质量

方案 B：协同过滤预筛选 推荐

思路：利用用户历史交互的物品，找同类别 / 同艺人 / 被相似用户交互过的物品，优先放入候选池
实现： 
# 伪代码
def hybrid_recall(user, item_embeddings, item_meta, train_data, k=200):
    history_items = train_data[user]
    history_categories = {item_meta[i]["category"] for i in history_items}

    # 路径1: 同类别物品（协同过滤简化版）
    same_cat = [iid for iid, m in item_meta.items()
                if m["category"] in history_categories
                and iid not in history_items]

    # 路径2: embedding 相似度（保留原有逻辑）
    emb_top = top_k_similar(user_emb, item_embeddings, k=k)

    # 合并去重，优先保证 same_cat 覆盖
    candidates = merge_and_dedup(same_cat[:100], emb_top[:150], k=200)
    return candidates
覆盖率：用户历史类别内的物品通常数百~数千个，test item 大概率在其中
代价：改动 ~30 行代码，无额外 LLM 调用
是否解决根因：直接解决。协同过滤信号是推荐系统召回的核心

方案 C：混合召回 最稳健

思路：多路召回合并，确保覆盖率
候选池 = 合并去重(
    embedding_top_200,          # 语义相似
    same_category_top_100,      # 类别协同
    popular_in_category_top_50, # 类别热门
    random_sample_50            # 随机负例（用于公平性评估）
) → ~300-400 候选
优势：即使某一路召回失效，其他路仍能兜底
代价：候选池扩大到 300-400，LLM 调用量 ×6-8，但配合异步并发仍可控

方案对比

方案改动量能否解决LLM 成本推荐度
A. 扩大 top-K改 1 个常量缓解×10低
B. 协同过滤预筛选~30 行大概率解决×2-4中
C. 混合召回~60 行最稳健×6-8高（配合异步）
